# Unit tests of this package

Notes of dawcore Package (`@dawcore/components`), moved out of the package's `CLAUDE.md`. Read before writing or changing a test in `src/__tests__` (after the skill `unit-testing`).

**Testing gotchas:**

- `isConnected` is a readonly getter in happy-dom — cannot be set via `Object.assign` on elements. Append the element to `document.body` instead.
- Mocks for async functions (e.g., `resumeGlobalAudioContext`) must return `Promise.resolve()`, not `undefined`. Calling `.catch()` on `undefined` crashes.
- `canvas.getContext('2d')` returns `null` in happy-dom. Tests must mock it: `vi.spyOn(canvas, 'getContext').mockReturnValue(mockCtx as any)` where `mockCtx` has `clearRect`, `resetTransform`, `scale`, `fillStyle`, `fillRect` as `vi.fn()`.
- `PointerHandlerHost` and `ClipPointerHost` test mocks must include beats-mode fields (`scaleMode`, `ticksPerPixel`, `bpm`, `ppqn`, `_meterEntries`, `snapTo`, `renderSamplesPerPixel`). Default to `scaleMode: 'temporal'`, `snapTo: 'off'` for non-beats tests.
- `<daw-editor>` test mocks of `_peakPipeline` must include `terminate: vi.fn()` — `disconnectedCallback` calls it on `editor.remove()` and silently fails every test in the file with `TypeError`.
- **Use the shared harness** (`src/__tests__/helpers/editor-harness.ts`, #848): the editor builds a real engine on its arrangement at connect, so a bare `{ audioContext }` adapter makes the engine's adapter calls throw (`setTracks is not a function`, reported by vitest as unhandled rejections after a green run: read the exit code). `makeFakeAdapter()` is complete (`updateTrack` included, so the incremental path runs); `stubFetch` and `holdDecode` drive the arrangement's loading instead of replacing editor internals.
- Mock `PlayoutAdapter` for `<daw-editor>` tests must also include `init: vi.fn().mockResolvedValue(undefined)` and `isPlaying: vi.fn().mockReturnValue(false)` (in addition to `updateTrack` above). Minimal mock shapes crash on lifecycle paths the editor exercises during element setup. When writing a new editor test, copy `daw-editor-midi.test.ts:makeMockAdapter` rather than hand-rolling a thinner mock.
- **Lit calls a property's setter with `null` when its attribute is removed** (default converter, no `useDefault`). A custom setter that validates must treat `null`/`undefined` as "back to the default" without a warning: `<daw-track>`'s `renderMode` setter warned `render-mode="null" is not a render mode` on `removeAttribute('render-mode')` until `normalizeRenderMode` handled it (#763).
- `<daw-clip>.start` is `@property({ type: Number })` WITHOUT `reflect: true` — setting the JS property does NOT update the attribute. Tests asserting on `c.getAttribute('start')` will read `null` regardless of impl correctness. Use `(c as DawClipElement).start` (property access) instead.
- TDD failure-mode tests that intercept `editor.addTrack` to fail the Nth call should discriminate by `callCount` — NOT by introspecting `config.clips[0].midiChannel` or similar. The impl might use `addTrack({ midi: { ... } })` shorthand instead of `addTrack({ clips: [...] })`; a config-shape discriminator breaks silently. See `daw-editor-load-midi.test.ts` tests 8 and 9 for the pattern.
- happy-dom has no layout engine: `scrollLeft`/`scrollTop` assignments are NOT clamped, and `scrollWidth`/`scrollHeight`/`clientWidth`/`clientHeight` default to 0. Tests emulating scrollable or scroll-at-limit containers must stub these via `Object.defineProperty` (no-op setters emulate a clamped container).
- Fit-to-width elements (`<daw-player>`) read `clientWidth` during `render()` — since happy-dom returns 0, tests asserting rendered waveform channel count must stub at the PROTOTYPE level (`Object.defineProperty(HTMLElement.prototype, 'clientWidth', { configurable: true, get: () => 500 })`) in `beforeAll` + restore in `afterAll`. A per-element stub doesn't survive because the `.waveform-area` node is recreated on each render.
- Container queries are not evaluated in happy-dom — assert structure (classes) and `static styles` cssText instead; verify actual compact/responsive behavior in a real browser.
- `editor.addTrack({ name, midi: { notes } })` is the lightweight way to get fully loaded tracks in editor template tests — no fetch/decode. See `daw-editor-layout.test.ts` `makeEditor()`.
- Test cleanup (spy `mockRestore`, removing appended `daw-editor`s) belongs in `afterEach`, never as the last line of a test body — a failed assertion skips trailing cleanup and silently poisons subsequent tests in the file.
- After refactoring test cleanup, run `pnpm typecheck` too — vitest passing doesn't catch newly-unused destructured bindings (`TS6133` under `noUnusedLocals`).
- **Adding an optional trailing parameter breaks exact-args `toHaveBeenCalledWith` assertions** — vitest treats the callee's explicit trailing `undefined` as a mismatch against fewer expected args. Sweep existing assertions on that function and append `undefined // newParam` (see the `_addRecordedClip` clipName sweep in recording-controller.test.ts).
- happy-dom doesn't model `<option>` selectedness dirtiness or pointer-event delivery to hosts of disabled shadow controls — `?selected` toggles that break after a real user pick, and host-level `pointerdown` warns on disabled controls, must be verified in a real browser. The fix pattern for selects: sync the IDL `select.value` in `updated()` (see `daw-time-format.ts`).
- **Synthetic `dispatchEvent(new PointerEvent(...))` CAN drive handlers that only read `e.offsetX`/`e.currentTarget`** (e.g. `<daw-player>` click-to-seek) — set `offsetX` via `Object.defineProperty`. The root-CLAUDE "synthetic events can't drive pointer interactions" gotcha is specific to handlers using `setPointerCapture` (the editor's `PointerHandler`), which throws `NotFoundError` for fabricated pointerIds.
- **Adding an export to `@dawcore/wam` (or `@dawcore/faust`) breaks every existing `vi.mock` of it** — vitest strict mocks throw "No X export is defined on the mock" on property access. Sweep all `vi.mock('@dawcore/wam', ...)` factories in `src/__tests__/` and add the new export (a `vi.fn()` stub suffices) whenever the real package's index grows.
- **happy-dom re-invokes a patched instance `dispatchEvent` during propagation** — wrapping `host.dispatchEvent` and forwarding to the original counts 3 invocations per logical dispatch on an in-DOM element. Tests that count events must NOT forward (`vi.fn((e) => { events.push(e.type); return true; })`); forwarding wrappers are only safe with `events.find(...)`-style assertions.
- **A pre-stubbed `editor._engine` never registers engine-EVENT handlers** — `_ensureEngine` returns the stub without running `_buildEngine`, so `statechange`/`stop`/`pause` handler logic is untestable that way. Extract the handler body into a named method (e.g. `_reconcileDescriptorsWithEngineTracks`) and unit-test it directly.
- **Adding a method to `PeakPipeline` (or a member to a structural host interface like `RecordingClipHost`) breaks every hand-rolled stub** — sweep `grep -rn '_peakPipeline = {' src/__tests__/` and the `makeHost` helpers, adding the new member (a `vi.fn()` suffices). Same class as the `vi.mock('@dawcore/wam')` sweep above.
- **Hold an async load mid-flight with a deferred `mockImplementationOnce`** (`new Promise((r) => { release = r; })`) + `vi.waitFor(() => expect(mock).toHaveBeenCalled())`, then race the promise under test against a `setTimeout` sentinel to assert settle-vs-hang — the standard seam for removal/disconnect/stop races.
- **Module-level helpers must sit ABOVE the `@customElement` decorator** — a class inserted between the decorator and the element class makes the decorator target the helper (confusing `TS1238`, not a runtime error).
- **Real browsers fire `focus` BEFORE `click` on contenteditable targets; happy-dom's `.click()` fires neither** — any click guard keyed on focus-set state (e.g. `_editingId`) passes unit tests but swallows the first real click. Reproduce the native order in tests: `span.dispatchEvent(new FocusEvent('focus'))` then `row.click()`.
- **`vi.waitFor` defaults to a 10 s ceiling in this package** (`src/__tests__/setup/wait-timeout.ts`, wired through `vitest.config.ts` `setupFiles`; guarded by `wait-timeout-setup.test.ts`). vitest's own default is 1 s, which a loaded CI runner occasionally exceeded on multi-hop waits (MutationObserver → deferred element events → mocked decode), failing a different test each time. A polling wait returns as soon as its condition holds, so the ceiling costs nothing locally. Explicit `{ timeout }` options are kept. Fixed `setTimeout` waits are a different problem (next item).
- **`daw-editor-programmatic.test.ts` fixed-delay waits flake on slow CI** — `setTimeout(60-80ms)` load waits + single-macrotask post-removal asserts race async load/cleanup. Two tests hardened (await the `addTrack()` promise; wrap post-removal asserts in `vi.waitFor`); ~20 fixed waits remain in the file — apply the same recipe when one flakes, never bump the delay.
