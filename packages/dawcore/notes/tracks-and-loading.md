# Tracks, loading and peaks

Notes of dawcore Package (`@dawcore/components`), moved out of the package's `CLAUDE.md`. Read before changing `addTrack` / `removeTrack`, the file loader, track loading order, the peak worker or virtual scrolling.

## Programmatic Track + Clip API

- **The arrangement loads the tracks (#848)** — `_arrangement` (`createArrangement()`) exists from construction; the engine is built on it when the editor is connected with an adapter. A `<daw-track>` (page, `addTrack()`) registers its descriptor in `_onTrackConnected` and is queued (`_queueEntry`); `_flushTrackEntries` (a microtask, and again at the engine's build) enters the queue in DOM order through `_enterTrack`: `buildArrangementTrack` (`interactions/track-entry.ts`) makes a `LoadingClip` per audio clip (id = `<daw-clip>.clipId`, or a generated one written back into a drop descriptor), a loaded clip per MIDI clip at the adapter's rate, and lists a clip of the wrong kind as refused (`daw-clip-error`); `entryIndex` puts the track after the arrangement track of the nearest `<daw-track>` before it. Without an engine the queue waits, silently (maintainer, #917): MIDI clips need the adapter's sample rate. A drag holds no transaction (#848 PR 3), so a track enters during a drag as at any other time, an undo step of its own.
- **Who writes what** — the arrangement is the one owner of tracks, clips, mix, history and loading; the editor keeps no projection of it (#848 PR 3: `interactions/arrangement-view.ts` reads it). Every editor edit is an arrangement call, and a clip edit uses `updateTrack(id, (current) => …)`, so the track's loading clips stay (`_replaceClip`, `_removeClipFromTrack`, `_loadAndAppendClip`, `_replaceShorthandClips`, the recorded take). `_pending` holds a registered track's declaration until it enters (a `<daw-track>` element is read at entry, its `<daw-clip>` children as they are then; a dropped file carries its descriptor). `_extras` keeps only what the arrangement does not hold: kind, render mode, spectrogram config, the `src` shorthand, and every clip the editor took with its `peaks-src` (a clip's deferred `daw-clip-connected` finds it there and is not added twice).
- **The history rule for the page's tracks** — `_flushTrackEntries` enters the page's `<daw-track>` elements first and calls `clearHistory()` after them when the arrangement had no history (`!canUndo && !canRedo`); tracks `addTrack()` adds (element-less since #848 PR 3) and file drops enter after that and are undo steps. Page children connect in tasks of their own, so they enter one flush each; the rule holds for each because the flush before left the history empty.
- **Load events from the arrangement** — `LoadAnnouncer` (`interactions/load-announcer.ts`) runs over `getTracks()` and `sources` after each structural statechange and each `sources` change, and remembers what it announced: `daw-clip-error` once per failure object, `daw-clip-ready` for a clip it saw loading (`expectClip` before the add, so a clip whose source was loaded already is announced too), `daw-track-ready` / `daw-track-error` per transition of the track's state. A track that comes back by undo or redo is not announced again; `forget` on removal. The events are dispatched inside the arrangement call that causes them, so for a track with nothing to fetch they fire before `addTrack()` resolves (documented: listen before calling; maintainer, #917). `_whenTrackLoaded` (the file loader) reads `stateOf` / `errorOf` first, then waits for the events; a disconnect ends the wait as loaded (the track is kept, maintainer #917), and `disconnectedCallback` drops a dropped file that has not entered yet.
- **`addTrack()` resolves on entry** — `_waitForEntry` / `_settleEntry`: resolved in `_enterTrack`, rejected when the add throws, the track is removed while queued, or the engine cannot be built (`_buildEngineReporting` rejects every `addTrack()` still waiting, and its track goes). Since #848 PR 3 `addTrack(config)` makes no element: it puts a declaration (`clipDescriptorOf` per clip, a new id each) and the mix in `_pending`, and the track enters like any other. `addClip()` makes no element either: on an entered track the clip goes in at once (`_loadAndAppendClip`, a loading clip, one undo step; not recorded in `_extras.peaksSrc`, which lists the clips taken from `<daw-clip>` elements), on a queued one it joins the declaration (`extraClips` of an element entry). It listens for `daw-clip-ready` / `daw-clip-error` itself and watches the arrangement: once its clip has been in it and is gone (a removal, an Undo, its track removed) it rejects; every way out removes all three listeners. A clip added before a disconnect keeps waiting and settles once a fresh adapter loads it. `_awaitedClips` maps each waiting clip to its track and an internal reject: `_onTrackRemoved` rejects every one of that track's, and `removeClip` on a queued track rejects its own; no public event is sent for a removal the app made. `updateTrack` / `updateClip` change the arrangement (and `_extras`) and write no element; on a track still queued they change what it enters with. `removeTrack` / `removeClip` remove the element when there is one.
- **A failed track stays** — like a broken `<img>`: its loading clip stays in the arrangement, drawn `.placeholder.failed`; `retryTrack(trackId)` calls `arrangement.retry(src)` for each failed source of its loading clips. A dropped file that fails is the exception: `_discardTrack` removes it with `{ undoable: false }`.
- **`.dat` preview beside the clip** — `_requestPreview` fetches `peaks-src` after entry and, while the clip is still a `LoadingClip`, stores `_previewPeaks` (drawn) and `_previewWaveforms`; `_adoptLoadedClips` hands the `WaveformData` to `cacheWaveformData` when the audio arrives (no worker run), and `_clipPeaksReady` (called by the peak sync) drops the preview once the real peaks exist. Not on the `LoadingClip`'s `waveformData`: writing the clip after it entered would be an undo step.
- **`editor.tracks` returns `TrackWithId[]`** read from the arrangement (#848 PR 3: name, kind, mix and clips as it holds them, a clip's times in seconds, `kind: 'dom'` when a `<daw-clip>` is linked to it, else `'drop'` with its `clipId`; render mode, spectrogram config, `src` and `peaksSrc` from `_extras`), in the arrangement's order, then the queued tracks (their declaration as it is now); a `<daw-track>` whose track an Undo took out keeps its extras (for a Redo) but is not listed — the public enumeration of trackId + name for EVERY track incl. element-less (drag-dropped / undo-restored) ones.
- **Treat `editor.engine` as read-only from consumer code** — effects chains, clip caches and element alignment flow through the editor methods; reach into `engine` only for taps (`masterOutputNode`, analyzers).
- **`<daw-clip>` lifecycle events** — `daw-clip-connected` (deferred via `setTimeout(0)`) and `daw-clip-update` (fires only after first render, on any reflected property change). A clip connected to a track that has not entered is read when the track enters; one connected to an entered track goes in through `_loadAndAppendClip` as a loading clip, one undo step. The editor does not listen to `daw-clip-update` (#848 PR 3): a live property set calls `_requestClipChange`, which changes a loaded clip (`_applyClipUpdate`, from the live values with the request applied) or a clip still loading (`_updateLoadingClip`, its `LoadingClip` seconds), one undo step; a value the arrangement holds already changes nothing.
- **`<daw-track>`/`<daw-clip>` deferred events and entry** — both elements `setTimeout(0)` their connected dispatch so the editor's listener registers first. A track's declaration (its attributes and `<daw-clip>` children) is read when it ENTERS (`_pendingDescriptor` in `_enterTrack`, #848 PR 3), not at connect; the deferred `daw-clip-connected` of a clip read that way finds the clip in `_extras.peaksSrc` and is skipped silently. A move with `moveBefore()` runs `connectedMoveCallback` instead of disconnect and connect; it announces the element again (`_announceConnected`), so the editor sees a clip in another track or a track back in the editor.
- **Discriminator name should not collide with sibling field names** — `ClipDescriptor` originally used `source: 'dom' | 'drop'` next to `src: string`; reading `clipDesc.source === 'dom'` and `clipDesc.src` on adjacent lines was a real readability hazard. Use `kind` for discriminators in this codebase.
- **3+ narrowing sites = type predicate** — when a discriminated-union check (`c.kind === 'dom' && c.clipId === ...`) appears at multiple call sites, extract `isDomClip(c): c is DomClipDescriptor` co-located with the type definition. Five sites was the threshold that paid for the helper in PR #383.

## Web Worker Peak Generation

- **`peaksWorker.ts`** — Inline Blob worker (portable across bundlers). Generates WaveformData binary format from AudioBuffer channel data at a given scale. Uses `generateWaveformData` algorithm from BBC's waveform-data.js (MIT). Includes fix for upstream trailing-bin offset bug in 16-bit multi-channel.
- **`waveformDataUtils.ts`** — `extractPeaks()` converts WaveformData → PeakData. Handles all channels, mono merging (weighted average), slicing, and aligned resampling.
- **`peakPipeline.ts`** — Orchestrates worker lifecycle, WaveformData cache (WeakMap per AudioBuffer), inflight dedup, and peak extraction at any zoom level.
- **Peak resolution order:** (1) WaveformData cache hit → `extractPeaks()` (synchronous resample), (2) worker generation → cache → extract.
- **Zoom re-extraction:** `willUpdate()` detects `samplesPerPixel` changes and re-extracts peaks from cached WaveformData. Only works for scales coarser than the cached base — finer zoom requires regeneration via worker.
- **Aligned resampling** — When slicing WaveformData before resampling to a different scale, source slice indices must align to the resampling ratio. Uses `floor(targetStart * ratio)` / `ceil(targetEnd * ratio)` to include all contributing source bins. See browser CLAUDE.md "Aligned Peak Resampling" for full explanation.
- **CSP fallback** — Worker creation can fail in CSP-restricted environments blocking blob: URLs. The fallback rejects with actionable error message suggesting `worker-src blob:` directive.
- **Events that settle promises are dispatched also when detached** — the listeners of `addClip()` live on the editor element itself and still fire when it is detached (a disconnect ends `_whenTrackLoaded`'s waits as loaded); only ancestor bubbling is lost (pattern #36 applies to purely-outbound notifications like `daw-track-removed`).

## Virtual Scrolling

- **`ViewportController`** — Lit reactive controller. Attaches to `.scroll-area` (via `scrollSelector`) in `hostConnected` — auto-reattaches on disconnect/reconnect. Tracks scroll position with 1.5x overscan buffer and 100px threshold. Calls `requestUpdate()` on attach and scroll.
- **`getVisibleChunkIndices()`** — Shared pure function in `utils/viewport.ts`, re-exported from `viewport-controller.ts`. Used by `daw-waveform._getVisibleChunkIndices()`.
- **Permissive defaults** — Controller initializes `visibleStart=-Infinity, visibleEnd=Infinity` so all chunks render before scroll container is attached.
- **`daw-waveform` props** — `visibleStart`, `visibleEnd`, `originX` control which 1000px canvas chunks are rendered. Defaults to all-visible when not set.
- **File size budget** — `daw-editor.ts` hard max 800 lines. `loadFiles` extracted to `interactions/file-loader.ts`; `addRecordedClip` extracted to `interactions/recording-clip.ts`; `TrackDescriptor`/`ClipDescriptor` extracted to `src/types.ts`.

## File Loader Extraction

- **`interactions/file-loader.ts`** — `loadFiles()` through the `FileLoaderHost` interface: for each file, `_addDroppedFile` (an element-less track whose `DropClipDescriptor.file` is the `File`, entered through the queue), then `_whenTrackLoaded`, and `_discardTrack` when it failed (#848). Drops are sequential, so track order is drop order.
- **`src/types.ts`** — `TrackDescriptor` and `ClipDescriptor` interfaces, shared by `daw-editor.ts` and `file-loader.ts`. Re-exported from `index.ts`.
- **Non-private fields** — Fields the helpers in `interactions/` reach (`_arrangement`, `_peaksData`, `_clipBuffers`, `_clipOffsets`, `_peakPipeline`, `_raiseZoomFloor`, `_clipPeaksReady`, and the file loader's three methods) are non-private (no `private` keyword, `_` prefix convention only). Same pattern for `AnnotationDragHost` (`interactions/annotation-drag.ts`): `_renderSpp` and `_duration` are read directly by `AnnotationDragHandler._onPointerMove` (converting drag pixel deltas to seconds and clamping the boundary against timeline duration) — non-private for the same reason.
- **Per-clip Map cleanup** — Any `Map` keyed by clip ID (`_clipBuffers`, `_clipOffsets`, `_peaksData`) must be cleaned in `_onTrackRemoved`. When adding a new per-clip Map, add the corresponding `.delete(clip.id)` in the removal loop.

## Read `clip.audioBuffer` Directly

`cleanupOrphanedClipData` (in `syncPeaksForChangedClips`, called from the engine `statechange` handler) MUTATES `_clipBuffers` in-place on every `tracksVersion` bump, dropping every id that is not a loaded clip of the current tracks. `_clipBuffers` is a cache of the loaded clips' `audioBuffer`, refilled by the next peak sync; a helper that needs a clip's audio reads `clip.audioBuffer ?? this._clipBuffers.get(clip.id)` (`_maybeRegisterSpectrogramClipAudio` is the reference).
