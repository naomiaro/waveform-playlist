# Engine Package (`@waveform-playlist/engine`)

**Purpose:** Framework-agnostic timeline engine extracted from React hooks. Enables Svelte/Vue/vanilla bindings.

**Architecture:** Three layers — pure operations functions, the arrangement (`src/arrangement/`, public through `createArrangement()` and the `Arrangement` interface; the class `ArrangementImpl` is not exported), and the stateful `PlaylistEngine` class with event emitter. The arrangement owns the tracks, the mix, the undo history and transactions; the engine owns transport and view state, delegates every track, clip, mixer and history method to its arrangement, and follows it by subscription: for each change it is told about, its `AdapterSync` (`src/adapterSync.ts`) makes the adapter call and the engine emits `statechange` (#812). See "The arrangement owns the tracks" below.

**Build:** Uses tsup (not vite) — `pnpm typecheck && tsup`. Outputs ESM + CJS + DTS.

**Testing:** vitest unit tests in `src/__tests__/`. Run with `npx vitest run` from `packages/engine/`. An engine with an adapter attaches the adapter's audio context to its arrangement, so a test that gives such an engine a LOADING clip without a `loadSource` of its own runs `defaultLoadSource`: a real `fetch` of the clip's `src`, which fails in Node and marks the source failed some time after the test. Pass `createArrangement({ loadSource })` with a fake (`fakeLoads()` in `arrangementSources.test.ts` keeps every call pending until the test settles it; `await flush()` after each settle), or `attachDecodeContext: false`.

**Key types:** `Arrangement`, `CreateArrangementOptions`, `RemoveTrackOptions`, `RemoveClipOptions`, `MixerChangeOptions`, `ClipBounds`, `TrackMixerValues`, `ArrangementSourcesValue`, `ArrangementSourceState`, `LoadSource` (the arrangement's public face; its tracks are core's `ArrangementTrack`, whose clips are `AudioClip | LoadingClip`), `PlayoutAdapter` (pluggable audio backend interface — requires `readonly audioContext: AudioContext`, `readonly ppqn: number`; optional `addWorkletModule`/`createAudioWorkletNode`/`createMediaStreamSource` for cross-context worklet support, `masterOutputNode` for analyzer/recorder tap), `EngineState` (state snapshot; its `tracks` is `readonly ClipTrack[]`, not a copy, and holds loaded clips only), `EngineEvents` (statechange, play/pause/stop). The gesture ids come from core's `createMixerGesture()` (see "Mixer gestures").

**Operations:** `clipOperations.ts` (drag constraints, trim, split), `viewportOperations.ts` (bounds, chunks, scroll threshold), `timelineOperations.ts` (duration, zoom, seek).

**No React, no Tone.js** — zero framework dependencies. Only peer dependency is `@waveform-playlist/core`.

## Tempo Management

- **`setTempo(bpm, atTick?)` commits on adapter acceptance** — Forwards to `adapter?.setTempo?.()` FIRST; an explicit `false` return (e.g. the transport's multi-entry tempo-map guard, #407) means refused — `_bpm` keeps its prior value, no recompute, no statechange. `void`-returning and absent adapters count as accepted: then `_bpm` updates and the arrangement recomputes ("Recompute after a tempo change" below), which emits the statechange. `PlayoutAdapter.setTempo` is typed `boolean | void`.
- **`getCurrentTime()` always reads from adapter** — No `_isPlaying` gate. When adapter exists, adapter is the time authority. `_currentTime` is only a fallback for headless/no-adapter mode.
- **`_ticksToSeconds` / `_secondsToTicks`** — Delegates to `adapter.ticksToSeconds()` / `adapter.secondsToTicks()` when available (multi-tempo via Transport's TempoMap). Falls back to simple single-tempo math.
- **Recompute after a tempo change** — an accepted `setTempo` calls `ArrangementImpl.recomputeStartSamples()`, which immutably maps all tracks/clips, recomputes `startSample` from `startTick` for clips that have `startTick` defined (a clip whose start is already right keeps its object), increments `tracksVersion` and announces `'recompute'`; the engine's listener then sends every track to the adapter one by one (`AdapterSync.sendTrack`) and emits `statechange`. A tempo change therefore places every clip that has a tick on the CURRENT engine's tick grid, with or without an engine swap. A disposed engine's `setTempo` returns before the adapter call. It does nothing while no engine is attached.
- **`setTracks()` enriches clips** — Clips without `startTick` get it computed from `startSample / sampleRate` (`ArrangementImpl._ingest` → `_tickAt`, through the time base the engine gives the arrangement in `attachEngine`: closures over `_secondsToTicks()` / `_ticksToSeconds()`, evaluated at call time). Uses immutable mapping pattern. `addTrack` and `updateTrack(id, track)` do the same (a clip object the track already holds is kept as it is, and a `LoadingClip` is copied and never given a tick: it has no samples to count one from). With no engine attached there is no tempo to convert with, so a clip gets no tick (see "Without an engine" below); `attachEngine` gives one, from its `startSample`, to every clip that has none, in every state the arrangement holds (see "Attach prepares every state").
- **Constructor accepts `bpm` and `ppqn`** — Via `PlaylistEngineOptions`. Defaults: 120 BPM, 960 PPQN. Exposed in `EngineState`.

## Zoom Level Validation

`samplesPerPixel` must exist in the `zoomLevels` array — engine constructor throws if not (`indexOf` check, not `findClosestZoomIndex`). Default zoom levels: `[256, 512, 1024, 2048, 4096, 8192]`. Default `samplesPerPixel`: 1024. When adding examples, always use a value from the zoom levels array.

## Patterns

- **`setTracks`, `addTrack` and `updateTrack(id, track)` throw on a track whose clips do not match its `kind` (#756), on a duplicate track id and on two clips with one id in a track (#812)** — `assertClipsOfTrackKind` (core's `assertTrackKind`), then `assertUniqueTrackIds` / `assertUniqueClipIds` / `duplicateTrackId` (all in `arrangement/validate.ts`), all in the arrangement's method and all called FIRST: before the open transaction is ended, before the history is cleared, before the undo step, and so before any listener or adapter is told. A throw therefore leaves tracks, history, mixer and adapter exactly as they were (`trackKind.test.ts`, `arrangementRules.test.ts` "ids are unique"). Keep the assertions ahead of any mutation when changing these methods. The messages start with `[waveform-playlist]`. Two clips of one id on DIFFERENT tracks are accepted. A loading clip counts as an audio clip whatever it carries (`assertClipsOfTrackKind` hands `assertTrackKind` only its `id` and `name`, so one that plain JavaScript gave `midiNotes` is still read as audio: that is what it will become), so a `kind: 'midi'` track that holds one is refused with the same message as one that holds a loaded audio clip, and a loading clip and a loaded clip of one id on a track are a duplicate (`arrangementLoading.test.ts`, "a loading clip and the kind of its track"). `updateTrack` may give a track a new id that no other track has; a track given as the first tracks of `createArrangement({ tracks })` is checked the same way. Undo/redo restore tracks that were already accepted and do not re-check.

- **`play()` and `seek()` do not clamp to duration** — The Transport runs at any non-negative position, playing silence where there's no audio. This enables recording from cursor positions beyond existing clips. Only negative values are clamped to 0.
- **Default sampleRate is 48000** — Changed from 44100 to match modern hardware. Consumers should still pass `AudioContext.sampleRate` explicitly when creating the engine.
- All mutating methods (moveClip, trimClip, removeTrack, setZoomLevel) guard against no-op statechange emissions — bail early when constrained delta is 0, track not found, or zoom unchanged
- Tracks are copied on their way in (`_ingest`: the track and each clip); nothing handed to a caller is copied on the way out. `getState().tracks` and `arrangement.getTracks()` are the engine's own objects, typed `readonly ClipTrack[]` (`readonly ArrangementTrack[]` for `getTracks()`) and frozen outside production builds; an adapter receives those tracks without their view fields (`PlayoutTrack`, copies sharing the clips, also frozen) — see "The arrangement owns the tracks"
- `PlayoutAdapter.isPlaying()` is defined but not called by engine (engine tracks own `_isPlaying`) — bounded completion is now observed via `onPlaybackEnded` (#608); `isPlaying()` polling remains unused by design.
- **`onPlaybackEnded` hook (#608)** — optional `PlayoutAdapter.onPlaybackEnded(callback | null)`, for adapters that self-terminate a duration-limited `play(start, end)` (annotation/selection playback). Constructor subscribes once: `this._adapter?.onPlaybackEnded?.(() => queueMicrotask(() => { if (this._isPlaying && !this._disposed) this.stop(); }))`. The `queueMicrotask` defer matters because the Tone adapter fires this from inside the Transport tick chain, which catches nothing (see playout CLAUDE.md) — stopping the Transport re-entrantly from a tick callback is the hazard the microtask sidesteps. Re-checking `_isPlaying` AND `_disposed` inside the microtask covers a consumer `stop()`/`dispose()` landing in the gap between the adapter's callback firing and the microtask running.
- **`dispose({ keepAdapter: true })` (#848)** — for a host that plays another arrangement on the same adapter next (`<daw-editor>`'s `editor.arrangement` swap): `stop()` first when playing, then the same steps with `adapter.setTracks([])` instead of `adapter.dispose()` (an empty next arrangement sends no `setTracks`, so without it the old tracks went on playing; review of #919). The next engine's constructor subscribes `onPlaybackEnded` again and sends its arrangement's tracks (`setTracks`), so the adapter serves it like a fresh one.
- **A split keeps the left id (#848)** — `operations/clipOperations.ts` `splitClip` gives the left half `clip.id`, the right half a new id: an element or a selection that names the clip follows its left half, and an undo brings the clip back under its id. No attach-key change: a split's ids are behaviour of the copy that owns the arrangement, not part of the shape two copies must agree on.
- **Single callback slot, last-subscriber-wins** — `onPlaybackEnded` takes exactly one callback, not a listener set — matches the repo-wide one-engine-per-adapter convention (no fan-out, no unsubscribe-by-reference needed).
- **Dispose unsubscribes before tearing down the adapter** — `dispose()` sets `_disposed = true`, stops following the arrangement and detaches from it (`_stopFollowingArrangement()`, `_detachFromArrangement()`, then `_detachDecodeContext?.()`, which aborts the arrangement's loads in flight), sets `_isPlaying = false`, then calls `this._adapter?.onPlaybackEnded?.(null)` BEFORE `this._adapter?.dispose()` (itself wrapped in try/catch). This guarantees a disposed engine can't be re-entered by a late adapter callback; the microtask's own `_disposed` check is the second layer of defense for a callback that was already in flight when dispose ran.
- Engine uses `seek()` while browser package uses `seekTo()` — naming divergence, noted in root CLAUDE.md "Common Doc Drift"
- **Guard Against No-Op State Emissions** - In stateful classes with event emitters, check if an operation would actually change state before emitting. Zero-delta moves/trims, removing non-existent items, and setting zoom to the same level should bail early to avoid wasted listener calls and UI re-renders.
- **Engine owns selection, loop, selectedTrackId, zoom, and masterVolume (the arrangement owns tracks, mix and history)** — That is for a host that uses the engine by itself and for dawcore. `WaveformPlaylistProvider` owns these five itself since #826: it gives each engine its values and reads none back (`packages/browser/CLAUDE.md`, "The Provider Plays an Arrangement"). Consumers poll `engine.getCurrentTime()` per-frame in their own animation loops.
- `setSelection()` and `setLoopRegion()` normalize `start <= end` via `Math.min/Math.max` — consumers can trust `EngineState` invariants without defensive normalization
- **`getAudibleTime()` for visual consumers** — Latency-compensated position (raw − `outputLatency` − `lookAhead`, held at `_playStartPosition` during the pre-roll window) while playing; raw `_currentTime` when resting. Compensation is a property of *playing*, not of position — a seeked/paused/stopped cursor displays exactly. Storage stays raw (`getCurrentTime()`); never feed `getAudibleTime()` back into `play()`/`seek()`.
- **Loop activation uses `< loopEnd` check** — `play()` activates Transport loop when starting before `loopEnd` (not `>= loopStart && < loopEnd` like before). Starting before the loop region still activates looping — Transport plays through to `loopEnd`, then wraps to `loopStart`. Starting at or past `loopEnd` plays to the end without looping (click-past-loop behavior). `setLoopEnabled()`/`setLoopRegion()` during playback use `_isBeforeLoopEnd()` — same `< loopEnd` check against live adapter position. Selection/annotation playback (with `endTime`) always disables loop.
- **`play()` state rollback on adapter throw** — `play()` saves `prevCurrentTime` and `prevPlayStartPosition` before mutations. If `adapter.play()` throws, state is restored so the engine isn't left with a moved playhead but no audio.
- `engine.dispose()` wraps `adapter.dispose()` in try-catch to guarantee `_listeners.clear()` always runs. Explicit `engine.off()` is unnecessary when the engine itself is being disposed.

## The arrangement owns the tracks

One owner per piece of state (#812):

| State | Owner |
| --- | --- |
| tracks and clips, `tracksVersion` | the arrangement |
| the mix (volume, mute, solo, pan by track id), `mixerVersion` | the arrangement |
| undo/redo history (each state the tracks AND the mix), the open transaction | the arrangement |
| which tracks a take is recording onto (`recordingTrackIds`) | the arrangement, outside the history (see "The take's mute") |
| which sources are wanted, each source's status and its decoded `AudioBuffer` | the arrangement (`ArrangementSources`, over one `createSourceLoader` of core); `arrangement.sources` is derived from it and never written back |
| the audio context sources are decoded with | whoever attached it (`attachDecodeContext`): an engine with an adapter, or the host. The arrangement holds the getter while it is attached |
| transport (`_currentTime`, `_isPlaying`, `_playStartPosition`), selection, loop, zoom, selected track id, master volume, tempo (`_bpm`, `_ppqn`) | the engine |
| the audio graph | the adapter, a one-way cache the engine keeps in step by subscription |

**Files (`src/arrangement/`):**

- `types.ts` — the public `Arrangement` interface (tracks typed `ArrangementTrack`; `sources`, `retry`), `ClipBounds`, `RemoveTrackOptions`, `CreateArrangementOptions` (`tracks`, `undoLimit`, `loadSource`)
- `index.ts` — `createArrangement(options)`, the re-exports of `attachDecodeContext` and `defaultLoadSource`, and the public type re-exports; the only arrangement module `src/index.ts` exports from
- `Arrangement.ts` — `ArrangementImpl` (internal) with the internal types `ArrangementChange`, `ArrangementOptions`, `ArrangementVersions` (`ArrangementTimeBase` is re-exported from `attach.ts`)
- `sources.ts` — class `ArrangementSources` (internal): the one `createSourceLoader`, `declare(states)` (what is wanted), `beginPass(tickAt)` / `finishPass()` (the switch of loading clips to loaded ones over many states, and the published value), `attachDecodeContext(getContext)`, `retry(src)`; the public types `ArrangementSourcesValue`, `ArrangementSourceState`
- `attach.ts` — the two attach points, reached through `Symbol.for` keys (`ARRANGEMENT_ATTACH_DECODE`, `ARRANGEMENT_ATTACH_TIME_BASE`): the public `attachDecodeContext(arrangement, getContext)`, and the internal `attachTimeBase`, `isArrangement`, `ArrangementTimeBase`, `GetDecodeContext`
- `loadSource.ts` — type `LoadSource` and `defaultLoadSource` (fetch or `arrayBuffer()`, then `decodeAudioData`), with `sourceLabel` (what an error message calls a source)
- `resolveLoadingClip.ts` — `resolveLoadingClip(loading, buffer)`: `{ clip }` or `{ unusable: reason }`; never throws
- `mixer.ts` — `TrackMixerValues`, `Mixer` and the pure functions over the mixer Map (`seedMixer`, `setMixerValues`, `carryMixerEntry`, `mixerOf`, `withoutEntry`, `sameMixerValues`, `mixerChanges`, `withMixerValues`, `mixerValuesOf`, `decidePanLaws`)
- `history.ts` — undo/redo as pure functions over references: a `SavedState` is `{ tracks, mixer }` (`pushStep`, `undoStep`, `redoStep`, `beginBase`, `withStateTracks`, `mapHistoryTracks`, `sameTracks`, `sameState`, `withoutTrack`, `stateWithoutTrack`, `dropRepeats`, `purgeTrack`, `writeThrough`)
- `clipEdits.ts` — the clip edits as pure functions over a tracks array (`moveClip`, `trimClip`, `splitClip`, `clipBounds`, `constrainTrim`; `ClipEditTime` is how they convert time). They see loaded clips only: `findClip` warns for a loading clip, and `loadedClips(track)` is what a move or a trim collides with
- `ticks.ts` — `withClips`, `clipMapper` (one clip function over many states, keeping shared track objects shared), `forLoadedClips` (wraps a function of an `AudioClip` so that a loading clip is returned as it is), `tickPreparer(timeBase, fromPpqn)` (what an attaching engine does to every state: a `clipMapper` over `forLoadedClips`), `rescaleTick` (a tick from one ppqn to another)
- `validate.ts` — the checks a track passes before it enters: `assertClipsOfTrackKind` (core's `assertTrackKind` on a copy of the track in which each loading clip is reduced to `{ id, name }`, so it reads as an audio clip whatever else it carries), `assertUniqueClipIds`, `assertUniqueTrackIds`, `duplicateTrackId`
- `devFreeze.ts` — `freezeTracksInDevelopment`, `freezeTrackInDevelopment`, `isDevelopmentBuild`

Beside the folder: `src/adapterSync.ts` — class `AdapterSync`, what keeps the adapter in step: `tracks()` (the projection), `sendInitialTracks()`, `sendAllTracks()`, `sendTrack(id)`, `sendMixerValues()` (the mute it sends is the one the track plays with, so the recording track's is `true`), `sendMixerDiff(previousMixer)` (after an undo, a redo or an abort: the setter for each field that differs), `follow(change, at)`, `markSkip()` / `unmarkIfUnchanged()`. The engine keeps `_adapterSync`, `_onArrangementChange`, `_clearSelectionIfGone` and `_mixerChanged`.

**Rules:**

- **With or without the `arrangement` option** — `new PlaylistEngine({ arrangement })` plays an arrangement from `createArrangement()` (anything else throws: `asArrangementImpl` checks `isArrangement()`, which is true for an object that has a function under the `Symbol.for` key of the time-base attach point, not `instanceof`; see "Attaching goes through shared keys"); without the option the engine makes its own with `undoLimit`. With the option, `undoLimit` on the engine is ignored with a `console.warn`; `engine.undoLimit` reads the arrangement's.
- **Constructor order** — `attachTimeBase(arrangement, timeBase)` first (the arrangement's `attachEngine`, reached through its key), then `new AdapterSync(arrangement, adapter)`, then `onChange` (so the engine is not told about the attach's `'recompute'`; arrangement subscribers are, before the new engine's first adapter call), then `sendInitialTracks()`: one `adapter.setTracks` when the arrangement already has tracks, none when it is empty. If that call throws, the constructor stops following and detaches (`_stopFollowingArrangement()`, `_detachFromArrangement()`) before rethrowing, because nobody holds the engine to dispose it. Last, and only when there is an adapter and `options.attachDecodeContext !== false`: `attachDecodeContext(arrangement, async () => adapter.audioContext)`, whose detach function is kept in `_detachDecodeContext`; a constructor that threw before has attached no context (`arrangementAttach.test.ts`, "an engine whose constructor fails leaves no context attached"). No `statechange` is emitted by the constructor.
- **An arrangement outlives its engine** — `dispose()` unsubscribes and detaches; the arrangement keeps tracks, mix and history, can still be changed through the disposed engine or directly (no adapter call, no `statechange`, no throw: the track methods no longer reach the adapter, the mixer setters and `updateTrack(id)` check `_disposed`, `setTrackRecording` changes the arrangement only, and `setTempo` returns before the adapter call), and the next engine built on it finds all three. One engine at a time: `attachEngine` warns when a time base is still attached, and the new one replaces it.
- **Attach prepares every state, atomically** — a clip's `startTick` is counted in an engine's ppqn, and the arrangement remembers the unit its ticks are in (`_tickPpqn`: null until an engine has attached, so a tick a clip came with before that is read in the first engine's ppqn). `ArrangementTimeBase` has a `ppqn` field; the engine passes its own. `attachEngine` builds one `tickPreparer` (`ticks.ts`: a `clipMapper` over `forLoadedClips`, so a loading clip is left as it is) and runs it over the current tracks, every undo and redo state and an open transaction's base: a clip without a `startTick` gets one from its `startSample` (also when the ppqn is the same), and a tick in another ppqn is converted with `rescaleTick` (`Math.round(tick * to / from)`); `startSample` is untouched. The mapper remembers each track it has mapped, so states go on sharing the track objects they shared, and returns the same array when nothing in it changed. Everything is worked out BEFORE anything is assigned: if the engine's tempo map throws meanwhile, nothing has changed and the arrangement is not attached. One `'recompute'` and `tracksVersion + 1` when the CURRENT tracks changed (a change in stored states only announces nothing); not an undo step. Going to a coarser ppqn rounds (7 at 960 → 1 at 192 → 5 back at 960), so the next tempo change can place such a clip up to half a tick of the coarser engine away from where it was: 0.5 × 60 × sampleRate / (ppqn × bpm) samples, about 62 samples (1.3 ms) at 192 ppqn, 120 bpm, 48 kHz (figures from a reviewer's probe, not from a test in the repository). A different TEMPO is not converted: the tick is the musical position, and `startSample` disagrees with it until the next `setTempo` recomputes; clips added under the new engine get their ticks at its tempo and keep their place at that `setTempo`, while the older ones move. Two live engines with different ppqn on one arrangement (the case that warns) is unsupported: the second time base replaces the first, so the first engine's later tick conversions use the second engine's. `arrangementEdges.test.ts`, "an engine with another tick resolution (ppqn) takes over".
- **Immutable** — a change replaces the tracks array and only the track and clip objects that changed; nothing is written into an object `getTracks()` has returned. An undo step is a reference to an earlier array (`history.ts` copies no track), and two states share every track that is the same in both. `updateTrack(id, next)` in BOTH forms (a track object or a function of the current track) keeps a clip object THIS track already holds (the `held` set of `_ingest`, built from `current.clips`), so states go on sharing it and `AdapterSync` can see that it did not change; a clip object of the caller's own is copied, and so is one held by ANOTHER track (`arrangementLoading.test.ts`, "a track OBJECT built from the arrangement's own track is recognised too", "a clip object held by ANOTHER track is copied when it is put on this one"; `arrangementImmutable.test.ts`). `addTrack` copies the track and every clip. The exception to "only what changed" is `setTracks`: it copies every track and clip it is given, so no track object survives it.
- **Nothing handed out is a copy** — `getState().tracks`, `arrangement.getTracks()` and `arrangement.getMixer()`; the exception is what an adapter receives, the projection without its view fields (see "The projection"), a copy of each track that shares its clips. Types: `readonly ArrangementTrack[]` for `getTracks()`, `readonly ClipTrack[]` for the other two, `ReadonlyMap`. `getTracks()` is the same array until the tracks change; `getMixer()` is the same Map until a value changes, an entry is added (a track with a new id enters, or a track is given a new id), entries are dropped, or an undo, a redo or an abort brings back the Map of another state (`mixerVersion` counts a value change, and a restore that changes a value); `getState().tracks` the same array until tracks or mix change.
- **Dev freeze** — `ArrangementImpl._emit` freezes the current tracks before anyone is told (`freezeTracksInDevelopment`: the array, each track, its `clips` array, each clip; not what a clip refers to), and the engine freezes its projection the same way, also before the adapter receives it. `isDevelopmentBuild()` is `process.env.NODE_ENV !== 'production'`, and false where there is no `process` at all (a page that loads the module without a bundler). The caller's own objects are never frozen (they were copied on the way in). `arrangementFrozen.test.ts`.
- **The mix is a part of its own** — a Map by track id. A track's own `volume` / `muted` / `soloed` / `pan` fields are the values it ENTERED with: `seedMixer` makes an entry from them (`mixerValuesOf`, defaults 1 / false / false / 0 for a missing field) only for an id that has no entry. `addTrack`: seeded from the new track's fields, also for the id of a track removed earlier (the current Map has no entry for it; the saved state from before the removal keeps its own). `setTracks`: only an id that is in the tracks being REPLACED (the current tracks) keeps its mix; every other id is seeded from the new track's fields, and the entry of an id that is not in the new tracks is dropped (`mixerOf`). `updateTrack`: the entry stays; a track given a new id takes its mix with it (`carryMixerEntry` MOVES the entry: the old id's goes from the current Map, the saved state from before keeps it); the new track's fields are not read unless the old id had no entry. Seeding, carrying and dropping do not increment `mixerVersion`. A setter acts only on a track that is in the CURRENT tracks (`_setMixerValues` returns for any other id) and only on a value that changes (`setMixerValues` returns the same Map when the entry already has it; then nothing happens: no step, no `mixerVersion`, no announcement, no `statechange`). Otherwise it replaces the Map and one entry and no track object, is an undo step (see "Undo/Redo"), increments `mixerVersion` and announces `'mixer'` (only `'mixer'`, also when it pushed or dropped a step: the engine's `statechange` carries `canUndo` / `canRedo`).
- **The current Map holds the current tracks; each saved state holds its own** (#843) — every undo and redo step and an open transaction's base is a `SavedState { tracks, mixer }`: two references, no copy, and states that did not change the mix share one Map. So there is no retention: `removeTrack` drops the track's entry from the current Map (the step from before the removal has it), and an entry no state holds is simply gone with the last state that held it. A saved Map is never written to, except by a copy: `undoable: false` (`writeThrough`) and the purge (`stateWithoutTrack`) make new states, memoized per Map, so states that shared a Map go on sharing one.
- **Undo, redo and abort bring back the mix of the state they return to** (#843) — undoing a removal brings the track back with the mix it had, undoing a rename brings back the old id with the mix it had then, and an undoable mixer change made inside a transaction is taken back by its abort (an `undoable: false` one is written into the base, so the abort keeps it). `_restoreState(state)` sets both; it announces `'restore'` (with `previous` and `previousMixer`) when the tracks array is another one, `'restoreMix'` (with `previousMixer`) when only mixer values differ, and nothing when neither did (an undo or redo then announces `'history'`, since the history moved). `mixerVersion` counts it when a track that is in both states has other values (`mixerChanges`); an entry that comes or goes with its track is not a mixer change. `tracksVersion` counts only a `'restore'`. Undo and redo never change which tracks are recording.
- **The take's mute** (#843) — `setTrackRecording(trackId, recording)` (arrangement and engine) and `recordingTrackIds` (a `ReadonlySet`, the same object until it changes, replaced and never written to): the track a take is recording onto plays muted for the length of the take. It is not a record-arm (a record-arm the user sets and clears is a later feature, with a name of its own). The projection has `muted: stored || recording` (`AdapterSync._withMix`, through `_recordingNow`) and `sendMixerValues` sends the mute that way, also for `sendMixerDiff`; `getMixer()` keeps the stored mute, which a setter may still change during the take (it plays muted until the take ends, then with the stored value). The set is outside the history and outside every saved state: the take's mute is not an undo step and does not split a gesture, and undo, redo, an abort, `setTracks`, `clearHistory`, `removeTrack` and the purge leave it alone. An id that is not a current track is recorded too and mutes nothing until a track of that id enters (also by an undo that brings it back); a renamed track does NOT take the mute with it (the recording code clears the id it set). The same value does nothing. A real change announces `'recording'` (one `statechange`), and increments `mixerVersion` only when the id is a current track (the projection is cached on the two versions); `tracksVersion` never. The engine's `'recording'` case sends the stored mute through `sendMixerValues`, which applies the take's mute; for an id with no entry nothing is sent. So `PlaylistEngine.setTrackRecording` makes no adapter call of its own, and a disposed engine's changes the arrangement only. `PlaylistEngine.recordingTrackIds` is a read-only getter returning the arrangement's set (no copy), so a UI can disable a mute control while a take records onto its track (`<daw-track-controls>` does). `arrangementRecordingMute.test.ts`.
- **The projection** — `AdapterSync.tracks()` is the arrangement's tracks, each WITHOUT its loading clips (`_loaded`, memoized per track object in `_loadedMemo`; a track that holds none is the arrangement's own object) and with the current mixer values in their fields (`_withMix` → `withMixerValues`, memoized per track object in `_withMixMemo`; the array cached in `_projection` by both versions). `_project(track)` is the two together. It is what `getState().tracks` returns. Every adapter track call (`setTracks`, `addTrack`, `updateTrack`) sends it WITHOUT the view fields (core's `TRACK_VIEW_FIELDS`: `name`, `color`, `height`, `renderMode`, `spectrogramConfig`, `spectrogramColorMap`; `_playout`, a frozen copy per send, with no memo since nothing depends on its identity: the two memos of the first version were removed after a review showed every test passed without them), typed core's `PlayoutTrack`, and `_playsTheSame` ignores those fields, so a change of them alone makes no adapter call (it is still an undo step and a `statechange`). Exceptions, each a full send for another reason: after an adapter call threw (`_needsAllTracks`) the next change of ANY kind, a view-only one included, sends every track; a `'set'`; a late delivery; a `'recompute'` (tempo) sends every track without `_playsTheSame`. On the native transport an `updateTrack` stops the track's playing sources: a render-mode choice during playback silenced the track until its next clip (the review of #930 ran it on `ClipPlayer`); a rename in `<daw-editor>` took the same path. No adapter reads a view field (checked with `git grep -w` and XERJ: Tone's adapter read `name` only for its `Track` object and two warnings, which now use the id). `viewFields.test.ts`. So an adapter never receives a loading clip and a track that holds only loading clips is played as an empty track; `getState().duration` is `calculateDuration` over the projection, so loaded clips only. Derived, never written back. A track with no loading clip whose fields already hold the mixer values is the arrangement's own object. `arrangementLoading.test.ts`, "what an engine plays and reports leaves loading clips out".
- **Internal `onChange(change, at)` vs public `subscribe(listener)`** — `onChange` is for the engine: it is told WHAT changed (`ArrangementChange`: `set`, `add`, `remove`, `update` with `previous` (the track object that was replaced), `reorder`, `restore` with the previous tracks, `restoreMix` with the previous mix (an undo, a redo or an abort that changed only the mix), `load` with the previous tracks (audio arrived and loading clips of the CURRENT tracks became loaded clips), `mixer`, `recording` (a take started or ended recording onto a track), `recompute`, `history`) and the versions right after that change (`at`: `ArrangementVersions`, which for an `add` or an `update` also carries `switched`, the tracks from before a switch that happened inside the change; see "The switch"), before the subscribers; a listener here that throws does not stop the delivery, and the first error is thrown, once the queue is empty, to the caller of the arrangement method that is delivering (so an adapter that throws fails that call, and that change emits no `statechange`; for a change made from inside a listener the failing call is the OUTER one, not the one that made the change). The exception is `'load'`, which has no caller: `PlaylistEngine._followLoad` catches the adapter's error, reports it with `console.error('[waveform-playlist] The playout adapter failed while loaded audio was applied:', error)`, the `statechange` is still emitted (the tracks did change), and `_needsAllTracks` stays set, so the next track change sends every track (`arrangementSources.test.ts`, "an adapter that throws when loaded audio is applied"). `subscribe` is public: once per change, with one argument `{ type }` (`ArrangementChangeInfo`: the change's type and none of the engine's payload; a new object per change, shared by that change's subscribers; added for #826 so that the React provider's selected track id can keep the engine's rule "not for `set`"; a listener that takes no argument works as before, and the attach keys stay at `/v3` because the engine does not call `subscribe`), after the `onChange` listeners, so after the engine has made its adapter call for that change (not "the adapter is in step" in two cases: a change made with `skipAdapter`, and the tick assignment of `attachEngine`, which subscribers hear before the new engine's first `adapter.setTracks`); a subscriber that throws is reported with `console.warn('[waveform-playlist] Error in an arrangement subscriber:', …)` and fails nothing. Each `subscribe` call is its own entry, so one function subscribed twice is told twice.
- **Delivery is ordered** — `_emit` queues the change in `_pending`; a change made from inside a listener (an `onChange` listener, a subscriber, or a `statechange` listener, which runs inside the engine's `onChange` listener) waits until the one being delivered has reached every listener. Every arrangement change is exactly one `statechange`. `AdapterSync.follow(change, at)` decides the adapter call from the versions: ONE track edit made from inside a listener is still the current state when it is delivered (`at.tracksVersion === arrangement.tracksVersion`) and is sent as itself. A change delivered after the tracks have changed AGAIN (two or more track edits in one listener run) cannot be told from the current tracks alone: the adapter is sent every track once (`sendAllTracks()`, a full `adapter.setTracks` that can interrupt playback), which records the version it covers in `_syncedTracksVersion`, and the changes still waiting (`at.tracksVersion <= _syncedTracksVersion`) make no adapter call. Their `statechange` is still emitted. After an adapter call for a track change throws, `_needsAllTracks` stays set and the next track change sends every track. `mixer` changes are always forwarded (`sendMixerValues`). Do not go back to a guard per kind of change for the late case: the first one ("already sent") was wrong for a sequence with an undo in it (#847, second review round).
- **`skipAdapter` is marked by the change's `tracksVersion`** — the engine's `moveClip`/`trimClip` with `skipAdapter` call `AdapterSync.markSkip()`, which adds `tracksVersion + 1` to `_skipAt` before the arrangement is called; `follow` deletes `at.tracksVersion` from the set for an `'update'` and makes no adapter call when it was there. The mark travels with the version, not with the call, because a change made from inside a listener is delivered after the call returned. A call that changed nothing removes its mark (`unmarkIfUnchanged`, in a `finally`, so also when the arrangement call throws).
- **Adapter call per change** (`PlaylistEngine._onArrangementChange` → `AdapterSync.follow` → `_sendChange`, for a change that is still the current state; see "Delivery is ordered" for the others) — `set`: `setTracks`. `add`: `adapter.addTrack` when defined, else `setTracks` (`_addTrack`). `remove`: `adapter.removeTrack` when defined, else `setTracks`. `update`: nothing when the track plays the same as `change.previous` (`_playsTheSame`, see "A change to loading clips only"), else `sendTrack` (`adapter.updateTrack` when defined, else `setTracks`); a track that was given a new id is not found under the old one and goes as `setTracks`. `restore` and `load`: `_restore(change.previous)`, and after a `restore` also `sendMixerDiff(change.previousMixer)`, because a track call does not carry the mix to every adapter (Tone's `updateTrack` replaces clips only) (after a load: `sendTrack` for each track that gained a loaded clip; `setTracks` per such track for an adapter without `updateTrack`). After the call for an `add` or an `update` whose `at.switched` is set, `follow` also runs `_restore(at.switched)`, which sends each track that gained a loaded clip inside that change, unless every track was just sent (`_syncedTracksVersion` has reached `at.tracksVersion`: an adapter without `addTrack` / `updateTrack`, or a track given a new id). `recompute`: every track through `sendTrack`. `mixer`: `sendMixerValues`, the one adapter setter. `restoreMix`: `sendMixerDiff`, no track call. `recording`: `sendMixerValues(id, { muted: stored })`, which sends the mute the track plays with; nothing for an id with no entry. `reorder` and `history`: no adapter call. Every `setTracks` goes through `sendAllTracks()`.
- **The selected track id is cleared when its track is gone, except by `setTracks`** — `_clearSelectionIfGone()` runs in `_onArrangementChange` for `remove`, `restore` and `update` changes, before the `statechange` of that change: a `removeTrack`, an undo of an `addTrack`, a redo of a `removeTrack`, an abort, an `updateTrack` that gives the track a new id (it is gone under the old one). NOT for `set`: a host may empty the tracks and add them again, and the selection must survive that, as it did before #812. Tests: "the selected track" in `arrangementRules.test.ts`, "a track that is given a new id" in `arrangementEdges.test.ts`.
- **Arrangement-only API** — `removeClip(trackId, clipId, { undoable: false })` (#848) is the same for one clip: `purgeClip` / `stateWithoutClip` in `history.ts`, through the same `purgeStates` as `purgeTrack`. A stripped track that equals (same fields, same clip objects) a track another state holds becomes that object, so `dropRepeats` (identity, `sameTrackFields`) drops the step that only added the clip; without that, a redo that changes nothing was left. It announces `update` when the current tracks change (the clip was there, or the walk gave the current track the object of an equal earlier one), `history` when only stored states changed. Without the option it is `updateTrack` with the clip filtered out. `<daw-editor>` calls it for a removed `<daw-clip>` whose clip the arrangement does not hold now.
- **`removeTrack` takes `{ undoable: false }` (maintainer, 2026-11-14: `removeTrack` only; the mixer setters' `undoable: false` of #843 is another option, on the engine's setters too, see "Undo/Redo"). It is not "skip the undo step": a step is a whole earlier tracks array, so a later undo would bring the track back. `_removeTrackEverywhere` takes the track out of the current tracks, every undo and redo state and an open transaction's base (`purgeTrack` / `withoutTrack` in `history.ts`), drops the track's mixer entry from every state too, then the steps that no longer differ from the state next to them (`dropRepeats`, by `sameState`); it announces `remove`, or `history` when only stored states changed. `addTrack` and `updateTrack` have no such option, because applying an add or an update to every earlier state has no clear meaning; `updateTrack` takes a function of the current track (not called for an unknown id; returning the track it was given changes nothing). The engine's methods of the same names do not take these.
- **Loading clips** — an arrangement's tracks are core's `ArrangementTrack`: a clip is an `AudioClip` or a `LoadingClip` (`src` plus times in seconds; `isLoadingClip` tells them apart by the missing `sampleRate`). `createArrangement({ tracks })`, `getTracks`, `setTracks`, `addTrack` and `updateTrack` use that type; the ENGINE's `setTracks` / `addTrack` / `updateTrack` still take `ClipTrack`. `_ingest` copies a loading clip (`{ ...clip }`) and gives it no `startTick`; `tickPreparer` and `recomputeStartSamples` go through `forLoadedClips` and return it as it is, so it is the same object through an engine attaching, a tempo change, clip edits of its neighbours, a reorder and a mixer change, and it is in the undo steps like any clip. Clip order within a track is kept (`clipEdits.ts` replaces by index among ALL clips). `moveClip` / `trimClip` / `splitClip` on one warn (`… is still loading and cannot be edited until its audio has loaded`) and change nothing; `getClipBounds` is null and `constrainTrimDelta` 0, without a warning; loaded clips do not collide with it. `arrangementLoading.test.ts`.
- **A change to loading clips only makes no adapter call** — `AdapterSync._playsTheSame(previous, trackId)`: the current track is the same object as `previous`, or its `_loaded` form has the same loaded clip OBJECTS in the same order and every own field other than `clips` is `Object.is`-equal. Used for an `'update'` and, per track, in `_restore` (undo, redo, abort, load). The `statechange` is still emitted and `tracksVersion` still counts. It depends on `updateTrack` keeping held clip objects (the "Immutable" rule): a track object with clip copies of the caller's own is copied and sent. `engine.updateTrack(id)` (no track) always sends. `arrangementLoading.test.ts`, "a change to loading clips only is not sent to the adapter".
- **Wanted sources** (`ArrangementSources.declare(_heldStates())`, from `_emit` for every change but the mix-only ones (`'mixer'`, `'restoreMix'`, `'recording'`), and from `_resyncSourcesQuietly()` in the two places where a stored state is dropped with nothing to announce: `removeTrack(id, { undoable: false })` of a track that only an open transaction's base held, and `beginTransaction()` over an open transaction; there `sources` is published when a status changed and track subscribers are told nothing) — every `src` a loading clip names in the current tracks, every undo and redo state and an open transaction's base, plus the `src` of every loaded clip that carries BOTH `src` and `audioBuffer` (`carried`: the loader is given that buffer with `provide`, which also ends a load of that source in flight, and it is never fetched). A loaded clip with `src` and no `audioBuffer` (peaks first) names nothing: not fetched, not in `sources`. Per track object the names are worked out once (`_trackSources`, a WeakMap). The loader's `setWanted` is called only when the set's members changed (`provide` is called for each carried source on every declare and returns at once for one that is loaded). A source that leaves the set is dropped by the loader (its load aborted, its buffer let go): named again later, it is fetched again. So an undo never starts a fetch for a source the history still names, and a failed source stays failed until `retry`. `arrangementSources.test.ts`, "which sources are loaded", "a clip that already carries its audio", "a source that settles late".
- **The switch** (`_switchLoaded` → `ArrangementSources.beginPass(tickAt)`) — every loading clip whose source is loaded is replaced by `resolveLoadingClip(clip, buffer)`'s clip: seconds to integer samples (`Math.round`) at the BUFFER's sample rate, the same id, `name` / `color` / `gain` / `fadeIn` / `fadeOut` / `waveformData` / `src` carried, a duration more than one sample past the end cut to it with one `console.warn` per loading-clip object, and a `startTick` from `_tickAt` (undefined without an engine). Memoized per loading-clip OBJECT and buffer (`_resolved`), so one loading clip becomes the same loaded clip in every state; the pass maps the current tracks, every undo and redo state and an open transaction's base with the pass's two functions (`current` for the current tracks, called first, and `stored` for the others), which share one memory of the tracks they have seen, so states go on sharing tracks. It runs in two places. (1) `_emit` → `_syncSources`, before anyone is told: a clip that enters naming a source that is already loaded (and still wanted) is a loaded clip within that same call and notification. The same pass switches clips of OTHER tracks when the clip that came in (through `addTrack`, or `updateTrack` of another track) carries `src` and `audioBuffer` for a source they were waiting for; `_syncSources` returns the tracks from before the switch and `_emit` puts them on `at.switched` for an `add` or an `update` (the two changes that name one track), so the engine can send the other tracks too. Still one notification, one `tracksVersion` step and one `statechange` (`arrangementSources.test.ts`, "found by the review of part 4"). (2) `_onSourceSettled`, when the loader settles a source outside one of the arrangement's methods (the loader's notifications during `declare` are ignored through `_declaring`): when the CURRENT tracks changed, `tracksVersion + 1` and one `'load'` change with the previous tracks; when only stored states changed, no change is announced and only `sources` is published. Not an undo step, and it does not clear redo. `arrangementSources.test.ts`, "the switch: audio arrives", "the switch reaches every state the arrangement can return to"; `resolveLoadingClip.test.ts`.
- **A clip that cannot be made, and a source that fails** — `resolveLoadingClip` returns `{ unusable }` for numbers that are not usable (`start` / `offset` not finite or negative, `duration` not positive and finite; `null` duration is "not given"), an offset at or past the end of the audio, a duration shorter than one sample, an empty buffer, or anything `createClip` refuses. The clip then STAYS a loading clip in every state, and while it is in the CURRENT tracks `sources` shows its source as `failed` with an `Error` whose message is `clip "<id>": <reason>` (the first unusable clip of the current tracks the pass meets for that source; the same `Error` object while the message is the same, `_failure`). A usable clip of the same source is still switched. That failure is recomputed by every pass, not stored, and only from the current tracks (maintainer's decision, 2026-11-14: a clip that only an undo or redo state or an open transaction's base holds is not something the app can see or mend). `beginPass` returns `{ current, stored }`; `_switchLoaded` calls `current` with the current tracks FIRST and `stored` for every other state, and only `current` records into `_unusable` (a track object both share is met in `current` first, and the per-pass memo then returns it). So removing or replacing the clip with an undoable edit clears the failure at once (the source reads `loaded` while a stored state still names it), and an undo that brings the clip back brings the failure back. `retry` does nothing for it, because the loader's own state for the source is `loaded`. A source whose LOAD failed (the loader's `failed`, with the error `loadSource` or `getContext` rejected with) changes no track. `arrangementSources.test.ts`, "a clip that cannot be made, and a source that fails".
- **`arrangement.sources` and `retry`** — `sources` is a `ValueSource<ArrangementSourcesValue>`: `{ sources: ReadonlyMap<ClipSource, { status: 'pending' | 'loaded' | 'failed'; error? }>, pendingCount, failedCount, isLoading }`, one entry per wanted source; the order of the entries means nothing. `finishPass()` publishes a new object only when an entry was added or dropped or a status or a failure's `Error` object changed (`sameValue`); it runs at the END of `_emit`'s delivery (after the `onChange` listeners and the subscribers of every queued change, before a listener's error is rethrown), so whoever follows `sources` finds the tracks as they are now, and directly from `_onSourceSettled` when no change was announced. The converse: the tracks are announced first, so a `subscribe` listener that is told of a loaded clip still reads its source as `pending` in `sources`. `retry(src)` is the loader's: it restarts a source whose load FAILED and does nothing for any other source or status; while no context is attached it puts the source back to `pending` and the next attach starts it.
- **Nothing is fetched until a decode context is attached** — the loader's `load` waits for `_getContext` (a deferred that `attachDecodeContext` resolves), then awaits `getContext()` for EACH load, then calls `loadSource(src, { signal, audioContext })`; the sources are `pending` meanwhile, and a `getContext()` that rejects fails the source with that error. The detach function calls the loader's `suspend()`: loads in flight are aborted, loaded sources are kept, the aborted ones stay `pending` and the next attach starts them again (`setWanted` with the same set). A detach called twice, or after another attach replaced its context, does nothing. A second attach while one is attached warns (`An arrangement decodes with one audio context at a time…`) and replaces the getter; loads in flight go on with the context they have. The engine attaches `adapter.audioContext` in its constructor and detaches in `dispose()` (see "Constructor order"); `PlaylistEngineOptions.attachDecodeContext: false` leaves it to the host, and an engine without an adapter attaches nothing. `arrangementAttach.test.ts`.
- **Attaching goes through shared keys** (`attach.ts`) — `ArrangementImpl` has its two attach points as methods under `Symbol.for('@waveform-playlist/engine/arrangement/attach-decode/v3')` and `Symbol.for('@waveform-playlist/engine/arrangement/time-base/v3')`. An app whose own version of this package differs from the one a library pins has two copies installed, and `instanceof ArrangementImpl` would refuse an arrangement made by the other copy; `Symbol.for` gives both copies the same key. `isArrangement(value)` is "has a function under the time-base key", and the engine then treats the object as an arrangement of THIS version and uses it by name: the whole public `Arrangement` interface (every track, clip, mixer, recording and history method it delegates to, `getTracks`, `getMixer`, `recordingTrackIds`, the two version counters) and the internal `onChange(listener)` (with this version's `ArrangementChange` and `ArrangementVersions` shapes), `recomputeStartSamples()` and `undoLimit` (the list is in the header of `attach.ts`). A change to any of that needs a new key, so that copies which do not agree refuse each other. The keys were at `/v2` from #843 (the setters' options, the mix in the history with `'restoreMix'`, the take's mute) and are at `/v3` since #848 (`addTrack(track, { index })`): an engine and an arrangement of different key versions refuse each other (`isArrangement` is false, and the engine throws). The next change of that interface goes to `/v4`. `arrangementAttach.test.ts`, "an arrangement made by another copy of the package".
- **`defaultLoadSource`** (`loadSource.ts`, exported with the type `LoadSource`; `createArrangement({ loadSource })` replaces it) — a string is fetched with the signal, a `Blob` / `File` read with `arrayBuffer()`, then `audioContext.decodeAudioData`. `signal.throwIfAborted()` runs before the work starts and after each await, also in the `catch` blocks, so an abort wins over a fetch or decode failure. Messages: `Failed to fetch <label>: <status> <statusText>` for a response that is not ok; a `TypeError` from `fetch` (network failure, refused cross-origin request) becomes `Error('Failed to fetch <label>')`, with the original in `cause` ONLY when `label === src` (maintainer's decision, 2026-11-14: when the label left anything out, a user name or password, a query string, a fragment, a `data:` / `blob:` URL, the error has no `cause`, because the browser's own message can quote the whole URL; Chromium's does for a URL with credentials, `Request cannot be constructed from a URL that includes credentials: <url>`, run in Chromium 158, not in Firefox or Safari); any other fetch error, an `AbortError` included, is rethrown as it is; `Decoded audio is empty: <label>`; `Failed to decode audio: <label>` only when the decoder rejects with something that is not an `Error` (old Safari: `null`), because a decode `Error` is rethrown as it is and does NOT name the source. `<label>` (`sourceLabel` → `urlLabel`): a URL without its query string, fragment and `user:password@` (each can hold a secret). The `USERINFO` pattern is tried first; when it cuts nothing the string goes through `new URL(url, 'http://relative.invalid/')`, and if the parser finds a user name or password (forms the pattern does not see: one slash after the scheme, backslashes, white space in front) the label is the parsed absolute `href` without credentials, query and fragment. A string the parser refuses is echoed without its query and fragment only. `data: URL` / `blob: URL` for those schemes; a `File`'s name; `Blob`. `loadSource.test.ts`.
- **Without an engine** — `_tickAt` returns `undefined`, so `_ingest` adds no `startTick` (a clip that came with one keeps it), and a clip that is moved, trimmed on the left or split LOSES the tick it had (the functions in `clipEdits.ts` write `time.tickAt(...)`, which is `_tickAt` through `_clipTime`); a right trim keeps it. A loading clip that is switched meanwhile becomes a loaded clip without a tick. `attachEngine` then gives every loaded clip without a tick one from its `startSample`, in every state. `recomputeStartSamples` does nothing, and `_minDuration` is 0.1 s at the clip's own `sampleRate` instead of the engine's.
- **Tests that pinned the behaviour before #812** — `adapterCalls.test.ts` was written against the old engine; where a rule of #812 changed an expectation, the test carries a comment that starts `// Rule (#812…): ` and says what it was before. Keep that form when a later part changes more of them.

## Undo/Redo

- **A stack of references** — `History` (`arrangement/history.ts`) holds `undo` and `redo` arrays of earlier states (`SavedState { tracks, mixer }`: the tracks array and the mixer Map), pushed before each undoable change. No copy, no per-operation inverse logic. `undoLimit` defaults to 100.
- **Undoable operations:** `moveClip`, `trimClip`, `splitClip`, `addTrack`, `removeTrack`, `reorderTrack`, `updateTrack` (when track arg provided), and since #843 `setTrackVolume`, `setTrackMute`, `setTrackSolo`, `setTrackPan`, and `setTrackPanLaw` (#684) (one step per call by default; see "Mixer gestures" and "`undoable: false`"). A step holds the loading clips its tracks had; when their audio arrives they are switched in the step too (see "The switch"), so an undo brings back a loaded clip, and the switch itself is not a step. **Not undoable:** `setTrackRecording`, `setTempo`, `setSelection`, `setZoomLevel`, `setMasterVolume`, `setLoopEnabled`, `setLoopRegion`, `selectTrack`.
- **`setTracks()` clears history and ends an open transaction** — old states reference a different track set.
- **Transactions** — `beginTransaction()` keeps the current state (tracks and mix) as the base (`TransactionBase { state, changed }`); changes during the transaction don't push individual undo steps, they mark the base `changed` (in `_pushUndoSnapshot`, and for a mixer setter in `_recordMixerChange`, whose `gesture` is then ignored). `commitTransaction()` pushes the base as one step (`_pushStep`) when something changed AND the state is not back where the transaction began (`sameState`: `sameTracks`, the same track objects in the same order, and `sameMixerValues`, the same values by track id). `abortTransaction()` restores the base, mix included, without pushing: a mixer change made inside the transaction is taken back (before #843 it survived). An `undoable: false` change inside one is written into the base and does not mark it changed.
- **History changes are announced** — `commitTransaction` (when it added a step) and `clearHistory` (when there was history) announce `'history'`, as do a `removeTrack(id, { undoable: false })` that changed only stored states and an undo or a redo whose state equals the current one, so the engine emits a `statechange` with fresh `canUndo` / `canRedo`; neither version changes. A commit or a `clearHistory` that changes nothing announces nothing.
- **`undo` / `redo` with a transaction open abort it first** (`_abortOpenTransaction`): the transaction's changes are dropped, then the step is undone or redone. With nothing to undo the transaction is still aborted.
- **`canUndo`/`canRedo`** — exposed as getters and in `EngineState` for UI binding.
- **`moveClip` returns constrained delta** — Returns the actually-applied delta (number), not void. Callers (e.g., dawcore clip handler) track this instead of raw pixel delta to avoid no-op undo entries when dragging against boundaries.
- **`AdapterSync._restore` uses incremental adapter updates** — After an undo, a redo or an abort changed the tracks (`'restore'`, with the tracks that were replaced), it compares old and new tracks with `_playsTheSame`. When the same set of track ids is there before and after (decided by id, not by count), it calls `sendTrack` for each track that does not play the same (avoids full playout rebuild that interrupts playback; with an adapter that has no `updateTrack` that is one `setTracks` per differing track); a track the restore did not touch is the same object in both states and is not sent, so an undo of a reorder sends nothing, and neither is a track that differs in its loading clips only. A `'load'` change takes the same path. Falls back to `adapter.setTracks()` when the set of ids differs (`adapterCalls.test.ts` pins each case). Then `sendMixerDiff` calls the setter for each mixer field that differs on a track that was there before and after. An undo that changed only the mix (`'restoreMix'`) makes no track call, only the setters (`adapterCalls.test.ts`, "an undo of the mix calls the mixer setters only"). `ArrangementImpl._restoreState` only swaps the tracks and the mix, increments the versions and announces.
- **A transaction that changed nothing** — `abortTransaction` skips `_restoreState` when the base is not marked `changed`: nothing is announced, so no adapter call and no `statechange` (no full adapter rebuild on a click). `commitTransaction` then pushes no step.
- **`undoLimit`** — `createArrangement({ undoLimit })`, or `PlaylistEngineOptions.undoLimit` when the engine makes its own arrangement. `readonly` field on both. Default 100.
- **Console warn diagnostics** — `moveClip`, `trimClip`, `splitClip` log `console.warn('[waveform-playlist/engine] methodName: ...')` on invalid track/clip IDs. Tests exercising these paths must mock `console.warn`.
- **`tracksVersion` counter** — Monotonic counter in `EngineState` (and on the arrangement) that increments only on **structural** track changes: `setTracks`, `addTrack`, `removeTrack`, `reorderTrack`, `updateTrack(id, track)`, `moveClip`, `trimClip`, `splitClip`, an undo, a redo or an abort that changes the tracks (one that changes only the mix does not), an accepted `setTempo` (the recompute; `setTempo` with the bpm it already has and no `atTick` returns before that), a `removeTrack(id, { undoable: false })` of a track that was in the current tracks, an engine attaching to an arrangement whose current tracks have clips without ticks or ticks in another ppqn, and a source arriving for a loading clip that is in the current tracks (the `'load'` change; an arrival that changes stored states only does not count). Does NOT increment on selection/zoom/master volume/loop changes, on a `'history'` change, NOR on per-track mixer edits (those bump `mixerVersion` — see below). Keeping mixer edits OUT of `tracksVersion` is deliberate: consumers gate expensive structural work (audio-graph rewire, peak regeneration) on it, which must not run on every volume/pan drag frame.
- **`mixerVersion` counter (#501)** — Monotonic counter in `EngineState` (and on the arrangement) that increments on every change of the current mix: a per-track mixer edit (setTrackVolume, setTrackMute, setTrackSolo, setTrackPan) that changes a value of a track that is in the current tracks, an undo, a redo or an abort that brings back other values for a track that is in both states (#843), and the start or end of a take's mute on a current track (the projection has it). Not for a setter given the value the track already has, nor for an entry seeded, carried or dropped with its track. Lets a consumer redraw the mix (e.g. `@dawcore/components`' `<daw-editor>`, which reads it from the arrangement) WITHOUT triggering the `tracksVersion`-gated structural work. The React provider doesn't read it: `useArrangementView` subscribes to the arrangement and derives `trackStates` from `arrangement.getMixer()`.
- **Engine is headless — no rAF loop** — `PlaylistEngine` has no `requestAnimationFrame` dependency. Consumers drive their own animation loops and call `engine.getCurrentTime()` per-frame. The `timeupdate` event was removed — poll `getCurrentTime()` instead.
- **The pan law is a mixer value the first audio decides (#684)** — `TrackMixerValues.panLaw` is `'auto' | 'mono' | 'stereo'`, never absent. Invariant, in the current state and in every saved one: an audio track that holds decoded audio (a clip with an `audioBuffer`) has a decided law; `'auto'` is only the law of a track without any, or of a MIDI track. `mixerValuesOf` gives the entering law (the track's own field when decided, else its audio's, else `'auto'`; a value that is not a law counts as `'auto'`); `decidePanLaws(mixer, tracks)` fills an `'auto'` entry from the track's audio and never touches a decided one. It runs in ONE place, `Arrangement._decidePanLaws()` at the end of `_switchLoaded()`, which every tracks change passes through (`_emit` → `_syncSources`) as does a load that settles by itself: over the current state (bumping `mixerVersion` when it changed, with no `'mixer'` change emitted: the tracks change that brought the audio is the announcement, and the adapter gets the law in the track it is sent), over the history, a gesture's `before` and an open transaction's base (`stateWithDecidedPanLaws()` in `history.ts`, each state from its own tracks). When that changed a saved state OR the current one, `dropRepeats` runs (a law set on a track whose only clip was loading, and the clip has that law: the undo step no longer differs, or, after an undo, the redo step no longer differs from the filled current state; so a load can turn `canUndo` or `canRedo` false). An open gesture goes on when the step now on top equals the one it joined (the rule of `_writeMixerThrough`), and is cleared when its own step went. Review of #684: the first version ran the drop only for a changed saved state and cleared the gesture on any drop. A tracks write that did not go through `_emit` or `_resyncSourcesQuietly` would skip the fill. Because an entry keeps its law whatever the clips are, a track id reused for other material (`setTracks`, `updateTrack`) keeps the law, as it keeps volume and pan. `setTrackPanLaw` throws a `TypeError` for anything but `'mono'` / `'stereo'` before anything changes, and does nothing for a MIDI track. `withMixerValues` returns the track itself when it carries no `panLaw` and the entry is `'auto'` (absent means `'auto'` to `trackPanLaw`), so the projection keeps the arrangement's own track object for a track with an untouched mix. The adapter is sent a change of the law alone through its optional `setTrackPanLaw` (`'auto'` too, on an undo back to it), else through `sendTrack`; `PlaylistEngine.setTrackPanLaw`, unlike the other four, calls nothing on the adapter when the arrangement changed nothing. Functions that list the mixer fields by name, each silent when a field is missing: `sameValues`, `mixerChanges`, `withMixerValues`, `mixerValuesOf`, `AdapterSync.sendMixerValues`.
- **Mixer setters** — `setTrackVolume/setTrackMute/setTrackSolo/setTrackPan(trackId, value, options?: MixerChangeOptions)` on the arrangement and on the engine (the engine passes `options` on). The arrangement's setter replaces the mixer Map and the one entry (no track object is written to or replaced), records the undo step (below), bumps `mixerVersion` and announces `'mixer'`; the engine's listener forwards the value to the adapter (`AdapterSync.sendMixerValues`) and emits `statechange` (#501) — NOT `tracksVersion` (these are not structural changes). A later adapter rebuild keeps the value because every track is sent through the projection. When the arrangement changes nothing (a track that is not in the current tracks, or the value the track already has), no `statechange` is emitted and the engine still calls the adapter's setter itself (`_mixerChanged` returned false; a consumer may target a track the engine hasn't ingested yet), unless the engine is disposed; the mute goes through `sendMixerValues`, so the track a take is recording onto, when the arrangement holds it, is not unmuted by it.
- **Mixer changes are undo steps** (#843) — by default each call pushes the state from before and clears redo. `MixerChangeOptions`: `gesture` (a string) groups, `undoable: false` keeps a change out; with both, `undoable: false` wins. Inside an open transaction an undoable mixer change is part of it like any other change, and its `gesture` is ignored; an `undoable: false` one is written into the base and does not mark the transaction changed.
- **Mixer gestures** — a change with `{ gesture: id }` joins the top step when that step was pushed by a change with the same id and nothing has touched the history since (`_gesture`: its id and the history from before its step was pushed). It is cleared by every other push (`_pushStep`, also a commit's), `undo`, `redo`, `clearHistory`, `setTracks`, `beginTransaction`, `commitTransaction`, an abort, the purge, and an `undoable: false` change that dropped that step as a repeat of the current state; a take's mute (`setTrackRecording`), an `undoable: false` change that leaves the step or leaves an equal one on top (a step below that the write made equal to it: `dropRepeats` keeps the older of two, so `_writeMixerThrough` compares the new top with `sameState`, not by identity; review #909), and a setter that changes nothing do not clear it. Otherwise the change pushes a step and becomes `_gesture` (its id, and the history from before the push) (not with `undoLimit: 0`, which keeps no step). When a joined change brings the tracks and the mix back to the step's state, the step is dropped (`_dropReturnedGestureStep`) and the history it found is put back, redo states and a step the undo limit evicted included (as a transaction that changes nothing keeps them; `before` is mapped by the time base, the switch to loaded clips and `undoable: false`, and its tracks are in `_heldStates`); the next change of that gesture pushes a new one. The id is compared as a string. `createMixerGesture()` makes one per control; it is in core (`packages/core/src/mixerGesture.ts`, exported with `MixerGesture`), not here (it was put there while dawcore imported the engine only through `await import()`; since #848 it imports it normally): `id`, `end()` (a new id: the next change starts a new step) and `attach(input)`, which listens for `keydown`, `keyup`, `change` and `blur` and returns the function that removes all four. A `change` (the end of a pointer drag) ends the gesture unless a key that moves a range input (arrows, Page Up/Down, Home, End) is down; that key's `keyup` ends it, so a held key's auto-repeat is one step; `blur` ends it and forgets the held key. Ids are `mg-<prefix>-<n>`: a counter, with a random prefix made once per module, so two copies of the package never make the same id. Mute and solo buttons need no helper: each click is a step. Tests: core's `mixerGesture.test.ts` (the helper's events), here `mixerGestureUndo.test.ts` (one drag is one step), `arrangementMixerUndo.test.ts` and `arrangementGestureHistory.test.ts` (the three mappings of `before`, and the equal step left on top).
- **`undoable: false`** — no step: the value is set in the current mix and in the entry of that track in every saved state that has one (each undo and redo step and an open transaction's base: `writeThrough`, the same reach as the purge), so no later undo, redo or abort brings the old value back. Redo is kept. A step that no longer differs from the state next to it is then dropped (`dropRepeats`), so `canUndo` is never true for an undo that would do nothing visible; while a transaction is open the state next to the newest step is the base (what an abort returns to and a commit pushes), not the working state, and the purge compares the same way. For automation, or any value that is not the user's edit. **Known limits (R10):** the write follows the track by id, so it does not reach the states from before a rename (an undo past the rename brings back the value from before the write), and it does reach the saved states of a removed track whose id a new track re-uses (an undo back to the old track shows the written value, not its own).
- **Clip operations use `updateTrack`, not `setTracks`** — `moveClip`, `trimClip`, `splitClip` announce `'update'` (with the replaced track as `previous`; an edit replaces a loaded clip, so the track never "plays the same"), and the engine's listener calls `AdapterSync.sendTrack(trackId)` (through `follow`) which uses `adapter.updateTrack()` when available, falling back to `adapter.setTracks()`. This rebuilds only the affected track's clips on the adapter — other tracks keep playing uninterrupted.
- **`addTrack()` uses incremental adapter path** — When `adapter.addTrack` is defined, `AdapterSync._addTrack` calls it instead of `adapter.setTracks()`. The `PlayoutAdapter.addTrack` method is optional (`addTrack?`) for backwards compatibility.
- **`updateTrack(trackId, track?)`** — Public method. With a `track` argument: replaces that track in the arrangement (an undo step; the track's mixer fields are not read; given a new id, the track keeps its mix, the adapter gets a full `setTracks` and a `selectedTrackId` naming the old id is cleared), which emits statechange and reaches the adapter unless the track plays the same as before (the same loaded clip objects in the same order and the same own fields: `engine.updateTrack(id, { ...track })` with a track taken from `arrangement.getTracks()` is an undo step and a statechange with no adapter call); an id no track has does nothing (no undo step, no adapter call, no statechange), though the track is still checked first and a track of the wrong kind throws. Without one: sends the arrangement's current track (with the current mix) to the adapter again (`AdapterSync.sendTrack`), with no change of state and no statechange; a disposed engine does nothing. Used by external callers (e.g., dawcore `addRecordedClip`).
