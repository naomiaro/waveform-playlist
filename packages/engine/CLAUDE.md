# Engine Package (`@waveform-playlist/engine`)

**Purpose:** Framework-agnostic timeline engine extracted from React hooks. Enables Svelte/Vue/vanilla bindings.

**Architecture:** Three layers — pure operations functions, the arrangement (`src/arrangement/`, public through `createArrangement()` and the `Arrangement` interface; the class `ArrangementImpl` is not exported), and the stateful `PlaylistEngine` class with event emitter. The arrangement owns the tracks, the mix, the undo history and transactions; the engine owns transport and view state, delegates every track, clip, mixer and history method to its arrangement, and follows it by subscription: for each change it is told about, its `AdapterSync` (`src/adapterSync.ts`) makes the adapter call and the engine emits `statechange` (#812). See "The arrangement owns the tracks" below.

**Build:** Uses tsup (not vite) — `pnpm typecheck && tsup`. Outputs ESM + CJS + DTS.

**Testing:** vitest unit tests in `src/__tests__/`. Run with `npx vitest run` from `packages/engine/`.

**Key types:** `Arrangement`, `CreateArrangementOptions`, `RemoveTrackOptions`, `ClipBounds`, `TrackMixerValues` (the arrangement's public face), `PlayoutAdapter` (pluggable audio backend interface — requires `readonly audioContext: AudioContext`, `readonly ppqn: number`; optional `addWorkletModule`/`createAudioWorkletNode`/`createMediaStreamSource` for cross-context worklet support, `masterOutputNode` for analyzer/recorder tap), `EngineState` (state snapshot; its `tracks` is `readonly ClipTrack[]` and not a copy), `EngineEvents` (statechange, play/pause/stop).

**Operations:** `clipOperations.ts` (drag constraints, trim, split), `viewportOperations.ts` (bounds, chunks, scroll threshold), `timelineOperations.ts` (duration, zoom, seek).

**No React, no Tone.js** — zero framework dependencies. Only peer dependency is `@waveform-playlist/core`.

## Tempo Management

- **`setTempo(bpm, atTick?)` commits on adapter acceptance** — Forwards to `adapter?.setTempo?.()` FIRST; an explicit `false` return (e.g. the transport's multi-entry tempo-map guard, #407) means refused — `_bpm` keeps its prior value, no recompute, no statechange. `void`-returning and absent adapters count as accepted: then `_bpm` updates and the arrangement recomputes ("Recompute after a tempo change" below), which emits the statechange. `PlayoutAdapter.setTempo` is typed `boolean | void`.
- **`getCurrentTime()` always reads from adapter** — No `_isPlaying` gate. When adapter exists, adapter is the time authority. `_currentTime` is only a fallback for headless/no-adapter mode.
- **`_ticksToSeconds` / `_secondsToTicks`** — Delegates to `adapter.ticksToSeconds()` / `adapter.secondsToTicks()` when available (multi-tempo via Transport's TempoMap). Falls back to simple single-tempo math.
- **Recompute after a tempo change** — an accepted `setTempo` calls `ArrangementImpl.recomputeStartSamples()`, which immutably maps all tracks/clips, recomputes `startSample` from `startTick` for clips that have `startTick` defined (a clip whose start is already right keeps its object), increments `tracksVersion` and announces `'recompute'`; the engine's listener then sends every track to the adapter one by one (`AdapterSync.sendTrack`) and emits `statechange`. A tempo change therefore places every clip that has a tick on the CURRENT engine's tick grid, with or without an engine swap. A disposed engine's `setTempo` returns before the adapter call. It does nothing while no engine is attached.
- **`setTracks()` enriches clips** — Clips without `startTick` get it computed from `startSample / sampleRate` (`ArrangementImpl._ingest` → `_tickAt`, through the time base the engine gives the arrangement in `attachEngine`: closures over `_secondsToTicks()` / `_ticksToSeconds()`, evaluated at call time). Uses immutable mapping pattern. `addTrack` and `updateTrack(id, track)` do the same. With no engine attached there is no tempo to convert with, so a clip gets no tick (see "Without an engine" below); `attachEngine` gives one, from its `startSample`, to every clip that has none, in every state the arrangement holds (see "Attach prepares every state").
- **Constructor accepts `bpm` and `ppqn`** — Via `PlaylistEngineOptions`. Defaults: 120 BPM, 960 PPQN. Exposed in `EngineState`.

## Zoom Level Validation

`samplesPerPixel` must exist in the `zoomLevels` array — engine constructor throws if not (`indexOf` check, not `findClosestZoomIndex`). Default zoom levels: `[256, 512, 1024, 2048, 4096, 8192]`. Default `samplesPerPixel`: 1024. When adding examples, always use a value from the zoom levels array.

## Patterns

- **`setTracks`, `addTrack` and `updateTrack(id, track)` throw on a track whose clips do not match its `kind` (#756), on a duplicate track id and on two clips with one id in a track (#812)** — `assertTrackKind` from core, then `assertUniqueTrackIds` / `assertUniqueClipIds` / `duplicateTrackId` (`arrangement/validate.ts`), all in the arrangement's method and all called FIRST: before the open transaction is ended, before the history is cleared, before the undo step, and so before any listener or adapter is told. A throw therefore leaves tracks, history, mixer and adapter exactly as they were (`trackKind.test.ts`, `arrangementRules.test.ts` "ids are unique"). Keep the assertions ahead of any mutation when changing these methods. The messages start with `[waveform-playlist]`. Two clips of one id on DIFFERENT tracks are accepted. `updateTrack` may give a track a new id that no other track has; a track given as the first tracks of `createArrangement({ tracks })` is checked the same way. Undo/redo restore tracks that were already accepted and do not re-check.

- **`play()` and `seek()` do not clamp to duration** — The Transport runs at any non-negative position, playing silence where there's no audio. This enables recording from cursor positions beyond existing clips. Only negative values are clamped to 0.
- **Default sampleRate is 48000** — Changed from 44100 to match modern hardware. Consumers should still pass `AudioContext.sampleRate` explicitly when creating the engine.
- All mutating methods (moveClip, trimClip, removeTrack, setZoomLevel) guard against no-op statechange emissions — bail early when constrained delta is 0, track not found, or zoom unchanged
- Tracks are copied on their way in (`_ingest`: the track and each clip); nothing is copied on the way out. `getState().tracks`, `arrangement.getTracks()` and what an adapter receives are the engine's own objects, typed `readonly ClipTrack[]` and frozen outside production builds — see "The arrangement owns the tracks"
- `PlayoutAdapter.isPlaying()` is defined but not called by engine (engine tracks own `_isPlaying`) — bounded completion is now observed via `onPlaybackEnded` (#608); `isPlaying()` polling remains unused by design.
- **`onPlaybackEnded` hook (#608)** — optional `PlayoutAdapter.onPlaybackEnded(callback | null)`, for adapters that self-terminate a duration-limited `play(start, end)` (annotation/selection playback). Constructor subscribes once: `this._adapter?.onPlaybackEnded?.(() => queueMicrotask(() => { if (this._isPlaying && !this._disposed) this.stop(); }))`. The `queueMicrotask` defer matters because the Tone adapter fires this from inside the Transport tick chain, which catches nothing (see playout CLAUDE.md) — stopping the Transport re-entrantly from a tick callback is the hazard the microtask sidesteps. Re-checking `_isPlaying` AND `_disposed` inside the microtask covers a consumer `stop()`/`dispose()` landing in the gap between the adapter's callback firing and the microtask running.
- **Single callback slot, last-subscriber-wins** — `onPlaybackEnded` takes exactly one callback, not a listener set — matches the repo-wide one-engine-per-adapter convention (no fan-out, no unsubscribe-by-reference needed).
- **Dispose unsubscribes before tearing down the adapter** — `dispose()` sets `_disposed = true`, stops following the arrangement and detaches from it (`_stopFollowingArrangement()`, `_detachFromArrangement()`), sets `_isPlaying = false`, then calls `this._adapter?.onPlaybackEnded?.(null)` BEFORE `this._adapter?.dispose()` (itself wrapped in try/catch). This guarantees a disposed engine can't be re-entered by a late adapter callback; the microtask's own `_disposed` check is the second layer of defense for a callback that was already in flight when dispose ran.
- Engine uses `seek()` while browser package uses `seekTo()` — naming divergence, noted in root CLAUDE.md "Common Doc Drift"
- **Guard Against No-Op State Emissions** - In stateful classes with event emitters, check if an operation would actually change state before emitting. Zero-delta moves/trims, removing non-existent items, and setting zoom to the same level should bail early to avoid wasted listener calls and UI re-renders.
- **Engine owns selection, loop, selectedTrackId, zoom, and masterVolume (the arrangement owns tracks, mix and history)** — React subscribes to `statechange` and mirrors into useState/refs via `onEngineState()` callbacks in each hook. Consumers poll `engine.getCurrentTime()` per-frame in their own animation loops.
- `setSelection()` and `setLoopRegion()` normalize `start <= end` via `Math.min/Math.max` — consumers can trust `EngineState` invariants without defensive normalization
- **`getAudibleTime()` for visual consumers** — Latency-compensated position (raw − `outputLatency` − `lookAhead`, held at `_playStartPosition` during the pre-roll window) while playing; raw `_currentTime` when resting. Compensation is a property of *playing*, not of position — a seeked/paused/stopped cursor displays exactly. Storage stays raw (`getCurrentTime()`); never feed `getAudibleTime()` back into `play()`/`seek()`.
- **Loop activation uses `< loopEnd` check** — `play()` activates Transport loop when starting before `loopEnd` (not `>= loopStart && < loopEnd` like before). Starting before the loop region still activates looping — Transport plays through to `loopEnd`, then wraps to `loopStart`. Starting at or past `loopEnd` plays to the end without looping (click-past-loop behavior). `setLoopEnabled()`/`setLoopRegion()` during playback use `_isBeforeLoopEnd()` — same `< loopEnd` check against live adapter position. Selection/annotation playback (with `endTime`) always disables loop.
- **`play()` state rollback on adapter throw** — `play()` saves `prevCurrentTime` and `prevPlayStartPosition` before mutations. If `adapter.play()` throws, state is restored so the engine isn't left with a moved playhead but no audio.
- `engine.dispose()` wraps `adapter.dispose()` in try-catch to guarantee `_listeners.clear()` always runs. Explicit `engine.off()` is unnecessary when the engine itself is being disposed.

## The arrangement owns the tracks

One owner per piece of state (#812):

| State | Owner |
| --- | --- |
| tracks and clips, `tracksVersion` | the arrangement |
| the mix (volume, mute, solo, pan by track id), `mixerVersion` | the arrangement |
| undo/redo history, the open transaction | the arrangement |
| transport (`_currentTime`, `_isPlaying`, `_playStartPosition`), selection, loop, zoom, selected track id, master volume, tempo (`_bpm`, `_ppqn`) | the engine |
| the audio graph | the adapter, a one-way cache the engine keeps in step by subscription |

**Files (`src/arrangement/`):**

- `types.ts` — the public `Arrangement` interface, `ClipBounds`, `RemoveTrackOptions`, `CreateArrangementOptions`
- `index.ts` — `createArrangement(options)` and the public type re-exports; the only arrangement module `src/index.ts` exports from
- `Arrangement.ts` — `ArrangementImpl` (internal) with the internal types `ArrangementChange`, `ArrangementTimeBase`, `ArrangementOptions`, `ArrangementVersions`
- `mixer.ts` — `TrackMixerValues` and the pure functions over the mixer Map (`seedMixer`, `setMixerValues`, `carryMixerEntry`, `retainMixer`, `withMixerValues`, `mixerValuesOf`)
- `history.ts` — undo/redo as pure functions over references (`pushStep`, `undoStep`, `redoStep`, `beginBase`, `sameTracks`, `withoutTrack`, `purgeTrack`)
- `clipEdits.ts` — the clip edits as pure functions over a tracks array (`moveClip`, `trimClip`, `splitClip`, `clipBounds`, `constrainTrim`; `ClipEditTime` is how they convert time)
- `ticks.ts` — `withClips`, `clipMapper` (one clip function over many states, keeping shared track objects shared), `rescaleTick` (a tick from one ppqn to another)
- `validate.ts` — the unique-id checks
- `devFreeze.ts` — `freezeTracksInDevelopment`, `freezeTrackInDevelopment`, `isDevelopmentBuild`

Beside the folder: `src/adapterSync.ts` — class `AdapterSync`, what keeps the adapter in step: `tracks()` (the projection), `sendInitialTracks()`, `sendAllTracks()`, `sendTrack(id)`, `sendMixerValues()`, `follow(change, at)`, `markSkip()` / `unmarkIfUnchanged()`. The engine keeps `_adapterSync`, `_onArrangementChange`, `_clearSelectionIfGone` and `_mixerChanged`.

**Rules:**

- **With or without the `arrangement` option** — `new PlaylistEngine({ arrangement })` plays an arrangement from `createArrangement()` (anything else throws: `asArrangementImpl` checks `instanceof ArrangementImpl`); without the option the engine makes its own with `undoLimit`. With the option, `undoLimit` on the engine is ignored with a `console.warn`; `engine.undoLimit` reads the arrangement's.
- **Constructor order** — `attachEngine(timeBase)` first, then `new AdapterSync(arrangement, adapter)`, then `onChange` (so the engine is not told about the attach's `'recompute'`; arrangement subscribers are, before the new engine's first adapter call), then `sendInitialTracks()`: one `adapter.setTracks` when the arrangement already has tracks, none when it is empty. If that call throws, the constructor stops following and detaches (`_stopFollowingArrangement()`, `_detachFromArrangement()`) before rethrowing, because nobody holds the engine to dispose it. No `statechange` is emitted by the constructor.
- **An arrangement outlives its engine** — `dispose()` unsubscribes and detaches; the arrangement keeps tracks, mix and history, can still be changed through the disposed engine or directly (no adapter call, no `statechange`, no throw: the track methods no longer reach the adapter, the mixer setters and `updateTrack(id)` check `_disposed`, and `setTempo` returns before the adapter call), and the next engine built on it finds all three. One engine at a time: `attachEngine` warns when a time base is still attached, and the new one replaces it.
- **Attach prepares every state, atomically** — a clip's `startTick` is counted in an engine's ppqn, and the arrangement remembers the unit its ticks are in (`_tickPpqn`: null until an engine has attached, so a tick a clip came with before that is read in the first engine's ppqn). `ArrangementTimeBase` has a `ppqn` field; the engine passes its own. `attachEngine` builds one `clipMapper` (`ticks.ts`) and runs it over the current tracks, every undo and redo state and an open transaction's base: a clip without a `startTick` gets one from its `startSample` (also when the ppqn is the same), and a tick in another ppqn is converted with `rescaleTick` (`Math.round(tick * to / from)`); `startSample` is untouched. The mapper remembers each track it has mapped, so states go on sharing the track objects they shared, and returns the same array when nothing in it changed. Everything is worked out BEFORE anything is assigned: if the engine's tempo map throws meanwhile, nothing has changed and the arrangement is not attached. One `'recompute'` and `tracksVersion + 1` when the CURRENT tracks changed (a change in stored states only announces nothing); not an undo step. Going to a coarser ppqn rounds (7 at 960 → 1 at 192 → 5 back at 960), so the next tempo change can place such a clip up to half a tick of the coarser engine away from where it was: 0.5 × 60 × sampleRate / (ppqn × bpm) samples, about 62 samples (1.3 ms) at 192 ppqn, 120 bpm, 48 kHz (figures from a reviewer's probe, not from a test in the repository). A different TEMPO is not converted: the tick is the musical position, and `startSample` disagrees with it until the next `setTempo` recomputes; clips added under the new engine get their ticks at its tempo and keep their place at that `setTempo`, while the older ones move. Two live engines with different ppqn on one arrangement (the case that warns) is unsupported: the second time base replaces the first, so the first engine's later tick conversions use the second engine's. `arrangementEdges.test.ts`, "an engine with another tick resolution (ppqn) takes over".
- **Immutable** — a change replaces the tracks array and only the track and clip objects that changed; nothing is written into an object `getTracks()` has returned. An undo step is a reference to an earlier array (`history.ts` copies no track), and two states share every track that is the same in both. `updateTrack(id, fn)` keeps the clip objects the arrangement already held (the `held` set of `_ingest`). The exception to "only what changed" is `setTracks`: it copies every track and clip it is given, so no track object survives it.
- **Nothing handed out is a copy** — `getState().tracks`, `arrangement.getTracks()`, `arrangement.getMixer()` and every track an adapter receives. Types: `readonly ClipTrack[]`, `ReadonlyMap`. `getTracks()` is the same array until the tracks change; `getMixer()` is the same Map until a value changes, an entry is added (a track with a new id enters, or a track is given a new id) or entries are dropped (`mixerVersion` counts only the first of these); `getState().tracks` the same array until tracks or mix change.
- **Dev freeze** — `ArrangementImpl._emit` freezes the current tracks before anyone is told (`freezeTracksInDevelopment`: the array, each track, its `clips` array, each clip; not what a clip refers to), and the engine freezes its projection the same way, also before the adapter receives it. `isDevelopmentBuild()` is `process.env.NODE_ENV !== 'production'`, and false where there is no `process` at all (a page that loads the module without a bundler). The caller's own objects are never frozen (they were copied on the way in). `arrangementFrozen.test.ts`.
- **The mix is a part of its own** — a Map by track id. A track's own `volume` / `muted` / `soloed` / `pan` fields are the values it ENTERED with: `seedMixer` makes an entry from them (`mixerValuesOf`, defaults 1 / false / false / 0 for a missing field) only for an id that has no entry. `addTrack`: an id whose entry is still kept for an undo (the track was removed) finds that entry again. `setTracks`: only an id that is in the tracks being REPLACED (the current tracks) keeps its mix; every other entry is dropped first, so an id that only the undo history held is seeded from the new track's fields. `updateTrack`: the entry stays; a track given a new id takes its mix with it (`carryMixerEntry`), also over an entry the new id still has from a removed track (the carried mix wins); the new track's fields are not read unless the old id had no entry. Seeding, carrying and dropping do not increment `mixerVersion`. A setter acts only on a track that is in the CURRENT tracks (`_setMixerValues` returns for any other id, also one whose entry is kept for an undo): it replaces the Map and one entry and no track object, increments `mixerVersion` and announces `'mixer'`; it is not an undo step and does not clear redo.
- **Mixer entries are retained while a state holds the track, and dropped when none does** — the states are the current tracks, every undo and redo step, and the base of an open transaction (`_heldStates()`). `retainMixer` over `_heldStates()` runs wherever a state can stop holding a track: `clearHistory`, `_removeTrackEverywhere`, `_pushStep` when the new step clears a redo stack or pushes a step past `undoLimit`, and `_emit` for every `'remove'` and `'restore'` (a removal, an undo, a redo or an abort that leaves no state holding the track). So `removeTrack` keeps the entry while its undo step exists, and with `undoLimit: 0` the entry goes at once. `setTracks` clears the history and keeps only what the rule above says.
- **Undo, redo and abort never change the mix** — the history holds tracks only. Undo of a `removeTrack` brings the track back with the mix it had when removed; a mixer change made inside a transaction survives its abort. One exception: undoing or redoing an id change (`updateTrack` with a new id) switches between the old id's entry and the new id's entry, so a fader moved after the rename is not what the old id has after the undo. A second one: when a track is given the id of a removed track whose removal can still be undone, the renamed track's mix replaces the removed track's, so undoing back past the removal brings that track back with the renamed track's mix. (One entry per id: `carryMixerEntry` overwrites. The old id's entry is dropped at the rename unless a stored state still holds a track of that id.)
- **The projection** — `AdapterSync.tracks()` is the arrangement's tracks with the current mixer values in their fields (`_withMix` → `withMixerValues`, memoized per track object in `_withMixMemo`; the array cached in `_projection` by both versions). It is what `getState().tracks` returns and what every adapter track call sends; derived, never written back. A track whose fields already hold the values is the arrangement's own object.
- **Internal `onChange(change, at)` vs public `subscribe(listener)`** — `onChange` is for the engine: it is told WHAT changed (`ArrangementChange`: `set`, `add`, `remove`, `update`, `reorder`, `restore` with the previous tracks, `mixer`, `recompute`, `history`) and the versions right after that change (`at`), before the subscribers; a listener here that throws does not stop the delivery, and the first error is thrown, once the queue is empty, to the caller of the arrangement method that is delivering (so an adapter that throws fails that call, and that change emits no `statechange`; for a change made from inside a listener the failing call is the OUTER one, not the one that made the change). `subscribe` is public: no arguments, once per change, after the `onChange` listeners, so after the engine has made its adapter call for that change (not "the adapter is in step" in two cases: a change made with `skipAdapter`, and the tick assignment of `attachEngine`, which subscribers hear before the new engine's first `adapter.setTracks`); a subscriber that throws is reported with `console.warn('[waveform-playlist] Error in an arrangement subscriber:', …)` and fails nothing. Each `subscribe` call is its own entry, so one function subscribed twice is told twice.
- **Delivery is ordered** — `_emit` queues the change in `_pending`; a change made from inside a listener (an `onChange` listener, a subscriber, or a `statechange` listener, which runs inside the engine's `onChange` listener) waits until the one being delivered has reached every listener. Every arrangement change is exactly one `statechange`. `AdapterSync.follow(change, at)` decides the adapter call from the versions: ONE track edit made from inside a listener is still the current state when it is delivered (`at.tracksVersion === arrangement.tracksVersion`) and is sent as itself. A change delivered after the tracks have changed AGAIN (two or more track edits in one listener run) cannot be told from the current tracks alone: the adapter is sent every track once (`sendAllTracks()`, a full `adapter.setTracks` that can interrupt playback), which records the version it covers in `_syncedTracksVersion`, and the changes still waiting (`at.tracksVersion <= _syncedTracksVersion`) make no adapter call. Their `statechange` is still emitted. After an adapter call for a track change throws, `_needsAllTracks` stays set and the next track change sends every track. `mixer` changes are always forwarded (`sendMixerValues`).
- **`skipAdapter` is marked by the change's `tracksVersion`** — the engine's `moveClip`/`trimClip` with `skipAdapter` call `AdapterSync.markSkip()`, which adds `tracksVersion + 1` to `_skipAt` before the arrangement is called; `follow` deletes `at.tracksVersion` from the set for an `'update'` and makes no adapter call when it was there. The mark travels with the version, not with the call, because a change made from inside a listener is delivered after the call returned. A call that changed nothing removes its mark (`unmarkIfUnchanged`, in a `finally`, so also when the arrangement call throws).
- **Adapter call per change** (`PlaylistEngine._onArrangementChange` → `AdapterSync.follow` → `_sendChange`, for a change that is still the current state; see "Delivery is ordered" for the others) — `set`: `setTracks`. `add`: `adapter.addTrack` when defined, else `setTracks` (`_addTrack`). `remove`: `adapter.removeTrack` when defined, else `setTracks`. `update`: `sendTrack` (`adapter.updateTrack` when defined, else `setTracks`); a track that was given a new id is not found under the old one and goes as `setTracks`. `restore`: `_restore`. `recompute`: every track through `sendTrack`. `mixer`: `sendMixerValues`, the one adapter setter. `reorder` and `history`: no adapter call. Every `setTracks` goes through `sendAllTracks()`.
- **The selected track id is cleared when its track is gone, except by `setTracks`** — `_clearSelectionIfGone()` runs in `_onArrangementChange` for `remove`, `restore` and `update` changes, before the `statechange` of that change: a `removeTrack`, an undo of an `addTrack`, a redo of a `removeTrack`, an abort, an `updateTrack` that gives the track a new id (it is gone under the old one). NOT for `set`: a host may empty the tracks and add them again (the React provider calls `setTracks([])`), and the selection must survive that, as it did before #812. Tests: "the selected track" in `arrangementRules.test.ts`, "a track that is given a new id" in `arrangementEdges.test.ts`.
- **Arrangement-only API** — `removeTrack` takes `{ undoable: false }` (maintainer, 2026-11-14: `removeTrack` only). It is not "skip the undo step": a step is a whole earlier tracks array, so a later undo would bring the track back. `_removeTrackEverywhere` takes the track out of the current tracks, every undo and redo state and an open transaction's base (`purgeTrack` / `withoutTrack` in `history.ts`), drops steps that no longer differ from the state next to them (`sameTracks`), and drops the mixer entry; it announces `remove`, or `history` when only stored states changed. `addTrack` and `updateTrack` have no such option, because applying an add or an update to every earlier state has no clear meaning; `updateTrack` takes a function of the current track (not called for an unknown id; returning the track it was given changes nothing). The engine's methods of the same names do not take these.
- **Without an engine** — `_tickAt` returns `undefined`, so `_ingest` adds no `startTick` (a clip that came with one keeps it), and a clip that is moved, trimmed on the left or split LOSES the tick it had (the functions in `clipEdits.ts` write `time.tickAt(...)`, which is `_tickAt` through `_clipTime`); a right trim keeps it. `attachEngine` then gives every clip without a tick one from its `startSample`, in every state. `recomputeStartSamples` does nothing, and `_minDuration` is 0.1 s at the clip's own `sampleRate` instead of the engine's.

## Undo/Redo

- **A stack of references** — `History` (`arrangement/history.ts`) holds `undo` and `redo` arrays of earlier tracks arrays, pushed before each undoable change. No copy, no per-operation inverse logic. `undoLimit` defaults to 100.
- **Undoable operations:** `moveClip`, `trimClip`, `splitClip`, `addTrack`, `removeTrack`, `reorderTrack`, `updateTrack` (when track arg provided). **Not undoable:** `setTrackVolume`, `setTrackMute`, `setTrackSolo`, `setTrackPan`, `setTempo`, `setSelection`, `setZoomLevel`, `setMasterVolume`, `setLoopEnabled`, `setLoopRegion`, `selectTrack`.
- **`setTracks()` clears history and ends an open transaction** — old states reference a different track set.
- **Transactions** — `beginTransaction()` keeps the current tracks array as the base (`TransactionBase`); changes during the transaction don't push individual undo steps, they mark the base `changed` (in `_pushUndoSnapshot`). `commitTransaction()` pushes the base as one step (`_pushStep`) when something changed AND the tracks are not back where the transaction began (`sameTracks`: the same track objects in the same order). `abortTransaction()` restores the base without pushing.
- **History changes are announced** — `commitTransaction` (when it added a step) and `clearHistory` (when there was history) announce `'history'`, as does a `removeTrack(id, { undoable: false })` that changed only stored states, so the engine emits a `statechange` with fresh `canUndo` / `canRedo`; neither version changes. A commit or a `clearHistory` that changes nothing announces nothing.
- **`undo` / `redo` with a transaction open abort it first** (`_abortOpenTransaction`): the transaction's changes are dropped, then the step is undone or redone. With nothing to undo the transaction is still aborted.
- **`canUndo`/`canRedo`** — exposed as getters and in `EngineState` for UI binding.
- **`moveClip` returns constrained delta** — Returns the actually-applied delta (number), not void. Callers (e.g., dawcore clip handler) track this instead of raw pixel delta to avoid no-op undo entries when dragging against boundaries.
- **`AdapterSync._restore` uses incremental adapter updates** — After an undo, a redo or an abort changed the arrangement (`'restore'`, with the tracks that were replaced), it compares old and new tracks by reference. When the same set of track ids is there before and after (decided by id, not by count), it calls `sendTrack` for each track that is a different object (avoids full playout rebuild that interrupts playback; with an adapter that has no `updateTrack` that is one `setTracks` per differing track); a track the restore did not touch is the same object in both states and is not sent, so an undo of a reorder sends nothing. Falls back to `adapter.setTracks()` when the set of ids differs (`adapterCalls.test.ts` pins each case). `ArrangementImpl._restoreTracks` only swaps the tracks, increments `tracksVersion` and announces.
- **A transaction that changed nothing** — `abortTransaction` skips `_restoreTracks` when the base is not marked `changed`: nothing is announced, so no adapter call and no `statechange` (no full adapter rebuild on a click). `commitTransaction` then pushes no step.
- **`undoLimit`** — `createArrangement({ undoLimit })`, or `PlaylistEngineOptions.undoLimit` when the engine makes its own arrangement. `readonly` field on both. Default 100.
- **Console warn diagnostics** — `moveClip`, `trimClip`, `splitClip` log `console.warn('[waveform-playlist/engine] methodName: ...')` on invalid track/clip IDs. Tests exercising these paths must mock `console.warn`.
- **`tracksVersion` counter** — Monotonic counter in `EngineState` (and on the arrangement) that increments only on **structural** track changes: `setTracks`, `addTrack`, `removeTrack`, `reorderTrack`, `updateTrack(id, track)`, `moveClip`, `trimClip`, `splitClip`, `undo`, `redo`, an abort that restores, an accepted `setTempo` (the recompute; `setTempo` with the bpm it already has and no `atTick` returns before that), a `removeTrack(id, { undoable: false })` of a track that was in the current tracks, and an engine attaching to an arrangement whose current tracks have clips without ticks or ticks in another ppqn. Does NOT increment on selection/zoom/master volume/loop changes, on a `'history'` change, NOR on per-track mixer edits (those bump `mixerVersion` — see below). Used by the provider to detect structural statechange events and skip `loadAudio` rebuilds. Keeping mixer edits OUT of `tracksVersion` is deliberate: consumers gate expensive structural work (audio-graph rewire, peak regeneration) on it, which must not run on every volume/pan drag frame.
- **`mixerVersion` counter (#501)** — Monotonic counter in `EngineState` (and on the arrangement) that increments on per-track mixer edits (setTrackVolume, setTrackMute, setTrackSolo, setTrackPan) of a track that is in the current tracks. Lets a consumer that caches a track snapshot (e.g. `@dawcore/components`' `<daw-editor>` `_engineTracks`) refresh that cache WITHOUT triggering the `tracksVersion`-gated structural work. The React provider doesn't need it (it persists mixer state via `trackStates`).
- **Engine is headless — no rAF loop** — `PlaylistEngine` has no `requestAnimationFrame` dependency. Consumers drive their own animation loops and call `engine.getCurrentTime()` per-frame. The `timeupdate` event was removed — poll `getCurrentTime()` instead.
- **Mixer setters** — `setTrackVolume/setTrackMute/setTrackSolo/setTrackPan` call the arrangement's setter, which replaces the mixer Map and the one entry (no track object is written to or replaced), bumps `mixerVersion` and announces `'mixer'`; the engine's listener forwards the value to the adapter (`AdapterSync.sendMixerValues`) and emits `statechange` (#501) — NOT `tracksVersion` (these are not structural changes). A later adapter rebuild keeps the value because every track is sent through the projection. For a track that is not in the current tracks (never seen, or removed with its entry kept for an undo), nothing changes and no `statechange` is emitted, and the engine still calls the adapter's setter itself (`_mixerChanged` returned false; a consumer may target a track the engine hasn't ingested yet), unless the engine is disposed.
- **Clip operations use `updateTrack`, not `setTracks`** — `moveClip`, `trimClip`, `splitClip` announce `'update'`, and the engine's listener calls `AdapterSync.sendTrack(trackId)` (through `follow`) which uses `adapter.updateTrack()` when available, falling back to `adapter.setTracks()`. This rebuilds only the affected track's clips on the adapter — other tracks keep playing uninterrupted.
- **`addTrack()` uses incremental adapter path** — When `adapter.addTrack` is defined, `AdapterSync._addTrack` calls it instead of `adapter.setTracks()`. The `PlayoutAdapter.addTrack` method is optional (`addTrack?`) for backwards compatibility.
- **`updateTrack(trackId, track?)`** — Public method. With a `track` argument: replaces that track in the arrangement (an undo step; the track's mixer fields are not read; given a new id, the track keeps its mix, the adapter gets a full `setTracks` and a `selectedTrackId` naming the old id is cleared), which reaches the adapter and emits statechange; an id no track has does nothing (no undo step, no adapter call, no statechange), though the track is still checked first and a track of the wrong kind throws. Without one: sends the arrangement's current track (with the current mix) to the adapter again (`AdapterSync.sendTrack`), with no change of state and no statechange; a disposed engine does nothing. Used by external callers (e.g., dawcore `addRecordedClip`).
