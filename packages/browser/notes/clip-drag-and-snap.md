# Clip drag, trim and snapping

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before changing `useClipDragHandlers`, `ClipInteractionProvider`, a dnd-kit handler or modifier, or snap-to-grid.

## Trim/Move Asymmetry in useClipDragHandlers

Both end in ONE call on the provider's arrangement (`useArrangement()`), made on release: a move is `arrangement.moveClip(trackId, clipId, delta)` on drop, a trim `arrangement.trimClip(trackId, clipId, boundary, delta)`. Neither opens a transaction; one call is one undo step. The engine and the view follow the arrangement, so both work whether an engine is attached or not, and the hook throws outside `WaveformPlaylistProvider`. They differ in what the user sees meanwhile.

**Move:** `onDragStart` notes the clip and its track by id (`MoveDrag`); nothing else is computed until the drop. The Feedback plugin draws the dragged clip and the collision modifier constrains the visual position per frame with the engine's pure `constrainClipDrag` function. The drop moves the clip and track picked up at drag start, also when the tracks were reordered or the row's clips changed meanwhile (a clip arriving earlier in the row shifts every later position; `clipDragAcrossArrival.test.tsx`); the drop's own data is used only when the drag start was not seen. A move whose track is gone, or whose clip is not a loaded clip of that track, is dropped with a console warning. A cancelled move needs nothing: the plugin puts the clip back and nothing was told.

**Trim (#812): a view-only preview.** `onDragStart` finds the track at the row's index in `arrangement.getTracks()`, the clip by id among its loaded clips (`loadedClipsOf`), and records its bounds (`TrimDrag`: ids, boundary, `startSample`, `durationSamples`, `offsetSamples`). Each `onDragMove` computes the delta from those bounds (never from the previous move): `calculateBoundaryTrim`, then the boundary's absolute position snapped, then `arrangement.constrainTrimDelta` (a query; the clip has not been changed during the drag, so it constrains from the same bounds the release will use). The result is published as a `TrimPreview` (`trackId`, `clipId`, `startSample`, `durationSamples`, `offsetSamples`) to the provider's `TrimPreviewContext`. The arrangement is not changed. `lastBoundaryDeltaRef` holds the delta of the last preview, which is what the release sends, so the preview shows what the release commits.

**Who follows the preview.** Only the dragged clip's `ClipView` (`usePreviewedClipPeaks` in `hooks/useTrimPreviewView.ts`, a `useSyncExternalStore` whose snapshot is `null` unless the preview names that clip) and the root (`useTrimPreviewExtent`, for the width). The previewed clip's drawing record comes from `TrimPreviewPeaksContext.peaksFor`, which runs the same per-clip step as `derivePeaks` (`clipPeaksFor`) over the latest tracks, so the waveform is the slice for the previewed offset. The two contexts are INTERNAL (not exported from the package or `/tone`), blocked under the MediaElement provider; `useTrimPreviewOptional()` and `useTrimPreviewPeaksOptional()` turn blocked or absent into "no preview" because the clip rows are shared by both providers. The preview is not public until a use case needs it (maintainer's decision).

**The spectrogram follows the preview.** `ClipView` passes the drawn record's `offsetSamples` / `durationSamples` to `SmartChannel` (`spectrogramOffsetSamples` / `spectrogramDurationSamples`), `SpectrogramChannel` registers each canvas with them and keys its canvases on them, and `SpectrogramProvider` draws each clip for the range its canvases registered with. So a move mounts and registers new canvases for the dragged clip only (as the length change did when a trim changed `tracks` per move) and the provider renders them; the release registers nothing, because the committed clip has the range the canvases were drawn for; Escape and an undo of a trim register the committed range again. A clip move changes neither field (the picture is drawn in clip coordinates), so its canvases register again only when the drawn width changes, as before. Tests: `trimPreviewSpectrogram.test.tsx`, ui-components' `SpectrogramChannelRange.test.tsx`, spectrogram's `registeredRange.test.tsx`.

**Width past the end.** While the previewed end is past `duration`, the root's `displayDuration` is that end rounded UP to the next 10 seconds (`TRIM_EXTENT_STEP_SECONDS`, the recording layout's `RECORDING_EXTENT_STEP_SECONDS`), so the root renders once per step and not per move; after the release the width is the exact new duration. `useTrimPreviewExtent` returns the stepped number as its snapshot for that reason.

**Release.** `commitTrim` calls `arrangement.trimClip()` and then clears the preview, as two plain calls with no `flushSync`. dnd-kit calls `onDragMove` and `onDragEnd` inside `startTransition`, but the view reads both the arrangement and the preview with `useSyncExternalStore`, whose updates React applies at once and together, even inside a transition; so no frame shows the clip where it was before the drag (the release test in `trimPreview.test.tsx`). Until the provider moved onto the arrangement, the trim reached the app's `tracks` state through `onTracksChange` as a transition update and the two calls needed a `flushSync` around them; do not put it back. (The track-reorder drop in `ClipInteractionProvider` still uses `flushSync`: there two React state updates, the cleared preview and the epoch, must commit with the arrangement's reorder.)

**Cancel.** `event.canceled` (Escape, focus loss, unmount) clears the preview and changes nothing: there is no state to revert, because none was changed. A drag that never ends (the component unmounts mid-drag) clears its preview in an effect cleanup, only when a trim is in progress. Same shape in `useAnnotationDragHandlers` (`annotationPreview`).

**No engine attached** (before the first build, or while an engine is being rebuilt): a trim, a move or a split made then is applied to the arrangement and the next engine plays it (`trimPreview.test.tsx`, "release while no engine is attached commits the trim to the arrangement and clears the preview"; `providerOnArrangement.test.tsx`, "edits and undo work while no engine is attached…"). In the intermediate state of #812 (the trim preview on the provider that still took `tracks`), such an edit was dropped with a console warning.

**Clips are found by id.** The drag data keeps `clipId`, `trackIndex` and `clipIndex`. The handlers read `trackIndex` once, at drag start, to find the track in `arrangement.getTracks()`, and from then on use the track id and the clip id; `ClipCollisionModifier` finds the clip with `tracks[trackIndex].clips.find((c) => c.id === clipId)` over the provider's loaded tracks. `clipIndex` is not read: it is a position in the drawn row, which can hold placeholders that are not in `track.clips`. A clip still loading is not among `loadedClipsOf(track)`, so it cannot be trimmed, moved or split. `useClipSplitting().splitClipAt(trackId, clipId, splitTime)` is by id too and makes one `arrangement.splitClip()`.

**Why not `trimClip()` per frame:** the arrangement's methods apply deltas to the current state, and the handler computes each move from the bounds at drag start; per-frame calls would compound them (and each would be a change of the tracks and an undo step).

**No flag makes the provider ignore the tracks during a drag.** Until #812 `useEngineRefs().isDraggingRef` made the provider's loading effect skip `tracks` changes while a trim was dragged; that was a second owner of the tracks (see "One Owner per Piece of State"). The ref and the loading effect are both gone: the provider derives what it shows from the arrangement at every change, and a change during a trim (an undo, audio arriving, a recording) is an ordinary one. Do not reintroduce such a flag.

**Render scope** (a browser probe counted 22 components per move with one trigger root, `ClipView`, on `/examples/multi-clip`: measured in a probe run on 2026-11-14, not a test in the repository). Tests that pin it: `trimPreview.test.tsx` ("a move renders the dragged clip's view and no other clip, row or the root"), `visualizationMemoBoundaries.test.tsx`, `contextSplitByChangeRate.test.tsx`.

**Undo is inert during a clip drag (#848).** `onDragStart` of a clip source marks the provider's drag guard (`providerInternals/dragGuard.ts`, read through the internal `DragGuardContext` with `useDragGuardOptional()`), and `onDragEnd` ends the mark, as does an effect cleanup when the hook's component unmounts mid-drag (no dragend comes then). `useArrangementEditing`'s `undo` / `redo` return while the guard is active. The guard is a counter, not React state: nothing re-renders when a drag starts, and `canUndo` / `canRedo` do not change. Escape needs nothing here: dnd-kit's pointer sensor cancels the drag and calls `preventDefault()` on the key (bound on the event target and `document.body`, before `useKeyboardShortcuts`' `window` listener), and core's `handleKeyboardEvent` skips an Escape whose default was prevented, so Stop and the annotation deselect do not also run. `arrangement.undo()` called directly is not guarded (#848's design, PR 3: an outside change during a drag cancels it). Tests: `undoDuringDrag.test.tsx`, `dragGuard.test.ts`, `e2e/drag-undo-escape.spec.ts`.

## Stable Drag Handlers and Modifiers (#694)

Anything keyed on `tracks` is rebuilt by every clip operation, also one that lands mid-drag (an undo, a recording, audio arriving for a clip), and a rebuilt handler or modifiers array is handed to `DragDropProvider` anew. (Until #812 a trim also changed `tracks` on every pointer move; it no longer does.) Three things are therefore read when they are needed, not captured:

- `useClipDragHandlers` takes no `tracks`: it reads `arrangement.getTracks()` when a handler runs. `onDragStart` never changes, `onDragMove` changes identity only with `samplesPerPixel`/`sampleRate` and `onDragEnd` only with `samplesPerPixel` (all three also depend on the arrangement and the preview, which are fixed for a mount). A trim's `onDragMove` finds the track by the id captured at drag start, not by `data.trackIndex`, so a reorder mid-drag does not lose it.
- `ClipInteractionProvider` passes `ClipCollisionModifier.configure({ tracks: getTracks, … })` with a stable getter over the provider's loaded tracks (`usePlaylistTimeline().tracks`, read through a ref) (the option accepts `readonly ClipTrack[] | (() => readonly ClipTrack[])`), so the `modifiers` array handed to `DragDropProvider` is not rebuilt mid-drag.
- Clip order: `sortedClipsOf(clips)` (`src/utils/sortedClips.ts`) caches the sorted copy per clips array in a `WeakMap`; during a move the array is not replaced, so `ClipCollisionModifier.apply` sorts once. A trim no longer replaces the array per move, and `onDragStart` records the trimmed clip's `sortedClips`/`sortedIndex` once in `trimOrderRef`; only the neighbours are read from it (`constrainBoundaryTrim`). Each move checks, by identity, that every other clip of the track is still the one the order was computed from, and recomputes if not (an undo during the trim, a recording landing on the track, audio arriving for another clip of it).

`useKeyboardShortcuts` likewise keeps the latest `shortcuts` in a ref and subscribes to `keydown` once per `enabled` value; callers build the array inline. Guarded by `stableDragHandlers.test.tsx`, which mocks `@dnd-kit/react`'s `DragDropProvider` to capture the props it is given.

## Clip Interaction Options Have One Source (#690)

Whether clips can be dragged and trimmed (`enabled`) and whether their trim handles are widened for touch (`touchOptimized`) come from ONE place: `ClipInteractionContext` (`contexts/ClipInteractionContext.tsx`), read by `ClipView` for what a clip does, and by `ClipInteractionProvider` only to inherit `touchOptimized` (below). `ClipInteractionOptions` (exported) is the only component that provides it; `ClipInteractionProvider` renders `<ClipInteractionOptions enabled touchOptimized={…}>` around its `DragDropProvider`. The view's compositions and parts take neither as a prop, and neither is threaded through `TrackRows` / `TrackRow`.

- A prop left out of `ClipInteractionOptions` is inherited from the one above (`??`, not `||`), so it nests: `<ClipInteractionOptions touchOptimized={false}>` inside a touch-optimized provider keeps 8px handles and stays interactive, and `enabled={false}` switches interaction off for part of the tree.
- `ClipInteractionProvider` resolves its own `touchOptimized` the same way (`prop ?? inherited`) and uses that one value for `useDragSensors` and for the `ClipInteractionOptions` it renders, so sensors and handle width cannot disagree and a provider inside `<ClipInteractionOptions touchOptimized>` inherits it.
- The value is memoized on its two booleans. `ClipInteractionProvider` renders on every change of `tracks` (every clip operation); an unmemoized value would re-render every clip each time.
- History, so it is not repeated: a first version (#773, reverted by #774) kept the two `<Waveform>` props and combined them with the context using `||`. Two sources meant no prop could switch off what the provider turned on, and `<PlaylistVisualization>` changed behaviour under the provider without anyone having decided it. The maintainer's rule for these components (2026-11-11): no doubled sources; a small context with a value that rarely changes, read where it is used, instead of props passed down through components that do not use them.
- A view option that every clip needs and that never changes per frame belongs in a context like this one. `samplesPerPixel` and `sampleRate` are still props of `ClipView`: they were kept as props while the data context that held them changed on every trim move. Since #768 they are in the view and zoom values, which do not, so `ClipView` could read them itself (not done; #685 reshapes these components).

Tests: `clipInteractionOptions.test.tsx` (it mocks `useDragSensors` to record the options the provider passes). `e2e/mobile-multi-clip.spec.ts` checks the 24px handles on a page that sets only the provider flag. `/examples/custom-drag-setup` (`CustomDragSetupExample.tsx`) is the custom path for real: its own `DragDropProvider` plus `ClipInteractionOptions`, with a checkbox per option; `e2e/custom-drag-setup.spec.ts` drags and trims there by exact pixel distances, switches interaction off and on, and checks the handle widths. In that spec a clip is dragged by pressing 8px below the top of its `[data-clip-container]` (the header strip), which works whether or not the header is a draggable; clip positions are whole pixels, so compare within 1px of the computed value.

## SnapToGridModifier (Beats & Bars)

**Location:** `src/modifiers/SnapToGridModifier.ts`

**Two modes via discriminated union:**

- `mode: 'beats'` — Quantizes in PPQN tick space (bar or beat grid). Uses `samplesToTicks` → `snapToGrid` → `ticksToSamples` round-trip.
- `mode: 'timescale'` — Quantizes by `gridSamples` (consumer typically derives this from `getScaleInfo(samplesPerPixel).smallStep * sampleRate / 1000`).

**Boundary trims:** Modifier skips trims (returns `transform` unchanged). Trim snapping is handled in `useClipDragHandlers` via optional `snapSamplePosition` callback.

**Consumer pattern:** Example conditionally includes modifier in array (exclude entirely when snap is off) rather than relying solely on the modifier's internal `snapTo === 'off'` guard.

## Snap-to-Grid: Absolute Position, Not Delta

**Decision:** Snap the clip's absolute timeline position to the grid, not the drag delta.

**Why:** Delta-snapping preserves off-grid offsets permanently — if a clip starts off-grid (from collision, initial placement, or trimming), snapping the delta to grid-sized increments keeps it at the same offset from every grid line.

**Move snapping (SnapToGridModifier):** Reads `startSample` from `source.data`, computes `proposedPosition = startSample + delta`, snaps that to grid, derives delta as `(snappedPosition - startSample) / samplesPerPixel`.

**Trim snapping (useClipDragHandlers):** Optional `snapSamplePosition` callback. After `calculateBoundaryTrim`, snaps the boundary's absolute position (left → snap `startSample`, right → snap end position). Stored in ref to avoid dependency churn. `lastBoundaryDeltaRef` uses the effective (snapped, then constrained) delta so `arrangement.trimClip()` gets the correct value.

**Draggable data:** `Clip.tsx` includes `startSample` and `durationSamples` in all draggable `data` objects (clip move + both boundary handles) so modifiers can compute absolute positions.
