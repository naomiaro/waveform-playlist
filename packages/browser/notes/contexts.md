# Contexts and render boundaries

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before adding a field to a context, reading a context in a component, changing a hook in `contexts/playlistContexts.ts`, or changing a memo boundary in the visualization.

## Memo Boundaries in the Visualization (#693)

`WaveformRoot` is the shell (`Waveform` / `WaveformEditor`, or the consumer, compose it with its parts, see "The View Is a Root With Parts"): sizes, the shared vertical layout, the selection-drag pointer handlers and `PlaylistInfoContext` (the last two through `useWaveformFrame`, shared with `MediaElementWaveformRoot` since #685 part 2). It does not subscribe to the selection (#733), the resting cursor position, the active annotation (#740, both in the sections below) or the selected track (#685: the tracks part and the controls part read that), so it renders when playback starts or stops, on its own state (a drag in progress, the settings modal, the measured container width), on timeline, zoom, view, theme and spectrogram-integration changes, on a reorder drag-over, on a recording layout step, and whenever the component that composes it renders. What it renders is split so that this is cheap:

- `WaveformTracks` → `TrackRow` → `ClipView` (`components/TrackRows.tsx`) and `WaveformTrackControls` → `TrackControlsSlot` → the panel template (`components/TrackControlsColumn.tsx`; since #687 the panel is the part's children, `<DefaultTrackControls />` by default, see "Track Controls Are Pieces Bound to a Track"). `TrackRow`, `ClipView`, `WaveformTrackControls`, `TrackControlsSlot` and `DefaultTrackControls` are `React.memo` (`DefaultTrackControls` takes only `children` and reads no context; the pieces inside it read the track); `WaveformTracks` is not (it has children). None reads selection, cursor or annotation state. What a row or a clip is handed is primitives, stable callbacks, and the identity-stable pieces of `peaksDataArray` from `derivePeaks` (#692).
- `WaveformSelection`, `WaveformPlayhead`, `WaveformAnnotationBoxes`, `WaveformLoopRegion` (`components/VisualizationOverlays.tsx`) read that state from context themselves.
- In `ChannelWithProgress`, only the inner `ClipProgress` overlay subscribes to the provider's contexts (`useIsPlaying`, `usePlaybackRefs`, `useCurrentTime`, `usePlaylistView`, `usePlaylistZoom`). The channel itself must not: `ClipProgress` calls `useCurrentTime()` (so it renders per move of a leftward selection drag).

Rules when changing these files:

1. Everything in the root's two layout values (`components/waveformLayoutContext.ts`) and everything the tracks part hands a row must keep its identity across a render that did not change it. `selectTrack` reads `tracks` through a ref for this reason; both layout values and the `PlaylistInfoContext` value are `useMemo`'d; track heights depend on the recording's track id and channel count, not on `recordingState` (a new object literal on every render of the consumer).
2. `recordingState` is passed down to the armed track's row only (`undefined` for the others). Since #695 it holds a `progress` source instead of per-frame values, so a recording frame re-renders the preview clip only, and `displayDuration` grows in 10-second steps (see "60 Hz Values Are Sources"): every row gets a new `width` once per step, not once per frame.
3. Pass track fields (`trackId`, render mode) rather than the `track` object: track objects are replaced by the arrangement whenever that track changes (an edit, an undo, audio arriving for one of its clips).
4. The panel of a track is the controls part's children, rendered once per track inside a memoized slot (#687; `renderTrackControls`, `onRemoveTrack` and `trackReordering` are removed). The part renders on the root's rows value (tracks, peaks, layout), mixer state, the selected track, a reorder, the spectrogram integration and its own props; a slot renders only when one of its primitive props or the template changed; a piece renders when its track's context value changed. The template is compared with the previous one (`useStableTemplate`), so inline children do not render the panels; a prop of a child with a new identity per consumer render (an inline `onRemove`) does render every panel, as an unstable `onRemoveTrack` did.

`visualizationMemoBoundaries.test.tsx` counts renders with wrappers around the real `Clip`, `SmartChannel`, `Track`, `Controls` and `SmartScale`. `SmartChannel` is the proxy for `ChannelWithProgress` renders including context-triggered ones. Measured on `/examples/multi-clip` (7 tracks, 13 clips): about 440 component renders per pointer move of a selection drag before, 31 (dragging right) and 63 (dragging left) after.

## Selection Has Its Own Context (#733)

`selectionStart` / `selectionEnd` live in `SelectionContext` (`useSelection()`), not in `PlaylistStateContext` (which #768 has since split into several). They are the only state that changes on every pointer move of a selection drag; in the state value they re-rendered every `usePlaylistState()` consumer per move (annotation list, annotation boxes, loop button, a consumer's own app component).

- Call `useSelection()` only in a component that shows or uses the selection: `WaveformSelection`, `WaveformPlayhead`, `SelectionTimeInputs`, `SetLoopRegionButton`, and `usePlayFromSelectionOrCursor` (so `PlayButton` and `KeyboardShortcuts` render per move; measured about 0.04 ms together, dev build).
- The provider itself still renders per move (selection is its React state); its `children` are stable, so only context consumers follow.
- The drag (`useSelectionDrag`) takes the anchor from `pressTimeRef` (set at mouse-down), never from `selectionStart`. `selectionStart` is `min(anchor, pointer)`, so it stops being the anchor once the pointer passes left of it: until #733 a leftward drag selected only the last pointer movement.
- `MediaElementPlaylistProvider` renders the same `SelectionContext` (#688, part 2), so `useSelection()` works under it; its view uses the same hook, which stores the range ordered (#688). Both views render the same `WaveformSelection` (part 3).
- `setSelection` also sets `currentTime`, so a LEFTWARD drag changes the resting cursor position per move; that has its own context since #740 (next section).

Measured per move of a rightward drag (dev build, `probes/select733.cjs`, which adds render time to the fiber-walk count): multi-clip 31 components to 9; annotations example (15 annotations) 369 to 17, React render at 4x CPU throttle 19.8 ms to 1.5 ms. Leftward: multi-clip 63 to 54, annotations 371 to 370. Guarded by `contextValueStability.test.tsx` (identities and render counts) and the drag-direction tests in `e2e/multi-clip.spec.ts`.

## Resting Cursor Position and Active Annotation Have Their Own Contexts (#740)

`currentTime` lives in `CurrentTimeContext` (`useCurrentTime()`), not in `PlaybackAnimationContext`. `activeAnnotationId` lives in `ActiveAnnotationContext` (`useActiveAnnotation()`), not in `PlaylistStateContext`. (Both of those larger contexts were split further in #768, next section.)

- `currentTime` is the RESTING position (seek, pause, stop, a selection whose start moves). It does not advance during playback; `currentTimeRef` and frame callbacks do that. The animation value now changes only when `isPlaying` does.
- A context subscription is to the whole value. Before the split, a component that read only `currentTimeRef` or `isPlaying` still rendered on every seek; changing the annotations example to read the ref alone did not change its render count at all. That is why the fix had to be in the provider and not in consumers.
- `ClipProgress`, `AnimatedPlayhead`, `CustomPlayhead` and `AudioPosition` call `useCurrentTime()` for the re-render only. They position from `visualTimeRef` / `currentTimeRef` in an effect without dependencies, so without the call they would not move on a seek while stopped. Any new component that shows the resting position needs the same call (tests: "still follows a seek while stopped" in `visualizationMemoBoundaries.test.tsx`).
- `useActiveAnnotation()` is called by `WaveformAnnotationBoxes`, `AnnotationList` and `KeyboardShortcuts` only (the first two under either provider since #686).
- Both annotation renderers memoize their items, so an active-annotation change renders the item that stops being active and the one that becomes active, not all of them: `AnnotationBoxItem` in `components/AnnotationBoxes.tsx`, and `AnnotationListItem` inside `AnnotationText` (annotations package). The functions and objects handed to an item must keep their identity when only the active annotation changes: the box click handler is a `useCallback`, the list's edit/control handlers are `useCallback`s over `annotations`, and `AnnotationList` memoizes the `annotationListConfig` it passes (since #686 `AnnotationText` also reads it through a ref, so a new one renders no row). Tests: `annotationBoxesMemo.test.tsx`, `playlistAnnotationListMemo.test.tsx`, `mediaElementAnnotationsMemo.test.tsx` (browser), `annotationTextItems.test.tsx` (annotations).
- `MediaElementPlaylistProvider` renders the same `CurrentTimeContext` and `ActiveAnnotationContext` since #688, part 2 (see "One Set of Context Objects for Both Providers").

Measured (dev build, 4x CPU throttle, `probes/select740.cjs`, which charges each rendered component to the nearest rendered ancestor whose parent did not render):

- Leftward selection drag, per move: annotations example 370 components / 21 to 24 ms React render before, 21 / 1.8 ms after; multi-clip 54 / 3.5 ms before, 37 / 2.3 ms after (26 of the 37 are the 13 `ClipProgress` and their styled child).
- Active-annotation change during playback, per boundary: annotations example (15 annotations) 369 components / 23 to 27 ms before; 265 / 16 to 22 ms with the context split alone (the list, 168, and the boxes, 94, re-rendered every item); 48 / 5.3 to 6.8 ms with the items memoized.

The three internal contexts of #812 (none exported from the package or `/tone`; `MediaElementPlaylistProvider` blocks all three, and `ArrangementContext` with them):

- `TrimPreviewContext` holds the trim preview source (a `TrimPreviewHandle`, the `ValueSourceHandle` made once by `providerInternals/useTrimPreview.ts`; the drag handlers write it, and only the dragged clip's `ClipView` and the root, for the width, subscribe to it) and `TrimPreviewPeaksContext` the stable `peaksFor(preview)` that draws the previewed clip from the provider's latest tracks. Both values keep their identity for the life of the provider, so a trim renders no context reader; the timeline and mixer values do not change per move. The shared clip rows read them through `useTrimPreviewOptional()` / `useTrimPreviewPeaksOptional()`, where blocked or absent means "no preview". The mechanism is in "Trim/Move Asymmetry in useClipDragHandlers" (`clip-drag-and-snap.md`).
- `RecordingArmContext` holds `{ armedTrackId }`, the track a take is recorded onto (`useRecordingArm()`, internal). It changes when a take starts or ends and when the armed track changes. `WaveformTrackControls` is its reader and hands each slot the boolean `isRecordingArmed`, so only the armed track's slot follows; a consumer reads `useTrack().isRecordingArmed`. See "End-of-Timeline Semantics" (`playback-and-engine.md`).

`ArrangementContext` is the provider's `arrangement` prop itself. Reading it never re-renders; a component that draws tracks subscribes with `useArrangementTracks(arrangement)` (loading clips included, no render on a mix change) or reads `usePlaylistTimeline()` (loaded clips, peaks). `useClipDragHandlers` and `useClipSplitting` read it with `useArrangement()` and change tracks through it.

`contextValueStability.test.tsx` pins the identities and that `useEngineRefs()` has no `isDraggingRef`; `contextSplitByChangeRate.test.tsx` the per-action render sets.

Rules:

- A new field goes into the value whose other fields change when it does, never into the nearest one. A field that changes on its own gets its own context. Add the field to the "has exactly the documented fields" case in `contextSplitByChangeRate.test.tsx`, which also states, per action, exactly which hooks' readers render; that file is the contract.
- `timeFormat` and `isAutomaticScroll` have their own value (`usePlaylistSettings()`) for that reason. The first version of #768 put them in the view value to save a context; toggling automatic scroll on `/examples/multi-clip` then rendered 58 components where it had rendered 32 before the split, because every `ClipProgress` and the shell read the view value for `sampleRate`. Measure the action a field changes on before choosing its group, on a page with many clips.
- The old hooks were removed, not slimmed. A hook kept under its old name with fewer fields hands `undefined` to a plain-JS consumer with no error; a missing export throws at the first render. The one exception is `usePlaybackRefs()` (#688, part 2), which kept its name and lost eight fields; a leftover read of one is `undefined` (the maintainer had the throwing getters removed in part 3), see "One Set of Context Objects for Both Providers". Do not add a hook that merges several of these values "for convenience": it would re-render for all of them, and it would be a second source for the same fields.
- `usePlaylistViewOptional()` / `usePlaylistZoomOptional()` (exported from the context file, NOT from the package) return `null` where no provider is above; only `useAnnotationKeyboardControls` uses them, because it may also be called outside a provider with explicit options. Both providers render the two contexts, so under either one they return the value.
- Who reads the hot values: `usePlaylistTimeline()` is read by the view's root (and by no part of the view: they take `rows` and the peaks from the root's rows value), `ClipInteractionProvider`, `KeyboardShortcuts`, `SpectrogramProvider`, `ExportWavButton` and `LoopButton` (it reads `duration` for its click handler). `FastForwardButton` and `SkipForwardButton` no longer read it (#688, part 2: they call `seekTo`, which clamps). `usePlaylistMixer()` is read by the controls part (`WaveformTrackControls`; not by the root above it, so a slider step renders the column, the one slot whose props changed and the pieces of that track that call `useTrack()`), `MasterVolumeControl` and `ExportWavButton`. No piece and no panel reads `usePlaylistMixer()`: a piece that did would render on every track's changes. `trackStates` is derived during render from the arrangement's tracks and its mixer (`deriveTrackStates` in `providerInternals/useArrangementView.ts`) and keeps its identity while no entry changed, so a clip edit that changes no mixer field and no name leaves the mixer value as it was (`arrangementView.test.tsx`; and since #812 a move of a trim does not change `tracks` at all).
- A queued play shows later than it did: `play()` during an engine rebuild sets the time refs without setting `currentTime` state (the two `setCurrentTimeRefs` calls in `play()` are the only ones not paired with `setCurrentTime`). Before #768 the playhead, `ClipProgress` and `AudioPosition` jumped to the queued start when the rebuild finished, only because they read the data value and it changed then; now they move when `isPlaying` turns true (and stay put if the queued play never starts because the build failed). Found by reading in review, not reproduced in a browser; the maintainer was told. Do not "fix" it by adding a timeline subscription to those three components.
- `renderPlayhead` is called when `WaveformPlayhead` renders, on what it reads (play state, the selection, zoom, view settings, the theme) and whenever the component that composes the view renders (it gets a new element then; it is not memoized), and on a change of the resting cursor (a seek): the `CustomPlayhead` wrapper around the function reads `useCurrentTime()` and `useIsPlaying()` itself. It is not called at all while a range is highlighted at rest. Until #685 it was also called on every render of the shell, so on every timeline change, track selection and reorder drag-over even when the composing component stood still; on the example pages that component holds the tracks and renders with them anyway. A first draft of the #768 upgrade guide claimed more than was true and review caught it: read the parent's subscriptions before writing when a render prop is called.
- `Waveform` reads no context and takes `className` only (#686). `AnnotationList` returns nothing itself when there are no annotations, so the `AnnotationListWhenPresent` child of #744 is gone. Nothing counts `Waveform`'s own renders in a unit test.
- `PlaylistInfoContext` (ui-components) has no `duration`: every `Track`, `SmartChannel` and `ChannelWithProgress` reads that context, and the displayed length changes when a clip operation moves the end of the timeline, and in 10-second steps while a trim is dragged past it. `SmartScale` takes `durationMs` as a prop; the memoized `WaveformTimescale` reads `displayDuration` from the root's extent value.
- The MediaElement provider renders the shared context objects since #688, part 2; its four public hooks (`useMediaElementAnimation/State/Controls/Data`) and its two internal contexts are gone. See "One Set of Context Objects for Both Providers".
- The provider nests the contexts with the least-changing outermost. The order has no effect on behaviour.

Measuring: `probes/split768.cjs <port> <route> [throttle]` performs single actions (volume, pan, mute, master volume, loop, checkboxes, time format, reorder button, track selection, zoom, play/stop) and reports components rendered per action with the trigger roots; `probes/trim767.cjs` does the same for a trim. `probes/codemod768.cjs <files>` rewrites `const { … } = usePlaylistData()` style destructurings to the new hooks (it mangles an import list that has a comment inside it: check the diff).
