# MIDI clip rendering

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before changing how a MIDI clip is drawn.

## MIDI Clip Rendering Pipeline

**Problem:** MIDI clips have no `audioBuffer` or `waveformData`, so Path C in peak generation gave them `length: 0`, rendering as invisible zero-width clips.

**Fix:** In Path C, detect `clip.midiNotes` and compute `pixelLength = Math.ceil(clip.durationSamples / samplesPerPixel)`.

**Data threading:** `ClipPeaks` includes `midiNotes`, `sampleRate`, `offsetSamples` which flow through `WaveformTracks` → `ChannelWithProgress` → `SmartChannel` → `PianoRollChannel`.

**A piano roll comes from the track kind, not from a render mode (#756, #763).** `RenderMode` is `'waveform' | 'spectrogram' | 'both'` and applies to audio tracks: `trackRenderMode(track, override)` (`src/utils/trackRenderMode.ts`) gives the override, else the track's `renderMode`, else `'waveform'`, and always `'waveform'` for a MIDI track so that nothing starts a spectrogram for it. What makes a piano roll: `TrackRow` gets `kind` (row background, `data-track-kind`), and `ChannelWithProgress` and `SmartChannel` treat a clip whose `midiNotes` is not null as a MIDI clip (piano roll, no progress overlay). `TrackMenuButton` draws nothing for a MIDI track (`useTrack().hasSpectrogram` is false for it): the menu holds only render-mode choices and spectrogram settings. The engine guarantees the two agree (a MIDI track holds only clips with notes). The press handler (`handleMouseDown`) finds the row under the pointer with `trackIdAtOffset` over `trackLayout`, the layout the rows are positioned with, and does no height arithmetic of its own: its old loop counted a `'both'` track twice as tall as it is drawn, so a press on any row below one selected the row above (#762). The selected row carries `data-selected="true"` (`clickSelectsRowUnderPointer.test.tsx`, `e2e/track-selection.spec.ts`). Do not bring `'piano-roll'` back as a mode value.

**Styling a track row from outside:** an `outline` or `background` on `[data-track-row]` does not show: the row's children (`position: relative` with their own background, clips at `z-index: 10`) paint over it. The row must not get a `z-index`, `transform` or `filter` (a stacking context there breaks clip interactions). Draw on `[data-track-row]::after` with `position: absolute; inset: 0; pointer-events: none` and a `z-index` above 100 (the playhead). The Track Management guide carries this example.

**What selects a track:** a press on the click overlay (row under the pointer), a press on a clip unless it starts on a draggable header or trim handle, and a click anywhere in a track's slot of the controls column, whatever panel is drawn there (#687: the click handler is on the slot, it was on the default panel), except on the remove button, the menu button and the reorder grip and buttons (they stop propagation). A render-mode radio in the track menu DOES select: the dropdown is a portal and React bubbles its click to the slot (written for the default panel before #687; not re-checked in a browser for the slot).

**A track the arrangement refuses throws at the call that offered it (#812).** The arrangement checks a track before it enters (`setTracks`, `addTrack`, `updateTrack(id, track)`: clips that do not match the track's kind, which includes a clip still loading on a MIDI track; a duplicate track id; two clips with one id) and throws before anything changes: see the engine notes. So `arrangement.addTrack(badTrack)` throws to the code that called it, with the playlist as it was (`trackKindProvider.test.tsx`: `onError` is not called, nothing reaches the adapter, the playlist stays ready), and a `useCreateArrangement` initializer that returns such a track throws out of the render, to the nearest error boundary. The provider's `onError` is for an engine or adapter that cannot be built, and for an `onReady` that throws. Until #812 the provider handed `tracks` to the engine inside a `try`/`catch` in its async load and reported a refused track through `onError`, leaving `isReady` false; none of that code exists now.
