# Annotations in the view

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before changing the annotation list, the annotation boxes, their edge drag or the annotation options.

## One Annotation List and One Row of Boxes for Both Players (#744)

- Since #686 there is one component of each for both providers: `AnnotationList` (it replaced `AnnotationListView`, `PlaylistAnnotationList` and `MediaElementAnnotationList`) and `WaveformAnnotationBoxes` (it replaced the MediaElement twin), which hands values to the internal `AnnotationBoxes` row. Neither knows which provider it is under: they read shared hooks only. Change annotation list or box behaviour there, once.
- `MediaElementWaveform` and `MediaElementWaveformRoot` must not call `useActiveAnnotation()` (it changes at every annotation boundary) or `useAnnotations()`. `WaveformAnnotationBoxes` is the one part of a view that does (annotations, active annotation, the boundary-drag handlers and their `DragDropProvider`); the list does too, outside the root.
- This is why `activeAnnotationId` was NOT moved to its own MediaElement context: moving the subscription down into the leaf that uses the value gave the gain with no API change. Before splitting a context (breaking), check whether the consumers that render too much can stop subscribing instead; a split is needed only when a consumer needs one field of the value and must not follow another (#740).
- Testing a wrapper: record the props it hands to a fake `AnnotationText` and assert that the union of keys that differ after an active-annotation change is exactly `['activeAnnotationId']`. A real `MediaElementPlaylistProvider` mounts in jsdom with `createPlayout={() => fake}` and a `WaveformData.create({...})` track (`mediaElementAnnotationsMemo.test.tsx`).
- `useAnnotationDragHandlers` only turns pointer movement into a time and an edge; the boundary rules (linked endpoints, collisions, minimum duration) are core's `updateAnnotationBoundaries`, shared with dawcore. Do not reintroduce a local copy: the one deleted in #747 had the same bug as core's and would have kept it. With link endpoints on, a neighbour's edge within 10 ms is set to the dragged edge exactly.
- `useAnnotationDragHandlers` defaults `sampleRate` to 48000; every caller must pass the real rate (the MediaElement player did not, so a boundary on a 44100 Hz file moved about 8% less than the pointer; `e2e/media-element-annotations.spec.ts`).

Measured on `/examples/media-element-annotations` (15 annotations, dev build, `probes/select744.cjs … play`), per annotation boundary: 220 components / about 14 ms at 4x CPU throttle before; 81 / 8 ms with the shared memoized list and boxes; 45 / 4.5 ms with the annotation state out of the waveform shell.

## Annotation Edge Drag: Preview Source, One Report per Drag

Both providers create one `annotationPreview` (`ValueSourceHandle<AnnotationData[] | null>`, in the controls value, stable). `useAnnotationDragHandlers({ preview })` publishes each move to it and calls `onAnnotationsChange` once, on release; without `preview` it reports every move, as before. The components that draw annotations read `useAnnotationsWithPreview(annotations, annotationPreview)`: `WaveformAnnotationBoxes` and `AnnotationList` (four components until #686 merged the twins). Nothing else follows the preview: the engine, the animation loop's annotation lookup and `KeyboardShortcuts` see the committed annotations until release.

- Each move is applied to the RESULT OF THE PREVIOUS MOVE (the preview's snapshot, or the current `annotations` without one), not to the annotations at drag start. That is what lets an edge dragged into a separated neighbour pick it up and carry it along with Link endpoints on (#747, tried by hand by the maintainer); computing from the drag-start snapshot, as dawcore's `AnnotationDragHandler` does, loses that and failed `e2e/media-element-annotations.spec.ts`. The snapshot (`dragRef.current.snapshot`) is kept for Escape only: it is restored (no preview) or the preview is dropped (with one), so every annotation the drag moved goes back (maintainer's decision, 2026-11-11).
- The release commits and clears inside one `flushSync`. Cleared first, or committed in a later render than the clear, the boxes would show the old positions for a frame.
- The hook's handlers read `annotations` and `onAnnotationsChange` through refs, so they keep their identity for the whole drag.
- `AnnotationText` (annotations package) reads the list through a ref in its edit and control handlers. They are props of every memoized row; built from the array they re-rendered all rows whenever one annotation changed.
- Known edge: with a preview, the release commits the previewed array as a whole, so a change made to `annotations` by something else during the drag (a keyboard nudge, a text edit) is overwritten. Without a preview each move builds on the current `annotations` and such a change survives.
- Not covered by a unit test: the `flushSync` on release (two plain calls pass every test; a missing frame cannot be seen in jsdom).
- Since #686 the box part wires the drag under both providers and always uses the preview. A consumer calls the hook only for a row of boxes of their own.

Measured on `/examples/annotations` (15 annotations, dev build, 4x CPU throttle, `probes/close704.cjs … boundary`), per pointer move: 312 components / 18 ms React render before (all under the example's own root component, which holds the annotations); 47 / 4 ms after (the list shell and the boxes shell with the items that moved).

## Annotation Parts Own Their Options; the Options Are Provider State (#686)

Two components, the same under both providers: `WaveformAnnotationBoxes` (`components/WaveformAnnotationBoxes.tsx`; a part of either root; `getLabel`, `height`) and `AnnotationList` (`components/AnnotationList.tsx`; anywhere under a provider; `height`, `actions`, `scrollActivePosition` with `'none'`, `scrollActiveContainer`, a function child). `Waveform`, `WaveformEditor` and `MediaElementWaveform` take `className` only and hand the root module-level `<WaveformAnnotationBoxes />` and `<AnnotationList />` elements. Removed with no shim: the seven / eight annotation props of the compositions, `MediaElementAnnotationBoxes`, `PlaylistAnnotationList`, `MediaElementAnnotationList`, `AnnotationListView`, `annotationListConfig`, every `onAnnotationUpdate`, `useAnnotationEditing()`, `annotationList.controls`. The upgrade guide has the table.

- **One home for the three options: `useAnnotationOptions()` = `{ editable, linkEndpoints, continuousPlay }`**, state in `providerInternals/useAnnotationState.ts` for both providers, setters on `usePlaybackControls()`. `useAnnotations()` is `{ annotations }`. `continuousPlay` moved out of the annotations value so the toggle does not render readers of `annotations`; the cost is that an editable or link-endpoints toggle renders readers of `continuousPlay` too (they are `KeyboardShortcuts`, the box part, the list, and the three checkboxes of `@waveform-playlist/annotations`).
- **The options follow the `annotationList` prop (maintainer's choice B, 2026-11-13): `useFollowedOption`.** State plus "the last prop value seen", also state, compared DURING RENDER (no effect, so a StrictMode remount or a revealed `<Activity>` cannot put an unchanged prop back over a value the user chose). A field left out says `false`, so leaving it out and writing `false` are the same value. Between two changes of the prop a setter or checkbox wins; the prop is not told (there is no change callback), and its next change wins for the field that changed. `continuousPlayRef` is written during render as well as by the setter, so a value taken from the prop reaches the animation loop.
- **Nothing on the annotation path is a fixed value (maintainer's instruction).** Row height: `height` on the box part (`DEFAULT_ANNOTATION_BOXES_HEIGHT` 30). Box border: the theme's `annotationBoxBorder`, which had no reader before; its dark default was changed to `#ff9800` so the default themes draw what they drew (maintainer: keep the site's colours, apply them through the theme). The glow of the active box is that colour too (`AnnotationBox`'s `color` prop at 40% and 20% with `color-mix`; it was a fixed orange `rgba`). Active row and focus rings of the list: the new theme key `annotationTextItemActiveColor` (the tints are `color-mix(in srgb, <colour> N%, transparent)`). Scroll-to-active: `scrollActivePosition="none"`. Touch setting of the edge drag: `useClipInteraction().touchOptimized` (`ClipInteractionOptions`), the existing home, read by the box part. Left fixed on purpose and said so in the guide: the horizontal-axis modifier (an edge moves along time only), and the list's 200 px maximum when `height` is not given.
- **The box part owns its `DragDropProvider`, nested inside whatever is above.** dnd-kit registers a draggable with the nearest provider, so a `ClipInteractionProvider` or a consumer's own provider above never sees an annotation edge drag, and clip drags are untouched (prototype: both drags work side by side; a consumer's provider counted 0 annotation drag starts). Cost: one component per render of the part (`DragDropProvider`); the list lost one wrapper, so the annotations example measures the same.
- **An edge can be dragged as far as the timeline is drawn (the extent's `displayDuration`), under both roots (maintainer's choice, 2026-11-13).** Not the audio's length: annotations may mark what is not recorded yet (chords, a lyric sheet). A first version clamped to the audio; on an empty timeline that is 0 and a dragged edge collapsed (seen in the Storybook story: 328 px to 5 px after a 10 px move; a side agent reported it to the maintainer before I did). Under the MediaElement root the drawn timeline is the audio. `KeyboardShortcuts` still hands the boundary shortcuts the timeline's audio `duration`, so those stop at the end of the audio (stated in the upgrade guide).
- **A toggle renders no box and no row: click-time values are not props.** The click handler of every box and row is `usePlaybackControls().playAnnotation`, which never changes (next bullet); `AnnotationText` reads `annotationListConfig` through a ref in its action handler. Before that a Continuous Play toggle on the annotations example rendered every box and row (312 components, with the page component already out of the picture; 397 on `main`, where the page component rendered too); with it 27.
- **A click on a row plays the annotation** (`onAnnotationClick` in the integration props; the list never passed it before, so a row click, and the `onClick` given to a custom row, did nothing). In the default row `AnnotationText` ignores a click inside a `contenteditable="true"` field; the action buttons already stopped theirs.
- **`playAnnotation(annotation)` in the controls value: each provider plays an annotation its own way (maintainer's choice after review round 1: "I like all the behaviour on main better").** `WaveformPlaylistProvider`: `play(start, end - start)` with continuous play off (the audio ends on the sample), open-ended with it on. `MediaElementPlaylistProvider`: always `play(start)`, and the animation loop ends playback with the active annotation. The first build gave both the bounded call through a shared hook (`usePlayAnnotation`, deleted); under MediaElement that changed four things the reviewer traced: Continuous Play ticked during the play no longer let playback run on (the MediaElement provider has no counterpart of the WebAudio `reschedulePlayback` effect that drops the annotation's end), a last annotation at the end of the audio rested at its end with the highlight kept, an end moved later or an id edited during the play stopped at the old end, and a selection ending at the annotation's end turned the click into a selection play. "One part for both providers" does not mean one playback call: when the two providers reach the same result by different mechanisms, the part asks the provider. Tests: `mediaElementSharedLoop.test.tsx` (three `playAnnotation` cases), `annotationBoxesMemo.test.tsx` (the WebAudio arguments).
- **The list draws nothing without annotations, and nothing plus one `warnOnce` without the integration** (it threw: `<Waveform />` with annotations and no `<AnnotationProvider>` crashed). The boxes return null silently, as before. The three checkboxes and the download button are in `@waveform-playlist/annotations` since #770 (browser exports none of them, and the integration has no entry for them); they read the playlist provider and do not need `<AnnotationProvider>`.
- **Sensors:** the part passes `useDragSensors({ touchOptimized })` under both providers. The MediaElement boxes passed none (dnd-kit's defaults, which include a keyboard sensor). Checked in a browser before the change (`probes/kbd686.cjs`): keyboard dragging of a handle moved nothing on either page, so nothing was lost.
- **The annotation checkboxes generate their ids (`useId`)**; the classes `continuous-play` and `link-endpoints` are unchanged.

Measured (dev build, components per action, `main` to branch; `probes/track687.cjs`, `close704.cjs`, `select740.cjs`, `select744.cjs`, `media769.cjs`): annotations example: edge drag per move 47 to 47, annotation boundary 50 to 50, Continuous Play toggle 397 to 27, Link Endpoints 292 to 27, Editable 344.5 to 259.5 (every box and row changes), zoom 283.5 to 280.5; media-element-annotations: boundary 36 to 35, continuous-play toggle 22 to 26 (the three library checkboxes read the options; the page had one input of its own), Editable 233 to 221, play / pause / stop one fewer each. A prototype measured the row forms first: a function child at module level, the `renderAnnotationItem` prop and a template with a per-row hook cost the same per move and per boundary; a function written INLINE costs 2 components per row on every render of the composing component (zoom 316.5 against 284.5 with 15 rows), which is why the docs say to define it outside.

Tests: `annotationParts.test.tsx` (every case under both providers: the options, following the prop, the list, the boxes, the compositions and their leftover props), `annotationListOptions.test.tsx` in the annotations package (row click, theme colour, ids, the options ref), and the older memo files.
