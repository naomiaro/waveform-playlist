# The view: roots, parts and view options

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before changing `<Waveform />`, `<WaveformEditor />`, `<MediaElementWaveform />`, any `Waveform*` part, the playhead, progress overlay or selection highlight, or a view option.

## One Playhead, One Progress Overlay, One Selection Highlight (#688, part 3)

`AnimatedPlayhead`, `ChannelWithProgress` (with its inner `ClipProgress`), and `WaveformSelection` and `WaveformPlayhead` (with its `CustomPlayhead` wrapper) from `components/VisualizationOverlays.tsx` read shared hooks only. Both views render them (the `WaveformTracks` and the overlays are the same components under either provider since #685 part 2); `AnimatedMediaElementPlayhead.tsx`, `ChannelWithMediaElementProgress.tsx`, `CustomMediaElementPlayhead`, `MediaElementSelectionOverlay` and `ZERO_REF` are deleted. None of these was a public export. Change playhead, progress or selection-highlight behaviour in the shared component, once. `VisualizationOverlays.tsx` also holds the multitrack-only overlays (annotation boxes, loop region); it imports no provider and no engine (the context file, `AnimatedPlayhead`, `AnnotationBoxes`, `useAnnotationsWithPreview`, ui-components), so the MediaElement view importing it pulls in neither.

- **`PlayheadProps` (ui-components) is seven props**: `position`, `color`, `isPlaying`, `currentTimeRef`, `visualTimeRef` (required), `samplesPerPixel`, `sampleRate`. The four engine values and `controlsOffset` are removed; a playhead that needs an engine value calls `useEngineRefs()` (the render function runs inside `CustomPlayhead`, so it may call hooks). `CustomPlayhead` cannot read `useEngineRefs()` itself: it throws under the MediaElement provider. The props are a plain object (no throwing getters, see part 2's section). `PlayheadWithMarker` places itself from `visualTimeRef` and still runs its own animation loop.
- **`WaveformPlayhead` hides the resting playhead while a range is highlighted, under both providers** (maintainer's choice; the MediaElement view used to show it always). The playhead is unmounted then, so a custom playhead's state is lost, and it mounts again as playback starts: checked in Chromium (8 loads each of `/examples/media-element` and `/examples/multi-clip`, a range then Play) that the new element is at the range start by its first frame, not at x = 0. Tests that find another element through `[data-playhead]` must do so before selecting a range.
- **`AnimatedPlayhead` registers under `useId()`.** It used the fixed id `'playhead'`, so two visualizations under one `WaveformPlaylistProvider` replaced each other's callback and one playhead stood still.
- **The overlay is as wide as the clip under both providers** (`clipPixelWidth`, "Progress Overlay Width Invariant"). The MediaElement copy used the peaks length, one pixel wider than the clip on every example page.
- **`WaveformSelection` is `React.memo` and takes no props** (it reads the theme itself), so a shell render does not render it. `WaveformPlayhead` is not memoized. Under neither view does a render of the root reach `renderPlayhead` (#685: the multitrack view since step 1, the MediaElement view since step 2).
- **Colour fallback in `ChannelWithProgress`, for the BACKGROUND only:** `(isSelected && selected colour) || unselected colour || default`, for both draw modes. `SmartChannel` picks the canvas colours with its own expression and has no fallback (reachable only with a theme key set to `undefined` explicitly). The MediaElement copy had the fallback and the multitrack one did not; the MediaElement view's one row is always the selected one (`useSelectedRow()`).

Measured (dev build, `probes/media769.cjs`, components per action, `/examples/media-element` then the annotations page, before is `main` after part 2): rightward drag per move 7 to 8 (the `WaveformPlayhead`); leftward 13 to 12 and 11 to 10 (the hidden playhead does not render); play, pause or stop 40 to 41; click to seek 67 to 69 and 93 to 95 (the overlay wrapper, once per shell render). Multitrack (`probes/split768.cjs`): play-then-stop 110 to 108 on multi-clip and stem-tracks, 122 to 120 on annotations (the memoized highlight); otherwise identical. This step removes duplicate code; it was not expected to change counts.

Tests: `onePlayheadOneProgress.test.tsx` (props under both providers, the hidden resting playhead, two visualizations, the deleted files), `progressOverlay.test.tsx` (widths, colours, the frame callback), `mediaElementShellQuiet.test.tsx`, and ui-components' `PlayheadWithMarker.test.tsx`. A mutation run of 33 one-line changes left three survivors, all on lines older than this step and all the same fact: at rest `visualTimeRef` and `currentTimeRef` hold the same value under both providers (`setCurrentTimeRefs` writes them together), so "rest position from the raw ref only" in `AnimatedPlayhead` and `CustomPlayhead`, and "the rest effect also runs while playing" in `AnimatedPlayhead` (it would write the value the frame callback just wrote), change nothing a test can see. Untested lines, not proven equivalent.

## The View Is a Root With Parts (#685, step 1)

The view is `<WaveformRoot>` with one part per thing that is drawn, each option on the part it configures. Step 1 built this inside `PlaylistVisualization`, which kept its props; step 3 exported the parts and removed that component (see "The Parts Are Public").

| Part | File | Drawn in | Options |
| --- | --- | --- | --- |
| `WaveformTimescale` | `waveformParts.tsx` | timescale strip | `renderTick` |
| `WaveformLoopRegion` | `VisualizationOverlays.tsx` | timescale strip | none |
| `WaveformTrackControls` | `TrackControlsColumn.tsx` | controls column | `width`; children: the panel of one track (#687) |
| `WaveformTracks` | `TrackRows.tsx` | tracks area | `gainScaled`; children `WaveformClipHeaders`, `WaveformFades`, `WaveformRecordingPreview` |
| `WaveformAnnotationBoxes` | `WaveformAnnotationBoxes.tsx` (since #686; both roots) | tracks area | `getLabel`, `height` |
| `WaveformSelection`, `WaveformPlayhead` | `VisualizationOverlays.tsx` | tracks area | `renderPlayhead` on the playhead |

- **The root sorts its children by part type** (`sortWaveformParts`): the two timescale parts go to the timescale strip, the controls part to the controls column, everything else stays in the scrolling tracks area in order. Fragments are looked through. A part wrapped in another component is not recognised and lands in the tracks area. Every top-level child keeps one position in the tracks area (`null` when it is drawn elsewhere or switched off), so `{flag && <Part />}` does not remount the tracks-area parts after it. That does not hold inside a fragment whose number of children varies, and the controls column is a compact list, and so was the timescale strip until step 3 keyed its parts by kind (see "The Parts Are Public").
- **`WaveformClipHeaders`, `WaveformFades` and `WaveformRecordingPreview` are markers that render nothing.** The tracks part and the root both find them with `scanTracksParts`. The maintainer chose markers over children rendered inside every clip after a prototype on `/examples/multi-clip`: with real per-clip children written inline, a trim rendered 384 components per move against 94, because new children on every parent render re-rendered every clip (three `useDraggable` hooks each). The header is structural as well: it adds to the row height the root must know before anything is drawn, and in ui-components' `Clip` it is what switches the clip's dragging and trim handles on (maintainer's choice: keep that).
- **A part is the component that draws, not a wrapper that forwards to one.** A first version put a forwarding component around `TrackRows`, `TrackControlsColumn` and the two overlays; whole-view renders (zoom, a trim that changes the length) then cost up to 6 components more than before. With the parts reading contexts themselves the extra is 1 to 3 (measured below).
- **Why a render of the root does not render the parts:** the part elements are passed on to `Playlist` exactly as the root received them, never cloned or re-keyed, so on a render of the root alone React sees the same elements and skips them. The `useMemo` around the sort only saves the sorting. `React.Children.toArray` would have cloned every element to give it a key; the tracks-area and controls lists are spread as the children of one fragment per place instead, and the strip's parts are each wrapped in a keyed fragment (step 3).
- **Two layout values, by what changes them** (`waveformLayoutContext.ts`, internal): the extent (`displayDuration`, `tracksFullWidth`) is the only layout value the timescale, the loop region and the annotation row read (the tracks part reads it too, for the row width); the rows value (`rows`: one `{ id, kind }` per track since part 2, the peaks, the drag source, heights, tops, `animateTrackLayout`, render modes, spectrogram helpers, `selectTrack`, the settings-modal opener, the recording's channel count, `showClipHeaders`) is read by the tracks and the controls. One value would render the timescale on every trim move.
- **The root is the only reader of `usePlaylistTimeline()` in the view.** The tracks part and the controls part take `rows` and `peaksDataArray` from the rows value. A first version had both call `usePlaylistTimeline()`; that value also changes when `isReady` flips (and, until #812, when `onTracksChange` was a new function), so both parts rendered for those too (found in review). Today an engine rebuild flips `isReady` twice and renders the root alone (`waveformPartsQuietShell.test.tsx`: "a rebuild of the engine renders the root (ready, then not, then ready); neither the tracks part nor the track controls follow"). Before a part reads a provider value, list what else changes that value: it must not change for things the part does not draw more often than for those it does. (`WaveformTracks` reads `usePlaylistView()` for two of its fields, `sampleRate` and `mono` (`waveHeight` comes from `usePlaylistInfo()` since #689), and `WaveformTrackControls` reads `useTrackReorderPreview()` for the epoch alone; both values change rarely, or together with the layout the part follows anyway. Since part 2 the tracks part reads no hook that only one provider serves: see the next section.)
- **The parts without children are memoized, except the playhead** (`WaveformTimescale`, `WaveformTrackControls`, `WaveformAnnotationBoxes`, `WaveformLoopRegion`, `WaveformSelection`; `WaveformPlayhead` is not, and the annotation row is skipped only while `getAnnotationBoxLabel` keeps its identity): the component that composes the view renders with the tracks when it reads them (`useArrangementTracks`, `usePlaylistTimeline`).
- **Moved out of the root in step 3:** the `setRecordingActive` effect (now `useRecordingSession`), the provider's `controls.show` as the switch for the controls column (now: a `WaveformTrackControls` among the children, as wide as its `width`) and the provider's `timescale` (now: a part in the timescale strip).
- `AudioPosition` registers its frame callback under `useId()`; under the fixed id `'audio-position'` two readouts under one provider replaced each other's callback.

Measured (dev build, components per action, before to after; `probes/split768.cjs`, `trim767.cjs`, `select740.cjs`): multi-clip zoom 385 to 386, trim per move 94 to 93 and 140 to 142 when the length changes, play then stop 108 to 104, a click on a row 115 to 105, mute 38.9 to 37.2; annotations zoom 283.5 to 285.5, each of the three annotation checkboxes +3, play then stop 120 to 115; stem-tracks zoom 395 to 398, reorder 187 to 186. Selection drags, volume, pan, loop and the settings toggles are identical on all three pages. The probes do not run on `/examples/recording` (no rows on load, no zoom button).

Tests: `waveformPartsSorting.test.tsx` (the sort and the scan), `playlistVisualizationParts.test.tsx` (each prop reaches its part, except `recordingState`, which `recordingPreviewSubscription.test.tsx` covers; widths; the drag-source mark; `renderPlayhead` not called for a track selection or a reorder preview), `waveformPartsQuietShell.test.tsx` (the root renders alone on a press and not at all on a track selection; a parent's re-render with the same props renders the root and the tracks part and no memoized part or row; an engine rebuild renders the root and neither the tracks part nor the track controls; two `AudioPosition`s). `staticEngineImports.test.ts` lists the new files. A mutation run of 57 one-line changes left two survivors: removing the `useMemo` around the sort (equivalent, see above), and `animateTrackLayout` forced to true (a CSS transition on the rows and control slots, older than this step, which jsdom cannot see: an untested line, not an equivalent one).

## Two Roots Over One Frame and the Same Parts (#685, step 2)

The MediaElement view is `<MediaElementWaveformRoot>` with `WaveformTimescale`, `WaveformTracks` (with the `WaveformFades` marker when fades are drawn), `WaveformAnnotationBoxes` (`MediaElementAnnotationBoxes` until #686), `WaveformSelection` and `WaveformPlayhead`. Step 2 built this inside `MediaElementPlaylist`, which kept its props; step 3 exported the root and removed that component.

- **Two roots, because a root reads what only its provider has.** `WaveformRoot` reads the timeline, the editor controls, the reorder preview, the spectrogram integration and the recording; `MediaElementWaveformRoot` reads `useMediaElementTrack()`. One root would need hooks called conditionally. A press also differs: the multitrack root selects the row under the pointer and a click while stopped is `setCurrentTime`; the MediaElement root's click is a collapsed `setSelection`.
- **What they share is a hook, not a component: `useWaveformFrame` (`waveformFrame.tsx`).** It reads shared hooks only and returns the scrolling frame (`Playlist`) with the parts in their places, the two layout contexts, the drawing-primitives context, the selection drag and its two helpers. A root calls `useWaveformParts(children)`, works out the length of the timeline and the rows value, and passes them in. A component in that place would be one more component on every render of either root; the hook adds none (multitrack counts are identical to before this step).
- **The rows value holds no `ClipTrack`.** `rows` is one `{ id, kind }` per track, which is all the tracks part and the controls part used of a track. `MediaElementWaveformRoot` supplies one constant row (`MEDIA_ELEMENT_TRACK_ID`, `'audio'`), always. When the provider has no peaks (extraction failed) the root gives that row an empty list of clips, so it is drawn one `waveHeight` tall with nothing in it and the click overlay still covers it (maintainer's choice; the view used to show the text "Loading waveform...", for good, and a first version of this step drew no row, which left an area of no height that could not be clicked). The provider's own `peaksDataArray` stays `[]`. The drag source of a reorder is in the rows value too (the multitrack root reads the preview anyway).
- **The selected row comes from an internal context both providers serve: `SelectedRowContext` / `useSelectedRow()`** (in `contexts/playlistContexts.ts`, not exported from the package). `WaveformPlaylistProvider` renders it with the very object of `SelectedTrackIdContext`; `MediaElementPlaylistProvider` with a constant naming its one track, so that row is always drawn selected (`data-selected="true"`, the selected colours, as before). This is the "shared hook, no optional reader" rule: `WaveformTracks` could not keep `useSelectedTrackId()`, which the MediaElement provider blocks. Putting the id in the rows value instead was approved and then dropped before it was built: the multitrack root would have rendered (root, `Playlist` and its styled elements, about 15 components by the count of a root-only render in `probes/split768.cjs`) on every selection made from the controls column or from code.
- **Fades are the clip's under both providers.** The MediaElement provider puts `track.fadeIn` / `track.fadeOut` on its one `ClipPeaks`, and ui-components' `Clip` draws them when the `WaveformFades` marker is present, placed from the clip's width (`clipPixelWidth`). The view used to draw `FadeOverlay` itself from the track's fades with the fade-out placed from the peaks length, one pixel further right on `/examples/fades` (741 px against 740 for an 810 px clip). The provider extracts the peaks in a memo of their own (`trackPeaks`), so a new fade or name builds a new clip object around the same peaks.
- **No controls column under MediaElement**: `MediaElementWaveformRoot` passes `controlsWidth: 0`, and warns in development when a `WaveformTrackControls` is among its children (the part is never rendered there).
- **`data-playlist-state` under MediaElement is always `"ready"`** (maintainer's choice after the first review): the waveform is drawn from the provider's first render. A first version followed `useMediaElementTrack().isReady`; with the CSS the Loading Audio guide recommends for `"loading"` (`pointer-events: none`) the waveform then ignored clicks until the metadata arrived, for good on a load error, and again on every player replacement. e2e can wait for `[data-playlist-state="ready"]` on these pages; it says the view is in the page, not that the player has loaded.
- **`MediaElementAnnotationBoxes` was a part of its own until #686**, with its drag wiring and `editable` / `linkEndpoints` / `onAnnotationUpdate` as props, and it clamped the edge drag to the extent's `displayDuration`, which under `WaveformRoot` can be longer than the audio. #686 replaced it by `WaveformAnnotationBoxes` for both roots, which keeps that limit on purpose (the drawn timeline: see the #686 section). Still true of the one part: it reads the root's extent and not `useMediaElementTrack()`, whose value also changes when the player becomes ready and with the track's name and fades (the label function ran for every annotation each time; found in review).
- **What the MediaElement root renders on:** a press and its release (the drag's own state), play, pause and stop, the player becoming ready, a new track or zoom, a view-setting or theme change, and a render of the component that composes it. Of these, a press, a release, play, pause, stop, the player becoming ready and a render of the composing component do not render the track, the clip or a channel (a new track, zoom, `waveHeight` or theme does, through the values the row reads). Not on a `seekTo`, a selection change, an annotation boundary or an automatic-scroll toggle.

Measured (dev build, `probes/media769.cjs`, components per action, before to after): `/examples/media-element` click to seek 69 to 30, play / pause / stop 41 to 24, selection drag per move 8 right and 12 left unchanged, speed select 6 unchanged; `/examples/media-element-annotations` click to seek 95 to 30 (147 to 88 while playing), play 77 to 47, pause 89 to 59, play again 53 to 23, stop 69 to 45, drag 8 / 10 unchanged, continuous-play toggle 22 unchanged, the page's own "Editable" checkbox (the whole page re-renders) 262 to 239. Multitrack (`split768`, `select740`, `trim767` on multi-clip): every action identical. On screen (`probes/shots685.cjs <tag> <output dir>` against a server on port 3077, four pages, run on the branch and with `main`'s `packages/browser/src` in place): the size of every player and clip is identical, and the only difference in what it records is the fade-out position above.

Tests: `mediaElementViewParts.test.tsx` (the rows of the upgrade guide's table that are about markup, fades, the controls column and the failure case; the root rendering alone; the nearest provider's row. For the two call-frequency rows: `renderPlayhead` is tested for a press and its release only, the box label function (`getLabel` since #686) also for the player becoming ready and for play, pause and stop), `mediaElementPlaylistProps.test.tsx` (since #686: the box part gets `getLabel` only, and the options come from the provider), `mediaElementShellQuiet.test.tsx`, `e2e/media-element-view.spec.ts`, and the multitrack files of step 1, whose existing tests are unchanged (`playlistVisualizationParts.test.tsx` gained three: the loading state, the kind of a MIDI row and panel, the timescale gap; `staticEngineImports.test.ts` lists the new files). A mutation run of 54 one-line changes left two survivors: the multitrack click while stopped calling `setCurrentTime` (an untested line older than this step; it matters after a small leftward drift), and `dragSourceTrackId` missing from the rows value's dependencies (a reorder preview always gives a new `trackLayout` in the same render, which is a dependency too).

## The Parts Are Public (#685, step 3)

The roots and the parts are exported under the names they have in the source, and the consumer composes them. `PlaylistVisualization` and `MediaElementPlaylist` are deleted; `Waveform`, `WaveformEditor` (clip headers and fades) and `MediaElementWaveform` are ready-made compositions that take `className` only (the annotation options left them in #686). The upgrade guide has the removed-to-replacement table.

- **A part is drawn by being rendered; no provider option switches one.** The providers' `timescale` and `controls` props and `usePlaylistView().timeScaleHeight` / `.controls` are removed. `useWaveformFrame` draws the timescale strip when a part is sorted into it (as tall as the first timescale part's `height`, 30 px by default, `DEFAULT_TIMESCALE_HEIGHT`, since #689), and the controls column when a `WaveformTrackControls` is among the children, as wide as that element's `width` prop (default 200, `DEFAULT_TRACK_CONTROLS_WIDTH`). The root reads the width from the element as it reads the per-clip markers: the column is the root's own, outside the scrolling area. ui-components' `PlaylistInfoContext` still gets `timeScaleHeight` from the frame (`controls` left that value in #689: nothing read it), worked out from the parts.
- **The ready-made compositions hand the root module-level elements** (`const TRACKS = <WaveformTracks />`). A render of `<Waveform />` therefore gives the root children it has seen, and React skips every part, the unmemoized tracks part included (it used to render on every parent render). `composeWaveform` is a function, not a component, so `Waveform` and `WaveformEditor` share it without a layer.
- **The recording effect is `useRecordingSession({ isRecording, trackId })`** (`hooks/useRecordingSession.ts`), called by the component that records. `WaveformRecordingPreview` only draws. A view without the hook does not mute the take's track (maintainer's choice E).
- **Per-clip options are a context of the tracks part, not props of the row** (`ClipDisplayContext` in `TrackRows.tsx`: `gainScaledWaveforms`, `showFades`, `selectTrack`, the two spectrogram canvas callbacks). `ClipView` reads it; `TrackRow` passes on only what it uses itself (`samplesPerPixel`, `sampleRate`, `showClipHeaders`). The value is memoized on its five fields, and a change renders every clip, as the props did.
- **The timescale strip's parts are keyed by kind** (`keyedByKind` in `waveformFrame.tsx`: `timescale-0`, `loop-0`), so `{flag && <WaveformTimescale />}` does not remount the loop region. Tracks-area children keep one position each (step 1); inside a consumer's list of varying length, keys on the parts do the same (checked: a filtered array remounts the later part without keys, not with them).
- **A misplaced part warns once in development and never throws** (`partWarnings.ts`, `warnMisplacedPart`; maintainer's choice). How each is detected: a per-clip marker's function body runs only when React renders it, which the tracks part never does, so running means it is somewhere else; `scanTracksParts` warns for an element that is no marker; `WaveformTimescale`, `WaveformLoopRegion` and `WaveformTrackControls` read `WaveformPartPlaceContext` (the frame provides `'timescale'` and `'controls'` around those two places, the default is `'tracks'`) and warn when they are drawn in the tracks area, which is where a part wrapped in another component lands; the sort warns for a second `WaveformTracks`, for a second `WaveformTrackControls` (both sets of panels are drawn in the one column) and for a controls `width` that is not a positive number (no column is drawn then: ui-components' `Playlist` shows the column for a width above 0); the tracks part warns when its own scan of the clip-headers marker or of the recording-preview marker differs from the root's (a tracks part wrapped in a component: the rows are then a header too short, or the timeline does not grow with the take; the root's side of the second comparison is `RootSeesRecordingPreviewContext`, a boolean of its own that only the tracks part reads: in the rows value it rendered the controls column each time the marker came or went); `MediaElementWaveformRoot` warns for a controls part. Messages are deduplicated per text for the life of the page.
- **Which part works under which provider.** Either: the timescale, the tracks, clip headers (under MediaElement a header with the track's `name`, "Track" without one; `ClipView` reads `useClipInteraction()` under either provider, so with clip interaction enabled above a MediaElement provider the header is a draggable that nothing handles: documented as "leave it off"), fades, selection, playhead. Multitrack only: `WaveformLoopRegion` (throws the blocked-hook message under MediaElement; so did `WaveformAnnotationBoxes` until #686 made it the one box part for both roots), `WaveformTrackControls` (never rendered there as a child of the root: the warning above; wrapped in a component it is rendered among the tracks and throws the blocked-hook message), `WaveformRecordingPreview` (throws `useEngineRefs needs…` once a take runs into the player's track id). (`MediaElementAnnotationBoxes` existed until #686.)
- **`MediaElementPlaylistProvider` compares `track.fadeIn` / `track.fadeOut` by value** (`useShallowStable`), for the clip and for the effect that creates the player. The effect listed the two objects as dependencies, so an inline fade in an unmemoized `track` disposed and re-created the player on every render of the provider's parent (found while reading for this step; on `main` until then).
- **Not built, on purpose:** `useSelectedRow` stays internal (nobody composes their own rows yet); the spectrogram settings modal's state stays in `WaveformRoot`; the annotation options stayed on the three compositions until #686. (The track-controls options were props of the controls part until #687, which made the panel the part's children: next section.)

Measured (dev build, components per action, before to after; same probes): multi-clip trim per move 93 to 89 and 142 to 138, zoom 386 unchanged, play then stop 104 and click a row 105 unchanged, drags 9 / 37 unchanged; annotations page: each of the three annotation checkboxes 6 fewer, zoom 285.5 to 284.5; stem-tracks reorder 186 to 183, zoom 398 to 394; MediaElement pages: click to seek 30, play / pause / stop 24, drags 8 / 12 unchanged. On screen (`probes/shotsAll685.cjs`, all 17 example pages, 31 views): every root, row, clip, strip and column has the same box as before; the count of dnd-kit `draggable` attributes differs between loads on `main` as well (pages without a `ClipInteractionProvider`), so it is not compared.

Tests: `waveformPublicParts.test.tsx` (the exports; the three compositions; a part drawn by being rendered; the width; the strip values handed to the drawing primitives; the recording session; every warning; a parent render not rendering the tracks), `testCompositions.tsx` (compositions with the old prop names for the older test files: `ComposedWaveform`, `ComposedMediaElementWaveform`), `mediaElementViewParts.test.tsx` (fades by value: no new clip, no new player), `multitrackDragDuringPlayback.test.tsx` (the click while stopped moves the cursor to the release: the line that survived three mutation runs).

## View Options Have One Home (#689)

`waveHeight`, `barWidth`, `barGap`, `roundedBars`, `progressBarWidth` and `fillViewport` are props of `<WaveformViewOptions>` (`components/WaveformViewOptions.tsx`), not of the providers, the roots or the parts. Removed with no shim: the six props on the providers (five on `MediaElementPlaylistProvider`, which never had `fillViewport`) and the six fields of `usePlaylistView()`, which is `{ sampleRate, mono, indefinitePlayback }`. The upgrade guide has the table.

- **A context, because several components draw with one value and one set of options serves several views.** The root lays the rows out with `waveHeight`, the channels draw the bars, the playhead takes its width, and the spectrogram labels their height. `WaveformViewOptionsContext` is internal (not exported from the file); `<WaveformViewOptions>` is its only provider and inherits each prop left out from the one above with `??`, like `ClipInteractionOptions`. Its value is memoized on the six values: the component that renders it often reads the tracks and renders with them. It works above the provider, and above several (`StylingExample`: one `waveHeight` over ten players; `MediaElementExample`: one element over three).
- **Published once.** A root calls `useResolvedViewOptions()` (defaults, the corrections below, `progressBarWidth ?? barWidth + barGap` worked out from the corrected bar and gap) and hands the result to `useWaveformFrame`, which puts the values in ui-components' `PlaylistInfoContext` together with the zoom, the sample rate and the strip height. That value is memoized on its primitives, so the resolved object is a plain new object per call (a mutation run showed a `useMemo` around it changed nothing). Everything drawn below a root reads `usePlaylistInfo()`: `Track`, `SmartChannel`, `ChannelWithProgress`, `SmartScale`, `TimeScale`, and since #689 `WaveformTracks` (`waveHeight`, for the spectrogram labels) and `AnimatedPlayhead` (`progressBarWidth`). Nothing below a root reads the options context: that would be a second path to the same values.
- **`PlaylistInfoContext` is `{ sampleRate, samplesPerPixel, waveHeight, timeScaleHeight, barWidth, barGap, roundedBars, progressBarWidth }`.** `controls` and `zoomLevels` had no reader and are gone; `progressBarWidth` was declared and never provided (#770 item 8). `AnimatedPlayhead` therefore renders when that value changes (a zoom, which it followed anyway; an option change; the strip appearing).
- **What stays on the provider, and why.** `mono`: the provider computes the peaks with it (`derivePeaks`). `indefinitePlayback`: the animation loop and `seekTo` read it through a ref; `WaveformRoot` also fills the container then (`indefinitePlayback || fillViewport`) and `FastForwardButton` is disabled. `theme`: the transport controls, the checkboxes and the annotation list are drawn outside a root and are styled by it (`useMergedTheme`: the prop merged over `defaultTheme`. styled-components merges an object theme over the theme above it, so an app's own `ThemeProvider` above the provider cannot set a key that `defaultTheme` defines, while keys `defaultTheme` does not define, such as `playlistBackgroundColor`, still reach the library's components from it; a `ThemeProvider` below the provider is merged over ours key by key. I first told the maintainer the outer theme was replaced entirely; the docs agent read the merge in styled-components' source).
- **One default for `waveHeight`: 80** (`DEFAULT_WAVE_HEIGHT` in ui-components, with `DEFAULT_BAR_WIDTH` 1 and `DEFAULT_BAR_GAP` 0). `MediaElementPlaylistProvider` defaulted to 100 (maintainer's choice, 2026-11-13: 80 is the primitives' default and no example page relied on 100).
- **Values that cannot be drawn are corrected in `useResolvedViewOptions`, with one `warnOnce` per message** (maintainer's choice: clamp and warn), in this order: a `waveHeight` or `barWidth` that is not above 0 (0, negative, `NaN`) becomes the default; a `barGap` that is `NaN` becomes 0; a `barGap` that makes `barWidth + barGap` less than 1 (with the corrected bar) is raised to `1 - barWidth`; a `progressBarWidth` that is not above 0 becomes `barWidth + barGap` (the corrected ones; its message also says to leave `<WaveformPlayhead>` out to draw no playhead). So `barWidth={0} barGap={0}` gives a bar of 1, a gap of 0 and a playhead of 1, with the `barWidth` warning only. `null` for an option is "not given" (`??`): no warning. A string from plain JavaScript is not coerced. ui-components' `Channel` guards its own loop with `barStep()` for direct users. Before the change `barWidth={0}` with `barGap={0}` did not hang, it drew a blank waveform (the first bar position was `NaN`). A negative step on `main` was read from the code and not tried; during this work a test of the new code with the guard removed did not end (the bar loop never reached its end).
- **`<WaveformTimescale height>`** (default 30): the root reads it from the element in `sortWaveformParts`, as it reads the controls part's `width`. The first timescale part decides; a strip with only a loop region is 30; a value that is not above 0 warns and is 30.
- **Theme key `spectrogramBackgroundColor`** (optional, `#000` in both default themes and as the fallback) replaced a fixed `#000`. It is read by the wrapper of ui-components' `SpectrogramChannel` (and by `ChannelWithProgress` for the background layer behind it). The wrapper's background is what shows until the worker has drawn the spectrogram and where a chunk is not mounted; once drawn, the spectrogram is opaque and covers it. The first build put the key only on the `ChannelWithProgress` background, which the channel's fixed black wrapper covered; a unit test on the covered element passed, and the review found it. The wrapper reads the key now, and its computed background was checked in Chromium.
- **Theme key `placeholderClipOpacity`** (optional, 0.5 when not set or not a number from 0 to 1) is the opacity of the whole container of a `Clip` given `isPlaceholder`, header included. The sibling of `spectrogramBackgroundColor`: read in `Clip.tsx` from the theme, not set in either default theme.
- **A placeholder without peaks draws a body** (#812): `ClipView` in `TrackRows.tsx` renders ui-components' `<ClipPlaceholderBody isSelected>` as the first child of the `Clip` when the record is a placeholder (`isPlaceholder`) and its peaks are empty (`peaks.length === 0`). The decision is in the row because only the row knows the record's peaks; the box is a ui-components part because it is drawn from the theme like a channel, and a Storybook story can show it. It fills the clip's channel wrapper (`position: absolute`, 100% by 100%: the clip's width, the height below the header), in the bar colour of both draw modes (`waveFillColor`, the selected one on the selected track), and sets no opacity: the clip container dims it. The zero-length channel of the record still renders after it (its progress tint is drawn over the body).
- **`<WaveformViewOptions>` goes above a root.** A root reads the options above itself, so one among a root's children does nothing for that root; `sortWaveformParts` warns once (`warnMisplacedPart`), and the parts inside it count as wrapped in a component. A nested `<WaveformViewOptions>` cannot return an option to its default or derived value (a prop left out, or `null`, inherits): `progressBarWidth={7}` outside and `barWidth={4}` inside leaves the playhead 7 px.
- **`SpectrogramProvider` sits above the views and no longer reads a row height.** It keeps the height each canvas registered with (`canvasHeightsRef`) and renders a channel's chunks at the first one's. `SpectrogramChannel` has the height in its canvas keys, so a new `waveHeight` mounts new canvases that register again (a transferred canvas cannot be resized from the page). In "both" mode the worker was told the full row height for a canvas half as tall; it now renders at the canvas's height. The range of the audio is registered the same way (`canvasRangesRef`, #812): a clip is drawn for the `offsetSamples` / `durationSamples` its canvases registered with, which is the trim preview's while a trim is dragged.
- **Views that share a provider are linked (maintainer, 2026-11-13: "if people actually want to share a provider it makes sense to link things like zoom, auto scroll etc. otherwise they can just use multiple providers").** They share zoom, selection and playback, and can differ in these options. Not linked yet (#803): the provider keeps ONE scroll container, so automatic scroll and zoom re-centring move only the view mounted last; and spectrogram canvas ids are per clip, so a spectrogram track draws in only one of two views (the other stays black). Both were seen in a browser with a prototype; tracked in #803. A view at another zoom is another provider under `MediaElementPlaylistProvider` (each is independent); under `WaveformPlaylistProvider` with the default Tone engine our docs say one instance per page (shared Tone.js transport), so it is not available by adding a provider today (#805; read from our docs, not traced in the engine).
- **Left fixed, on #804:** the 60 s empty timeline (`DEFAULT_EMPTY_TRACK_DURATION`) and the 10 s recording growth step (`RECORDING_EXTENT_STEP_SECONDS`). Fallback colours for a theme key set to `undefined` (`#1a1a2e`, `rgba(0, 0, 0, 0.1)`, `#ff0000`) are still literals.

## Progress Overlay Width Invariant

**Decision:** In `ChannelWithProgress`, `ProgressOverlay.$width` uses `clipPixelWidth()` from core, but `Background.$width` uses `smartChannelProps.length` (peak data length).

**Why:** Background must match the canvas area — extending it to `clipPixelWidth` bleeds the waveform fill color into the gap between audio end and clip end (where the playlist background should show). ProgressOverlay must match the clip container — using `peaksData.length` causes `scaleX(ratio)` to scale a narrower element, making progress visually lag behind the playhead.

## Controls Offset Removed

**Decision:** All `controlsOffset` / `controlWidth` arithmetic removed from mouse handlers, playhead positioning, selection, auto-scroll, and zoom calculations.

**Why:** Controls are now outside the scroll container (in `ControlsColumn`), so pixel positions in the scroll area map directly to timeline positions without offset adjustment.

**Affected:** `waveformFrame.tsx` (both roots), `AnimatedPlayhead`, `WaveformPlaylistContext` (auto-scroll + zoom), `MediaElementPlaylistContext` (auto-scroll), `useAnnotationKeyboardControls`.
