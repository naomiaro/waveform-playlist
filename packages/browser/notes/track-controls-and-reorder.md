# Track controls and track reordering

Notes of Browser Package (`@waveform-playlist/browser`), moved out of the package's `CLAUDE.md`. Read before changing the track control pieces, the controls column or the track-reorder drag.

## Track Controls Are Pieces Bound to a Track (#687)

The children of `<WaveformTrackControls>` are the panel of ONE track: a template the part renders once per track, inside that track's context. `renderTrackControls`, `onRemoveTrack`, `trackReordering` and `SortableTrackControls` are removed (no shims, nothing throws; the upgrade guide has the table). Files: `components/TrackControlsColumn.tsx` (part and slot), `components/trackContext.ts` (`useTrack()`, the three contexts), `components/TrackControlPieces.tsx`, `components/DefaultTrackControls.tsx`, `hooks/useTrackReorderHandle.ts`, `utils/stableTemplate.ts`. (`utils/trackMixerState.ts` is deleted: the mix is the arrangement's since #812, below.)

- **The slot is memoized on primitives.** `TrackControlsSlot` gets the track's id, index, kind, name, the four mixer values, `isSelected`, `isFirst`, `isLast`, render mode, `hasSpectrogram`, `isRecording`, height, top, `animate` and the template (`isLoading` is gone with #812: the controls are enabled while a track's audio loads). The column renders on every mixer change (it reads `usePlaylistMixer()`); only the slot whose track changed renders with it, builds a new `TrackContext` value, and the components that call `useTrack()` in that panel follow. Do not hand a slot an object (a `TrackState`, a track): it would render every slot.
- **The template is compared structurally (`useStableTemplate`, `sameTemplate`).** Children written inline are new element objects on every render of the composing component, which renders with the tracks when it reads them (`useArrangementTracks`, `usePlaylistTimeline`; a trim changes them once, on release, since #812). Handed on as they are, they rendered every piece of every track each time. Two templates are equal when element types and keys match and props are identical by `Object.is`, with `children` compared recursively and `style` one level deep (a style object is usually written inline); then the previous template is kept, and React skips everything below it. A function or object written inline as any other prop makes them differ. Prototype numbers (dev build, components per pointer move, fiber-walk probe): multi-clip trim 237 / 286 (when the length changes) with an inline template handed on, 83 / 132 compared or hoisted to module level; stem-tracks reorder 543 against 167. The ref is written during render; that is safe because it only ever stands in for a template equal to it.
- **`useTrack()` value per slot**, memoized on its fields; the actions are a separate memo so they keep their identity while the track's state changes (`moveUp` / `moveDown` read the position from `indexRef`, written during render). They change with the shared spectrogram value below (until #796 also when every slot was remounted after a reorder drag).
- **One shared, stable context for the spectrogram functions (`TrackControlsSharedContext`).** The spectrogram integration's value changes with the provider's `config` and `colorMap`. The part keeps the latest in a ref and publishes `{ menuAvailable, menuItems, setTrackRenderMode, openSpectrogramSettings }`, which changes only when a menu becomes available or stops being so. `TrackMenuButton` reads it; `useTrack().setRenderMode` / `.openSpectrogramSettings` call through it. `hasSpectrogram` is `spectrogram !== null && kind !== 'midi'`.
- **The reorder handle registers the SLOT's element, in a PASSIVE effect.** `useTrackReorderHandle()` gets the slot's element ref and `setDragSource` through `TrackSlotWiringContext` and calls dnd-kit's `ref(element)` in `useEffect`. A layout effect was tried and no drag started at all: a child's layout effects run before React attaches the parent's ref, so the slot's element was still null on first mount. The popover healer and the `feedback: 'move'` plugin config moved here unchanged from `SortableTrackControls` (see "Track Reordering"). **The slot's element is the keyed `ControlSlot` (#796),** not the `div` inside it that holds the panel: dnd-kit's sorting plugin moves the dragged element next to the element of the item it is dragged over, and with the inner `div` registered that moved one panel into the neighbouring slot, where React's later reorders never looked for it (see "Track Reordering").
- **No late-dragover guard (removed in #796).** From #687 until #796 a `dragover` arrived after the `dragend` of a canceled drag (Escape mid-drag) and set the reorder preview again, for good, so `ClipInteractionProvider` followed dragovers only between a reorder drag's start and end (`trackReorderDragActiveRef`). The note then blamed the sorting plugin putting the item back. Run on #796 with a probe in the handlers (3 canceled drags): the late event's source was a NEW `Sortable` object, made by the slot remount that `handleDragEnd` ran inside `flushSync`. dnd-kit dispatches `dragend` while its status is still `dragging` (it becomes `dropped` once the renderer settles), and a drop target that changes in that window is a real `dragover`. With the remount skipped on cancel the probe saw no late event (0 of 3), and with the remount removed and no guard `e2e/track-reorder.spec.ts` passed 20 of 20; the guard is removed.
- **The mix is the arrangement's, by track id; `trackStates` is derived (#812).** The provider stores no mixer state. `useArrangementView` reads `arrangement.getMixer()` with `useSyncExternalStore` and `deriveTrackStates` builds the public array during render: one entry per track of the arrangement in its order (name from the track, the four values from the mixer, `muted` also true while a take records onto the track: `arrangement.recordingTrackIds`, read the same way, #843), from the moment a track enters, also while its audio loads; an entry keeps its object while its five fields are the same, and the array itself is kept when every entry is. There is no `undefined` entry any more (`arrangementView.test.tsx`: a track with only a loading clip has a `trackStates` entry). A rebuilt engine needs no seeding with the mix: it is constructed on the same arrangement. History, as the lesson: before #687 the array was positional state, re-initialised on a track count change, and a rebuilt engine was seeded from it by index, so after a removal a track could sound with a neighbour's values (read from the code then; the audio was not checked). From #687 to #812 the provider kept a by-id map of its own (`trackMixerState.ts`) beside the engine's values, which is the second copy #812 removed.
- **The four setters take a track id** (`providerInternals/useArrangementEditing.ts`). Each ignores a non-string first argument with `warnOnce` (one message per setter name, development only; `warnOnce` is `partWarnings.ts`'s deduplicated warning under a general name) and otherwise calls the arrangement's setter of the same name with the caller's `MixerChangeOptions`, engine or not; an id no track has changes nothing (`mixerStateByTrackId.test.tsx`). Each call is an undo step (#843), and an undo brings the mix back with no code here (`mixerUndo.test.tsx`).
- **A slider drag is one undo step (#843).** `TrackVolumeSlider` and `TrackPanSlider` each make one `createMixerGesture()` (core) per mount (`useSliderGesture` in `TrackControlPieces.tsx`: `useState(createMixerGesture)`, `gesture.attach(input)` in an effect whose cleanup detaches, so StrictMode's second run attaches again) and pass `{ gesture: gesture.id }` on every `onChange`. The gesture ends on the native `change` at the end of a pointer drag, on the `keyup` of a held range key and on `blur`. Mute and solo pass nothing: each click is a step. Tests: `trackControlParts.test.tsx`, "a slider gesture is one undo step (#843)". Keyboard Undo does not fire while the slider has focus (#730; `e2e/track-controls.spec.ts` blurs before Ctrl+Z). A value set while a track's audio loads is kept (`playBeforeFirstReady.test.tsx`, "edits, mixer changes and `seekTo` before the first ready are applied").
- **`useExportWav`**: under the provider `tracks` and `trackStates` both have one entry per track. `exportWav` called directly may be given fewer states; a track without one is rendered with its own `ClipTrack` mixer fields (`stateOf`), and the solo rule reads the same fallback.
- **A click anywhere in a slot selects the track** (`onClick={actions.select}` on `ControlSlot`), so a consumer's panel selects as the default one always did. `TrackRemoveButton`, the `TrackMenu` button and `ReorderRail`'s grip and buttons stop propagation.
- **Pixel compatibility with the old default panel.** `TrackRemoveButton` wraps `CloseButton` in a span at `left: 1, top: 1` of the slot (where it sat inside the bordered panel); `TrackReorderGrip` is anchored at `right: 3`, vertically centred. The default panel's frame makes room for the grip with `*:has(> [data-track-reorder-grip]) > &` (18 px padding on both sides): the grip is a sibling of the panel, not a child, so the panel has to find it. An element rendered beside `<DefaultTrackControls />` in the flow is below the panel, which is `height: 100%` of an `overflow: hidden` slot: that is why `DefaultTrackControls` takes `children` (drawn below the pan slider).
- **Attributes:** `data-track-controls="<id>"` on the element inside the slot that holds the panel (the sortable item is the slot around it since #796, and carries dnd-kit's `data-dnd-dragging` and `popover` during a drag), `data-track-name` on `TrackName`, `data-track-reorder-grip` on the grip's anchor. `e2e/track-reorder.spec.ts` finds names through them.
- **Under `MediaElementPlaylistProvider`** the part is never rendered as a child of the root; a piece rendered there throws the `useTrack()` message.

Measured (dev build, components per action, before to after; `probes/track687.cjs`; figures from the #687 work, not re-run when this note was written): multi-clip track volume step 32 to 29, mute 37.2 to 34.2, master volume 16 to 9, trim per move 89 / 138 to 82 / 131, zoom 386 to 379, click a row 105.2 to 132.7 (the pieces of the two panels concerned render: `isSelected` is in the `useTrack()` value); stem-tracks volume 63 to 44, mute 65.4 to 46.4, reorder 183 to 169, zoom 394 to 370; annotations (one track) volume 26 to 29. The "track volume" figures of 16 and 33 in older notes were the MASTER slider: `probes/split768.cjs` matched the slider's name loosely; `probes/track687.cjs` matches it exactly.

- **Found in review, built:** a second reorder handle in one panel warns once in development (`handleCount` in the slot's wiring, counted by the hook's effect; two roots under one provider are not covered).
- **Found in review, left:** children that are `false`, `0` or `''` draw empty panels (`??` replaces only `null` and `undefined`); the default panel makes room for the grip only when they are siblings (`:has(> [data-track-reorder-grip]) > &`), and not at all without `:has()`; `<TrackRemoveButton>` without `onRemove` in plain JavaScript throws on click. Each is a row of the upgrade guide's behaviour table or a low on the PR. (Four more lows of #687 ended with #812, with the provider's own mixer map: entries kept across a deferred rebuild, two tracks with one id sharing a state, a value set for a loading track not kept, and a setter racing a rebuild.)
- **#798, closed by #812:** emptying the timeline used to dispose the engine and build a new one for 0 tracks, or leave `isReady` false for good. Now no track change builds an engine (`engineLifetime.test.tsx`, "`addTrack`, `removeTrack` and `setTracks([])` on the arrangement build nothing (#798)").

Tests: `trackControlParts.test.tsx` (exports, the template, `useTrack()` fields and identities, the pieces, clicks, the grip, the menu, the removed props, the MediaElement provider), `mixerStateByTrackId.test.tsx` (id setters, the index warning, an unknown id, removal), `arrangementView.test.tsx` (`trackStates` identity and entries), `recordingTakeMute.test.tsx` (`isRecording`, the disabled mute button), `stableTemplate.test.tsx`, `trackReorderHandleFeedbackPlugins.test.tsx`, `stableDragHandlers.test.tsx`, `e2e/track-controls.spec.ts`, `e2e/track-reorder.spec.ts`.

## Track Reordering (#612)

`useEditorControls().reorderTrack(trackId, toIndex)` calls `arrangement.reorderTrack()` (`useArrangementEditing`): an undo step of the arrangement, with or without an engine attached, and no engine is built for it. The view follows through `useArrangementTracks`; there is no reorder-specific plumbing.

**A reorder needs nothing for the mixer (#687).** The mix is a map by track id in the arrangement and the public `trackStates` array is derived from it and the tracks during render, so the new order of the tracks is the new order of `trackStates`. `reorderTrackPersistsMixerState.test.tsx` guards the behaviour.

**UI:** `<TrackReorderGrip />` among the children of `<WaveformTrackControls>` (#687; the `trackReordering` prop is removed) renders a `ReorderRail` (grip + move up/down chevrons, from `@waveform-playlist/ui-components`) at the right edge of the track's slot. The move buttons call `useTrack().moveUp()` / `.moveDown()` (`reorderTrack(trackId, index ∓ 1)`) and work with no other setup. Drag needs `ClipInteractionProvider` (the ambient `DragDropProvider`): `useTrackReorderHandle()` (`hooks/useTrackReorderHandle.ts`, exported; it replaces the deleted `SortableTrackControls`) registers the SLOT's element as a vertical sortable item (`data: { kind: 'track-reorder', trackId }`) dragged by the element its `handleRef` is attached to; `ClipInteractionProvider`'s `onDragEnd` branches on that `kind` to call `reorderTrack(data.trackId, sortable.index)` instead of the clip-move path. A consumer's own grip calls the hook; the item that moves is still the slot.

**`@dnd-kit/react` sortable-plugin DOM corruption (live-browser bug, fixed):** dragging the reorder grip activates two `Sortable` default plugins that do raw, React-bypassing DOM surgery — the `Feedback` plugin splices a placeholder node in on drag start and `placeholder.replaceWith(element)`s it back on drop (any pointer movement, `feedback !== 'none'`), and `OptimisticSortingPlugin`'s `reorder()` calls `insertAdjacentElement` live during `dragover` collision. Confirmed via `MutationObserver` instrumenting the React-owned row: 4-6 childList mutations per drag, final `parentElement`/`nextSibling` different from before. React's fiber tree never observes these moves; while the registered element was one level inside the keyed slot, the NEXT reorder (drag or button) left the moved panel in the wrong slot for the rest of the session (the mechanism is in (2) below) — `tracks`/`trackStates` are correct (verified via render-time tracing) and the canvas track area (not `useSortable`-wrapped) reorders fine; only the panel/name column gets stuck. Two-part fix: (1) `useTrackReorderHandle` sets `feedback: 'move'` on `useSortable` (per-entity, via `plugins: (defaults) => [...defaults, Feedback.configure({ feedback: 'move' })]` since @dnd-kit 0.5) — **not** `feedback: 'none'`, which looks like the boundary-trim precedent (`Clip.tsx`/`AnnotationBox.tsx`) but is wrong for a _sortable_: `'none'` bails out of `Feedback`'s render function before it ever sets `dragOperation.shape`, and `CollisionObserver` requires that shape — with `'none'`, collision (and `sortable.index`) never updates and drag-commit silently stops working entirely. `'move'` skips the placeholder/replaceWith splice (`placeholder = feedback !== 'move' ? ... : null`) while keeping the unconditional shape assignment, so collision keeps working. (2) `OptimisticSortingPlugin`'s own `reorder()` still moves the dragged element on any drag that crosses a collision boundary, and isn't configurable away without losing live index tracking: it is `targetElement.insertAdjacentElement(position, sourceElement)`, so the dragged element becomes a sibling of the target's element. That is harmless when the registered element is the node React keys and reorders: React's later reorder puts siblings where its own order says. **Since #796 the registered element is the keyed `ControlSlot`.** Until then it was the `div` inside the slot, so the move put panel A's `div` into slot B; React reorders slots, never moved it back, and the names stayed while the tracks moved. The fix then was to remount every slot after every reorder drag (`bumpTrackReorderEpoch` in `onDragEnd`, the slot keyed `${track.id}-${trackReorderEpoch}`), which discarded panel state and itself caused the late `dragover` above; both are removed. Run on #796 (2026-11-24, @dnd-kit 0.5.3): with the inner `div` registered and no remount, the drag test of `e2e/track-reorder.spec.ts` failed 5 of 5; with the slot registered, no remount and no dragover guard, the spec passed 20 of 20. A standalone page with only `@dnd-kit/*` and React (`~/Code/dnd-kit-796-repro` on the maintainer's machine, switch `wrap=1`) reproduces the desync with an inner element. Unit guard: "the sorting plugin's DOM move during a drag leaves each panel in its own slot" in `trackControlParts.test.tsx` (does what `reorder()` does, then reorders twice). The e2e drag test checks ground-truth `data-track-id` order AND the name span together (a names-only or ids-only check would have missed this class of bug).

**Undo is inert during a reorder drag (#848, #906).** `ClipInteractionProvider`'s `onDragStart` marks the provider's drag guard for a `track-reorder` source and `handleDragEnd` (and an unmount) ends it; `undo` / `redo` return meanwhile. An undo that landed mid-drag used to reorder under dnd-kit's optimistic DOM move and leave the panels' DOM (tab) order out of step with the screen (#906). See `clip-drag-and-snap.md`, "Trim/Move Asymmetry in useClipDragHandlers", for the guard.

**Nothing remounts a slot on a reorder (#796).** The slot around every panel is keyed by the track id, so React state inside a panel survives a reorder, by drag or by button. Until #796 every reorder drag remounted all slots (the epoch above), which reset that state.

**`feedback: 'move'` popover-dismissal (dragged row vanishes mid-drag, fixed):** dnd-kit's `Feedback` plugin layers the dragged element via the Popover API — `popover="manual"` + `showPopover()` puts it in the browser top layer (beats every z-index/stacking context; its stylesheet's `position: fixed; z-index: calc(infinity)` is only the fallback). But `OptimisticSortingPlugin`'s `insertAdjacentElement` splice (remove + reinsert) force-dismisses a shown popover **with no toggle events** (spec: removal-dismissal fires none), and a dismissed `[popover]` element is UA-hidden (`[popover]:not(:popover-open) { display: none }`) — so the row disappeared entirely the moment the drag crossed a collision boundary, looking like it was "hidden by the track controls being dragged over". dnd-kit's own recovery (`createDocumentMutationObserver` re-calling `showPopover`) is created only `if (placeholder)` — which `feedback: 'move'` (required, see above) never creates, so 'move' sortables silently opt out of recovery. And the dismissal repeats on **every** boundary crossing (verified live: healed once manually, closed again on the next splice), so a one-shot fix is insufficient. Fix: `createDragPopoverHealer` (`src/utils/dragPopoverHealer.ts`) — a body-scoped childList MutationObserver mirroring the upstream recovery, run by `useTrackReorderHandle` (on the slot's element) only while `isDragSource` is true; it re-shows the popover whenever the element is connected, has the `popover` attribute, and is not `:popover-open` (microtask timing = same-frame heal, no flicker). Covered by jsdom unit tests (stubbed `showPopover`/`matches`) and a mid-drag assertion in `e2e/track-reorder.spec.ts` (element must be `:popover-open` with non-zero height after crossing the boundary — confirmed RED with the healer disabled).

**Playwright synthetic-drag calibration:** `@dnd-kit/react`'s collision detector samples position per animation frame — 1-2 coarse `page.mouse.move(..., {steps})` calls fired back-to-back can outrun that sampling and never register a collision (the drag silently no-ops: `sortable.index` stays at `initialIndex`). Use many discrete `page.mouse.move()` calls (~15) with a short `waitForTimeout` (~60ms) after each, ending at the target grip's exact center — a larger overshoot over-shifts collision into the next row (the dragged item's own shape, not just the cursor, drives collision, so extra cursor travel means extra shape displacement).

**Drag-preview layout (`trackDragPreview`, `useTrackReorderPreview()`):** `useEditorControls().setTrackDragPreview` and `useTrackReorderPreview().trackDragPreview: TrackDragPreview | null` (`{ trackId, toIndex }`, `src/utils/trackOrderPreview.ts`) publish a view-only preview of the in-progress reorder — the arrangement's track order is untouched until drop. `ClipInteractionProvider`'s `handleDragOver` sets it from the sortable's live `sortable.index` on every `dragover` (functional-set with an equality guard so repeated dragovers at the same index don't re-render); `handleDragEnd` clears it unconditionally (both commit and cancel) together with `reorderTrack`, both inside one `flushSync`: dnd-kit calls the handler inside `startTransition`, where clearing the preview would be a transition update while the reorder (the arrangement, read with `useSyncExternalStore`) renders at once (`trackReorderDropCommits.test.tsx`). `WaveformRoot` derives `displayOrderIds` via `applyTrackOrderPreview(tracks, trackDragPreview)` and feeds both the waveform column and the controls column from the SAME `computeTrackLayout(displayOrderIds, heightById)` map (`{ topById, totalHeight }`) — rows are absolutely positioned (`.attrs()` `top`, deliberately NOT `translateY`: a transform creates a stacking context on every row, flattening clips' `z-index: 105` beneath the ClickOverlay's `z-index: 1` and blocking all clip interactions — found by full-suite e2e, fixed by positioning with `top`) at their layout top, and DOM order never changes mid-drag. This makes `OptimisticSortingPlugin`'s live DOM splices (see the DOM-corruption note above) visually inert — they still happen and `dragPopoverHealer` is still required, but the columns no longer visually rely on DOM order. The waveform rows' transitions (`top 150ms ease`) are gated by `useTrailingActive(trackDragPreview !== null, 200)` (`src/hooks/useTrailingActive.ts`; the control slots' only while the preview is live, below) — a 200ms trailing-active window so a canceled drag's revert-to-original-position also animates, not just the drag itself — and are skipped entirely under `prefers-reduced-motion`. **The released slot lands at once (#796).** The reorder sortable's `Feedback` config has `dropAnimation: null`: with `'move'` there is no placeholder, so the default drop animation animated the slot from where it was to where it was, and it hung at the pointer for about 250 ms (270–320 ms measured, on `dev` as well) before jumping into place. **The control slots animate `top` only while a preview is live, not in the 200 ms after it** (`animate={animateTrackLayout && dragSourceTrackId !== null}` in `WaveformTrackControls`; the waveform rows keep the window). dnd-kit copies a slot's computed `transition` when it lifts it and lets the slot's own one apply again when it releases it, so a `top` transition on at either moment animates between the slot's column position and dnd-kit's fixed, viewport-based one. Seen on #796 with the window on: a released slot appeared about 300 px away and slid back (9 of 9 drops), and a slot lifted within about 150 ms of another track's drop flew in from about 400 px away (3 of 3, found by the code review after a first fix that kept the transition off on the dropped slot alone). On a cancel the slots still glide back: dnd-kit animates `translate` on each sortable whose index it resets; in 9 of 15 Escapes past the next track the neighbour shows at its home for one frame first (8 of 12 unthrottled, 1 of 3 under 6x CPU throttling), and for up to about 250 ms the panels and the waveform rows move apart (dnd-kit's cancel glide lasts 250 ms, the rows' slide 150 ms; up to ~70 px apart, and up to ~100 px on a move-button press right after a drop, which the panels take as a jump), since the rows keep their window. Measured with this version (9a3d5826, stem-tracks): drops landed in place 13–40 ms after the release (8 of 8) and 25–52 ms under 6x CPU throttling (6 of 6), and a slot lifted 30–150 ms after a drop did not move (6 of 6). e2e guards in `e2e/track-reorder.spec.ts`: the drag test samples the dragged slot on every frame after the release, and "a track lifted right after another is dropped stays under the pointer"; both fail with the gate removed (3 of 3 each). A real drop and cancel animation is #907. Waveform row wrappers carry `data-track-row` + `data-track-id`; the row matching `trackDragPreview.trackId` also carries `data-track-drag-source`. The drag-source's controls slot renders fully opaque (`theme.selectedTrackControlsBackground`, matching the selected-track tint) with a shadow, since it floats in the browser's top layer via dnd-kit's Popover-based `Feedback` plugin and would otherwise show the row underneath through it. The lifted look is drawn by the slot (`TrackControlsSlot`, told through `TrackSlotWiringContext.setDragSource`), so a consumer's panel gets it without doing anything. Since #796 it is drawn on the `ControlSlot` itself (`$isDragSource`): that is the element in the top layer, and its `overflow: hidden` clips a shadow drawn by anything inside it.
