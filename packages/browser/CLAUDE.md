# Browser Package (`@waveform-playlist/browser`)

## Optional Playout Engines (#510)

`@waveform-playlist/playout`, `@waveform-playlist/media-element-playout`, and `tone` are
**optional `peerDependencies`**. The providers load the default engine via dynamic
`import()` through `src/playout/resolvePlayoutAdapter.ts` / `resolveMediaElementPlayout.ts`
(factory-or-dynamic, install-hint rethrow — the `@dawcore/midi` `loadMidiImpl` pattern).

- `WaveformPlaylistProvider` accepts `createAdapter?: () => PlayoutAdapter`. When supplied,
  neither `@waveform-playlist/playout` nor `tone` is imported.
- `MediaElementPlaylistProvider` accepts `createPlayout?: () => MediaElementPlayout`.
- **The provider static import graph must stay engine-free** — enforced by
  `src/__tests__/staticEngineImports.test.ts`. Use `import type` for engine types and
  `await import()` for engine values. Adding a static engine import to those files fails CI.
- **Tier-3 (Tone-coupled) surface moved to `/tone`**, NOT left in the core graph (see the
  `/tone` subpath section below). In-graph modules that couldn't move were decoupled instead:
  `soundFontSync` (structural `setSoundFontCache` check, not `isToneAdapter` from playout) and
  `useAnnotationDragHandlers` (tone-free `sampleRate` default).
- **Sample rate at mount** is provisional (`sampleRate` prop or 48000) and reconciled from
  `adapter.audioContext.sampleRate` on first `loadAudio`. A Tone consumer at 44100 Hz that
  passes no `sampleRate` prop sees 48000 for the brief pre-first-load window.
- **Removed in 14.0.0:** the `Tone` convenience re-export. Import `tone` directly.
- **Async effect cancel-race:** making a provider's init effect async (via `await import`) opens a dispose-before-resolve window. Both providers guard with `let cancelled = false`. In **WaveformPlaylistContext** cleanup only sets `cancelled = true`; dispose happens inside the async `loadAudio` body's `if (cancelled) { adapter.dispose(); return; }`. In **MediaElementPlaylistContext** the cleanup itself disposes the `createdPlayout` capture.
- **Test the dynamic-import seam, not the provider:** factory-or-dynamic-import logic lives in
  tiny pure async modules (`resolvePlayoutAdapter`/`resolveMediaElementPlayout`), unit-tested
  directly — `vi.doMock(pkg, () => { throw })` simulates a missing peer (no-peer install-hint
  test); the bypass test asserts the factory short-circuits before `import()`. Avoids mounting
  the heavy provider in jsdom (separate file per `vi.doMock`, per the dawcore midi precedent).

### `/tone` subpath (Tone batteries-included surface)

The core `@waveform-playlist/browser` entry is structurally free of `tone`/`playout`
(verified transitively by `coreBarrelEngineFree.test.ts`). All Tone-coupled exports —
`useAudioTracks`, `useDynamicTracks`, the effects hooks + factory/definitions,
`useExportWav` + `ExportWavButton`, `useOutputMeter`, `useMasterAnalyser` — live at
`@waveform-playlist/browser/tone`. A MediaElement-only or custom-adapter consumer never
resolves `tone`/`playout` under any bundler. `useAudioTracks`/`useDynamicTracks` moved
here because they decode on the Tone global context.

## Build (tsup)

Uses tsup (same as all other packages). tsup auto-externalizes `dependencies` and `peerDependencies` — no manual `external` list needed. Previously used Vite with a manual external list that drifted (#317).

## Custom Hooks Architecture

**Pattern:** Extract complex logic into reusable custom hooks.

**Key Hooks:**

- `useClipDragHandlers` - Drag-to-move and boundary trimming
- `useClipSplitting` - Split clips at playhead
- `useKeyboardShortcuts` - Flexible keyboard shortcut system
- `usePlaybackShortcuts` - Default playback shortcuts (0 = rewind to start)
- `useAnnotationKeyboardControls` - Annotation navigation, editing, auto-scroll, and playback
- `useDynamicEffects` - Master effects chain with runtime parameter updates
- `useTrackDynamicEffects` - Per-track effects management
- `useDynamicTracks` - Runtime track additions with placeholder-then-replace pattern
- `useSelectionState` - Selection state (start/end) with engine delegation
- `useLoopState` - Loop state (enabled, start, end) with engine delegation
- `useSelectedTrack` - Selected track ID with engine delegation
- `useZoomControls` - Zoom state (samplesPerPixel, canZoomIn/Out) with engine delegation
- `useMasterVolume` - Master volume with engine delegation
- `useTimeFormat`, etc.

**Location:** `src/hooks/`

## Audio Effects Architecture

**Three kinds of entry in one chain (`ActiveEffect.kind`):** `'tone'` (the 20 built-in Tone.js effects, `effectDefinitions.ts` + `effectFactory.ts`), `'wam'` (a hosted WAM plugin, `wamEffectFactory.ts`), `'custom'` (a type registered with `registerEffect()` from `@waveform-playlist/core`: an AudioWorkletNode or any native nodes, `customEffectFactory.ts`, #679). The registry and its per-context `prepare` bookkeeping live in core and are shared with dawcore; do not add a second registry here. The built-in kind was `'native'` until the review of #679: in core and dawcore "native" means a registry effect built from native nodes (`NativeEffectDefinition`, dawcore's `EffectState.kind: 'native'`, the `native-*` types), so in React the word named the opposite thing, a Tone.js effect, next to the new `'custom'` kind that IS a native-node effect. dawcore's own `kind: 'native'` is a different type and did not change.

**`EffectsRack` (`src/effects/effectsRack.ts`) is one chain: the list, the instances and the wiring.** `useDynamicEffects` owns one rack, `useTrackDynamicEffects` one per track id. The hooks are thin: they hold no effect state and do not re-render when a chain changes.

- The list is a `ValueSource<ActiveEffect[]>` (`rack.effects`), replaced on every change. Only a component that calls `useActiveEffects(source)` follows it. With the list in the state of a hook called at the page root, every slider step re-rendered the page: 214 component renders per step on the effects example, 34 after (all inside the rack component; `probes/close704.cjs 3077 effects 1 effects`).
- Everything the hooks return is identity-stable (the rack's methods are arrow properties; `getTrackEffectsFunction(trackId)` and the offline functions are cached per track). `availableEffects` is `getAvailableEffects()`: the built-ins, plus the registered custom types ONLY when `isNativeGlobalContext()` (outside native mode they cannot be added, so they are not offered). It returns the same array until that set changes, so it can be read during render. It is a read in the hook's render, not a subscription: a type registered after the calling component rendered appears on that component's next render. `rack.add(id)` looks the registry up itself and does not depend on it.
- `getAvailableEffects()` is what a picker should offer: the Tone catalogue, plus app-registered types in native-context mode. It leaves out definitions marked `builtIn` (dawcore's `native-*`, in the shared registry whenever `@dawcore/components` is loaded on the page): they worked when added but showed up as a second "Compressor" in a React picker. Maintainer's choice, 2026-11-11: "App-registered only". They can still be added by id.
- The rack rewires itself synchronously when `chainTopologyKey(list)` changes; there is no React effect involved. A parameter change or an in-place bypass does not change the key and touches no connection.
- A failed rewire rolls back (`commit()`): if `wire(next)` throws (a node on another AudioContext, say), the previous list is wired again, nothing is published, and the error propagates, so the list always describes what is connected. `append()` then removes the new instance from the map and disposes it, and the add rejects. `wire()` sets `wiredKey` to `UNWIRED` (a key no list can have) before touching any connection and to the real key only after the last one is made; if the restore throws too (warned, not rethrown), the key stays `UNWIRED` and the next change wires from scratch instead of being skipped as "same topology". `remove()` rewires first and disposes after, `clear()` always ends with an empty list (it is the way out of a broken chain) and rethrows, and an `attach()` whose wiring throws is not kept; each has a test that makes Tone's `connect` mock throw.
- A rewire disconnects the output of EVERY instance, including ones a bypass has taken out of the chain, before connecting the audible ones. An effect that makes sound with nothing connected to its input must fall silent when bypassed.
- The chains survive a remount; the hooks have NO cleanup effect. React runs the same effect cleanup for a real unmount, a StrictMode remount, Fast Refresh and a hidden `<Activity>`, and cannot tell them apart; in the last three the chain is state that must still be there afterwards. The maintainer decided on 2026-11-11 that the chain must survive a remount. A first version of #679 cleared the rack in the cleanup (`dispose()`), which emptied the chain on every StrictMode remount and Fast Refresh. Do not add a cleanup that clears or disposes. Consequence for consumers: defaults added on mount need a ref guard (an unguarded mount effect adds twice under StrictMode dev).
- Instances of a rack that is really gone are disposed when the rack is garbage-collected: the constructor registers the rack with a module-level `FinalizationRegistry` whose held value is the `instances` map (which must never reference the rack, or it would never be collected). Best effort: not prompt, not guaranteed, skipped where `FinalizationRegistry` does not exist. Verified once in Chromium: an unmounted page's worklet instance was disposed after a forced GC. `clear()` (`clearAllEffects` / `clearTrackEffects`) is the way to release at a known moment.
- `clear()` bumps a generation counter. An `add` / `addWam` that was awaiting (`prepare`, a WAM load) compares the counter afterwards, destroys the loaded WAM plugin if there is one, and rejects with "…aborted: the effects chain was cleared before …"; nothing is appended after a clear. An unmount aborts nothing. Keep the counter: a "cleared" flag would have to be reset somewhere, which is the `useDynamicTracks` bug of #704 (a cancelled flag set and never cleared).
- A type registered again while its `prepare` was running is added as the NEW definition: `ensureEffectPrepared` loops until the current definition is prepared, and `add` re-reads the registry after the await so the entry's `definition`/`params`/`wetParam` describe the instance that was created. Unregistered during the await: the add rejects.
- `updateParameter` ignores a non-number for a `'custom'` entry (a registered effect's parameters are numbers; storing anything else would show a value the effect is not using).
- `add()` is `async` but a built-in is appended before the first `await`, so `void addEffect('reverb')` in a mount effect behaves as the synchronous call did.

**Bypass has one rule (`isDisconnectBypassed` in `chainTopology.ts`):** an entry with a `wetParam` is bypassed in place (wet to 0, restored from `params` on un-bypass; a wet change while bypassed is stored, not applied); an entry without one is disconnected. `wetParam` is `'wet'` for a Tone effect that has a `wet` signal, the definition's `wetParam` for a custom effect, absent for WAM. Before #679 the rule was `kind === 'wam'`, and bypassing a compressor, limiter, gate or EQ3 (no `wet`) did nothing during playback. Anything new that changes what is connected (not how it sounds) must be part of the topology key.

**Native nodes need native-context mode.** `rack.add` for a custom type and `rack.addWam` throw unless `isNativeGlobalContext()`: under standardized-audio-context `new AudioWorkletNode(rawContext)` fails. The same guard runs at export. Native and Tone nodes are joined with Tone's `connect()`/`disconnect()` helpers, never `node.connect()`, and an instance has separate `input` and `output` (the same node for Tone and WAM entries).

**Effects must be built on the shared context.** `createEffectInstance` (`effectFactory.ts`) calls playout's `getGlobalContext()` before constructing the Tone effect. Tone nodes belong to whatever context is current at construction, and playout's global context only replaces Tone's default one when first requested — which the provider does after its engine loads. An effect added before that (a default effect on mount, as the effects example does) was built on Tone's default context and could never be wired to a track: `InvalidAccessError: cannot connect to an AudioNode belonging to a different AudioContext`, playlist stuck in `loading`. Any new code that constructs Tone nodes ahead of the provider needs the same call first.

**A track's effects function reaches the adapter through the provider's `trackEffects` prop (#752):** `trackEffects={getTrackEffectsFunction}`, forwarded by `resolvePlayoutAdapter` to `createToneAdapter({ trackEffects })` as ONE stable lookup (`resolveTrackEffects`) that reads the latest prop from a ref. The prop's identity is therefore not a dependency of the engine effect (an inline arrow rebuilds nothing), and a different function for a track that is already built applies at that track's next build. With `createAdapter` the prop does nothing, like `effects`: the consumer passes `trackEffects` to their own adapter.

**Track chains end at the track's fader (#660), not the master.** The track's effects function is `rack.attach(trackInput, faderInput)`: `trackInput → effects → faderInput`. The function `attach` returns is the cleanup: it disconnects every instance from that `faderInput` (targeted — instances outlive the track and are reused when the adapter rebuilds it, so without this each `setTracks` left one more edge into a dead fader) and forgets the attachment only if it is still the one it made (a rebuilt track may have attached first).

**Offline rendering:** `rack.renderOffline(from, to)` behind `createOfflineEffectsFunction()` / `createOfflineTrackEffectsFunction(trackId)`. It reads the chain WHEN THE EXPORT RUNS, not when the function was obtained (consumers obtain it in a render, and nothing re-renders on a chain change any more), and with no active effect it connects straight through, so the functions are never `undefined`. `buildOfflineChain` (`offlineChain.ts`) re-creates Tone effects on the offline context, re-instantiates WAM entries with `cloneInstanceInto` and the live `getState()`, and for custom entries awaits `ensureEffectPrepared(type, offlineRawContext)` before creating (an AudioWorklet module must be added to every context). Bypassed entries are left out whichever way they are bypassed. Any failure disposes what was built and rejects: an export never silently renders without an effect the live chain has.

**Testing:** `effectsRack.test.ts` drives the rack directly with `tone` and playout mocked (assert on Tone's `connect`/`disconnect` mocks; custom definitions return plain objects as nodes). `effectsHooksStore.test.tsx` counts renders and checks identities. Real audio is covered by `e2e/custom-effects.spec.ts` on `/examples/wam-effects` (native mode), two ways. (1) It compares exported WAVs: two exports of the same chain differ by about 4e-7 RMS (not 0), the demo tremolo on the master by about 0.16. (2) It reads the LIVE signal at the worklet's output during playback (`tapTremoloOutput`): an init script wraps `AudioNode.prototype.connect` and, whenever the tremolo's `AudioWorkletNode` is connected to anything but an analyser, also connects it to one shared `AnalyserNode` on `window.__tremoloTap`. The tap is made again on every connection because a rewire disconnects ALL outputs of every instance, the tap included. The test expects signal while the effect is on and none while it is bypassed, then signal again after un-bypass. That last step is what caught the worklet `return false` problem: the first demo processor returned `false` from `process()` to let itself stop, and in Chrome a processor that returned false while nothing was connected (bypass by disconnection) did not run again when reconnected. The export comparison could not see it (an offline chain is built fresh). The processor now returns `this.alive`, cleared by a `'dispose'` port message from the definition's `dispose` (see `website/CLAUDE.md`).

**Documentation:** `website/docs/react/guides/effects.md`, `website/docs/faust-effects.md`

## WAV Export (useExportWav)

**Single render path:** Export renders via `renderToneOffline()` (`src/utils/renderToneOffline.ts`), a hand-rolled `Tone.Offline` equivalent. It wraps a native `OfflineAudioContext` in a Tone `OfflineContext` when `isNativeGlobalContext()` is true (required to host WAM worklets offline), and constructs the standard `OfflineContext` otherwise. The previous global Tone context is restored in a `finally` block — unlike upstream `Tone.Offline`, a build that throws can't leave the offline context installed as the app's global context. Renders are serialized through a module-level promise queue: the async graph build (WAM host init + clone can take 100ms–1s) makes overlapping `getContext()`/`setContext()` swaps a real risk — a concurrent second export would capture the first's offline context as "previous" and restore a spent `OfflineAudioContext` as the global context. The offline graph mirrors the live playback topology (`Player → fadeGain → trackInput → [track effects] → trackVolume → trackPan → trackMute → masterVolume → destination`) — track effects are PRE-FADER inserts (#660): the offline track effects function is called as `trackEffects(trackInput, trackVolume, true)`, and the pan stage is core's `createPanStage(context.rawContext as BaseAudioContext, state.pan, trackChannelCount(track))`, joined to the Tone graph with `connect(stage.output, trackMute)` from `tone` — the same 2×2 gain-matrix stage live playback uses instead of a Tone `Panner`, so a stereo effect on a mono track stays stereo offline too. Master and per-track effects chains are conditionally inserted when provided, and their cleanups (destroying offline WAM clones) run in a `finally` block regardless of success or failure.

**Why single path:** Previously had a native `OfflineAudioContext` path (no effects) and a `Tone.Offline` path (with effects). The dual paths diverged — the native path used `StereoPannerNode` (correct stereo) while the Tone path used `Panner` without `channelCount: 2` (stereo→mono downmix). Unifying prevents this class of bug.

**Pan law from source:** pass `trackChannelCount(track)` from core to core's `createPanStage(context.rawContext, pan, count)` (native nodes on the raw offline context; `connect(stage.output, toneNode)` from `tone` makes the native → Tone edge) — it selects the mono or stereo pan law. Hardcoding `2` gives mono tracks the stereo law (+3 dB at centre); hardcoding `1` gives stereo tracks the balance law (−3 dB at centre).

**Output channels from source:** `Offline()` output channel count is derived from `trackChannelCount` across all rendered tracks — not hardcoded to 2.

**Fade types:** All 4 types (linear, exponential, logarithmic, sCurve) are applied with `applyClipFades()` on the native `AudioParam` of the clip's Tone `Gain`, reached through public API: `fadeGain.input.gain` (not the private `_param`; see playout's CLAUDE.md).

## Web Worker Peak Generation

**Decision:** Generate `WaveformData` in a web worker at load time, then use `resample()` for near-instant zoom changes.

**Key files:**

- `src/workers/peaksWorker.ts` — Inline Blob worker (portable across bundlers)
- `src/hooks/useWaveformDataCache.ts` — Cache hook, watches tracks for clips with `audioBuffer` but no `waveformData`
- `src/waveformDataLoader.ts` — `extractPeaksFromWaveformDataFull()` for resample + channel extraction

**Peak resolution order (`src/utils/derivePeaks.ts`):** (1) `clip.waveformData` (external pre-computed), (2) worker result for `clip.audioBuffer`, (3) empty peaks while worker runs.

**Peaks and duration are derived during render, never set by an effect (#692).** `duration = useMemo(timelineDuration(tracks))`; `peaksDataArray = useMemo(derivePeaks(...))` over `tracks`, `samplesPerPixel`, `mono` and the worker hook's `version`. `derivePeaks` is a pure function that takes the previous pass (`PeaksCache`, held in `peaksCacheRef`) and reuses three identities, each of which something downstream is keyed on: a clip's typed arrays (`Channel` redraws when they change), its `ClipPeaks` object, and its track's array. The typed arrays are reused while the clip's source waveform data, `offsetSamples`, `durationSamples`, `sampleRate`, `samplesPerPixel` and `mono` are unchanged. Entries are found by clip id and compared on the waveform data's identity (split clips share one buffer but differ in offset and duration); a clip that gets a new id always recomputes. So a trim gives new arrays to the trimmed clip only, and a move gives a new `ClipPeaks` with the same arrays. Do not add a field to `ClipPeaks` without adding it to `sameClipPeaks`, or a change to it will not reach the screen. Measured on `/examples/multi-clip` (14 canvases) during a trim: 26 canvas redraws and 3 React commits per pointer move before, 1 and 1 after.

**`useWaveformDataCache` has one piece of state, `version`.** Results live in a `WeakMap<AudioBuffer, WaveformData>` read during render through the stable `getWaveformData(buffer)`; `version` is bumped when a job finishes and is the dependency that makes the peaks memo look again. A `tracks` change over already-generated buffers sets no state (the old `Map<clipId, WaveformData>` state was rebuilt on every `tracks` change, one extra render per trim move). A job keeps running across `tracks` changes; only unmount forgets in-flight jobs, because terminating the worker rejects them (a StrictMode remount then starts them again).

**Automatic:** Any clip with `audioBuffer` (loaded or recorded) gets worker treatment — no opt-in needed.

**A failed job is retried on the next `tracks` change, three attempts per buffer.** A crashed worker is replaced, so a retry can succeed; a buffer that can never succeed (a CSP that blocks blob workers) used to be copied and sent again on every `tracks` change, i.e. every pointer move of a trim. Rejections caused by the unmount's `terminate()` are not counted.

## Pre-Computed Peaks Rate Mismatch

When `clip.waveformData.sample_rate` differs from `clip.sampleRate` (e.g., after `audioBuffer` decodes at hardware rate), Path A in `derivePeaks` converts `offsetSamples`, `durationSamples`, and `samplesPerPixel` to the waveformData's sample space using `ratio = wdRate / clipRate`. This prevents blank peaks when the clip is rebuilt at the decoded audio rate. Path A wins whenever it succeeds, and the worker skips clips that have `waveformData`, so these peaks stay until the clip loses its `waveformData`. `createClip` (called by both direct callers and `createClipFromSeconds`) logs a per-clip warning with the clip name.

## Memo Boundaries in the Visualization (#693)

`WaveformRoot` is the shell (`PlaylistVisualization` only composes it with its parts, see "The View Is a Root With Parts"): sizes, the shared vertical layout, the selection-drag pointer handlers and `PlaylistInfoContext`. It does not subscribe to the selection (#733), the resting cursor position, the active annotation (#740, both in the sections below) or the selected track (#685: the tracks part and the controls part read that), so it renders when playback starts or stops, on its own state (a drag in progress, the settings modal, the measured container width), on timeline, zoom, view, theme and spectrogram-integration changes, on a reorder drag-over, on a recording layout step, and whenever the component that composes it renders. What it renders is split so that this is cheap:

- `TracksPart` → `TrackRow` → `ClipView` (`components/TrackRows.tsx`) and `TrackControlsPart` → `DefaultTrackControls` (`components/TrackControlsColumn.tsx`). `TrackRow`, `ClipView`, `TrackControlsPart` and `DefaultTrackControls` are `React.memo`; `TracksPart` is not (it has children). None reads selection, cursor or annotation state. What a row or a clip is handed is primitives, stable callbacks, and the identity-stable pieces of `peaksDataArray` from `derivePeaks` (#692).
- `SelectionOverlay`, `PlayheadOverlay`, `AnnotationBoxesOverlay`, `LoopRegionOverlay` (`components/VisualizationOverlays.tsx`) read that state from context themselves.
- In `ChannelWithProgress`, only the inner `ClipProgress` overlay subscribes to the provider's contexts (`useIsPlaying`, `usePlaybackRefs`, `useCurrentTime`, `usePlaylistView`, `usePlaylistZoom`). The channel itself must not: `ClipProgress` calls `useCurrentTime()` (so it renders per move of a leftward selection drag).

Rules when changing these files:

1. Everything in the root's two layout values (`components/waveformLayoutContext.ts`) and everything the tracks part hands a row must keep its identity across a render that did not change it. `selectTrack` reads `tracks` through a ref for this reason; both layout values and the `PlaylistInfoContext` value are `useMemo`'d; track heights depend on the recording's track id and channel count, not on `recordingState` (a new object literal on every render of the consumer).
2. `recordingState` is passed down to the armed track's row only (`undefined` for the others). Since #695 it holds a `progress` source instead of per-frame values, so a recording frame re-renders the preview clip only, and `displayDuration` grows in 10-second steps (see "60 Hz Values Are Sources"): every row gets a new `width` once per step, not once per frame.
3. Pass track fields (`trackId`, render mode) rather than the `track` object: track objects are replaced by engine statechanges and by consumers.
4. `renderTrackControls(trackIndex)` is called inside the memoized controls part, so it runs when that part renders (the root's rows value, so tracks, peaks and layout; mixer state; the selected track; a reorder; the spectrogram integration; the theme; `onRemoveTrack`, `trackReordering`, the function itself) and not on time-selection or cursor changes. An `onRemoveTrack` or `renderTrackControls` with a new identity per consumer render re-renders every panel, as before; consumers get the benefit only with stable functions.

`visualizationMemoBoundaries.test.tsx` counts renders with wrappers around the real `Clip`, `SmartChannel`, `Track`, `Controls` and `SmartScale`. `SmartChannel` is the proxy for `ChannelWithProgress` renders including context-triggered ones. Measured on `/examples/multi-clip` (7 tracks, 13 clips): about 440 component renders per pointer move of a selection drag before, 31 (dragging right) and 63 (dragging left) after.

## Selection Has Its Own Context (#733)

`selectionStart` / `selectionEnd` live in `SelectionContext` (`useSelection()`), not in `PlaylistStateContext` (which #768 has since split into several). They are the only state that changes on every pointer move of a selection drag; in the state value they re-rendered every `usePlaylistState()` consumer per move (annotation list, annotation boxes, loop button, a consumer's own app component).

- Call `useSelection()` only in a component that shows or uses the selection: `SelectionOverlay`, `PlayheadOverlay`, `SelectionTimeInputs`, `SetLoopRegionButton`, and `usePlayFromSelectionOrCursor` (so `PlayButton` and `KeyboardShortcuts` render per move; measured about 0.04 ms together, dev build).
- The provider itself still renders per move (selection is its React state); its `children` are stable, so only context consumers follow.
- The drag (`useSelectionDrag`) takes the anchor from `pressTimeRef` (set at mouse-down), never from `selectionStart`. `selectionStart` is `min(anchor, pointer)`, so it stops being the anchor once the pointer passes left of it: until #733 a leftward drag selected only the last pointer movement.
- `MediaElementPlaylistProvider` renders the same `SelectionContext` (#688, part 2), so `useSelection()` works under it; its view uses the same hook, which stores the range ordered (#688). Both views render the same `SelectionOverlay` (part 3).
- `setSelection` also sets `currentTime`, so a LEFTWARD drag changes the resting cursor position per move; that has its own context since #740 (next section).

Measured per move of a rightward drag (dev build, `probes/select733.cjs`, which adds render time to the fiber-walk count): multi-clip 31 components to 9; annotations example (15 annotations) 369 to 17, React render at 4x CPU throttle 19.8 ms to 1.5 ms. Leftward: multi-clip 63 to 54, annotations 371 to 370. Guarded by `contextValueStability.test.tsx` (identities and render counts) and the drag-direction tests in `e2e/multi-clip.spec.ts`.

## Resting Cursor Position and Active Annotation Have Their Own Contexts (#740)

`currentTime` lives in `CurrentTimeContext` (`useCurrentTime()`), not in `PlaybackAnimationContext`. `activeAnnotationId` lives in `ActiveAnnotationContext` (`useActiveAnnotation()`), not in `PlaylistStateContext`. (Both of those larger contexts were split further in #768, next section.)

- `currentTime` is the RESTING position (seek, pause, stop, a selection whose start moves). It does not advance during playback; `currentTimeRef` and frame callbacks do that. The animation value now changes only when `isPlaying` does.
- A context subscription is to the whole value. Before the split, a component that read only `currentTimeRef` or `isPlaying` still rendered on every seek; changing the annotations example to read the ref alone did not change its render count at all. That is why the fix had to be in the provider and not in consumers.
- `ClipProgress`, `AnimatedPlayhead`, `CustomPlayhead` and `AudioPosition` call `useCurrentTime()` for the re-render only. They position from `visualTimeRef` / `currentTimeRef` in an effect without dependencies, so without the call they would not move on a seek while stopped. Any new component that shows the resting position needs the same call (tests: "still follows a seek while stopped" in `visualizationMemoBoundaries.test.tsx`).
- `useActiveAnnotation()` is called by `AnnotationBoxesOverlay`, `PlaylistAnnotationList` and `KeyboardShortcuts` only, and under the MediaElement provider by `MediaElementAnnotationList` and `MediaElementAnnotationBoxes`.
- Both annotation renderers memoize their items, so an active-annotation change renders the item that stops being active and the one that becomes active, not all of them: `AnnotationBoxItem` in `components/AnnotationBoxes.tsx`, and `AnnotationListItem` inside `AnnotationText` (annotations package). - A new field goes into the value whose other fields change when it does, never into the nearest one. A field that changes on its own gets its own context. Add the field to the "has exactly the documented fields" case in `contextSplitByChangeRate.test.tsx`, which also states, per action, exactly which hooks' readers render; that file is the contract.
- `timeFormat` and `isAutomaticScroll` have their own value (`usePlaylistSettings()`) for that reason. The first version of #768 put them in the view value to save a context; toggling automatic scroll on `/examples/multi-clip` then rendered 58 components where it had rendered 32 before the split, because every `ClipProgress` and the shell read the view value for `sampleRate`. Measure the action a field changes on before choosing its group, on a page with many clips.
- The old hooks were removed, not slimmed. A hook kept under its old name with fewer fields hands `undefined` to a plain-JS consumer with no error; a missing export throws at the first render. The one exception is `usePlaybackRefs()` (#688, part 2), which kept its name and lost eight fields; a leftover read of one is `undefined` (the maintainer had the throwing getters removed in part 3), see "One Set of Context Objects for Both Providers". Do not add a hook that merges several of these values "for convenience": it would re-render for all of them, and it would be a second source for the same fields.
- `usePlaylistViewOptional()` / `usePlaylistZoomOptional()` (exported from the context file, NOT from the package) return `null` where no provider is above; only `useAnnotationKeyboardControls` uses them, because it may also be called outside a provider with explicit options. Both providers render the two contexts, so under either one they return the value.
- Who reads the hot values: `usePlaylistTimeline()` is read by the view's root (and by no part of the view: they take `tracks` and the peaks from the root's rows value), `ClipInteractionProvider`, `KeyboardShortcuts`, `SpectrogramProvider`, `ExportWavButton` and `LoopButton` (it reads `duration` for its click handler). `FastForwardButton` and `SkipForwardButton` no longer read it (#688, part 2: they call `seekTo`, which clamps). `usePlaylistMixer()` is read by the controls part (`TrackControlsPart`; not by the root above it, so a slider step renders the column and one panel), `MasterVolumeControl` and `ExportWavButton`.
- A queued play shows later than it did: `play()` during an engine rebuild sets the time refs without setting `currentTime` state (the two `setCurrentTimeRefs` calls in `play()` are the only ones not paired with `setCurrentTime`). Before #768 the playhead, `ClipProgress` and `AudioPosition` jumped to the queued start when the rebuild finished, only because they read the data value and it changed then; now they move when `isPlaying` turns true (and stay put if the queued play never starts because the build failed). Found by reading in review, not reproduced in a browser; the maintainer was told. Do not "fix" it by adding a timeline subscription to those three components.

It is not called at all while a range is highlighted at rest. Until #685 it was also called on every render of the shell, so on every timeline change, track selection and reorder drag-over even when the composing component stood still; on the example pages that component holds the tracks and renders with them anyway. A first draft of the #768 upgrade guide claimed more than was true and review caught it: read the parent's subscriptions before writing when a render prop is called.
- `Waveform` reads no context. The "render the list only when there are annotations" test is in a child, `AnnotationListWhenPresent`, as in `MediaElementWaveform` (#744). Nothing counts `Waveform`'s own renders in a unit test.
- `PlaylistInfoContext` (ui-components) has no `duration`: every `Track`, `SmartChannel` and `ChannelWithProgress` reads that context, and the length changes on each pointer move of a trim at the end of the timeline. `SmartScale` takes `durationMs` as a prop; the memoized `TimescalePart` reads `displayDuration` from the root's extent value.
- The MediaElement provider renders the shared context objects since #688, part 2; its four public hooks (`useMediaElementAnimation/State/Controls/Data`) and its two internal contexts are gone. See "One Set of Context Objects for Both Providers".

Known equivalent mutant: removing the cursor write at an annotation's end in the WebAudio loop changes nothing, because the engine's stop mirror writes the same position.

**The MediaElement provider's init effect cleanup sets `isPlaying` false** (maintainer's decision in the review of #769). The cleanup stops the loop and disposes the playout, and it runs whenever one of the effect's dependencies changes: the track's `source`, `waveformData`, `name`, `fadeIn` or `fadeOut`, `audioContext`, the `playbackRate` or `preservesPitch` props, or an inline `onReady` / `onError` / `createPlayout` on a parent that re-renders. Until #769 it left `isPlaying` true: the UI showed "playing" with no audio and no loop. The playhead's own loop used to hide part of that (it kept redrawing `currentTimeRef`); with the single loop nothing would draw at all, since the resting position is drawn only while not playing. Playback does not resume on the new player. **Position and active annotation are reset only for new audio** (maintainer's choice, 2026-11-11): each run of the effect captures the `source` and `waveformData` its player is for, and its CLEANUP compares them with the latest committed render's (`latestAudioRef`, written in a layout effect so that a render React discards cannot leave uncommitted audio in it; layout effects run before the passive cleanups of the same commit): when either differs it sets `currentTimeRef` and `currentTime` to 0 and clears the active annotation, playing or not. The same audio in a new player (a new name, fades, the pitch setting, `audioContext`, a callback's identity) keeps both, and the cleanup sets `currentTime` to `currentTimeRef` (during playback only the ref advances), so the next Play continues from where the listener was and a consumer that shows `currentTime` is right. The reset is in the cleanup on purpose: React runs every passive-effect cleanup of a commit before any passive effect, so a child's `useEffect` that restores a saved position for the new source (`seekTo`, `setActiveAnnotationId`) runs after the reset and wins. A first version reset at the start of the effect body, after the children's effects, and overwrote them (found in review). A child's layout effect still runs before the cleanup and is overwritten. **`seekTo` clamps to `latestAudioRef.current.waveformData.duration`, not to the `duration` state** (which is 0 until the first player is ready, and the previous file's length while the next loads and inside `onReady`): with the state, a restore into a longer file was cut off at the old length and a restore for the first file went to 0 (found by a side agent and the review of the fix). A `seekTo` before the player is ready is therefore stored; when the player arrives the init moves it to `currentTimeRef` if that is above 0 (so `pause()`, which reads the player's time, and the media element's own `timeupdate` agree with the cursor before Play), and Play starts there. While the player loads, `currentTime` can be larger than `duration`. Checked in a real browser: `/examples/media-element?t=8` (`StartAtQueryTime` in the example seeks from a child effect before the player exists) and "a start position set before the player is ready…" in `e2e/media-element.spec.ts`, which shows 0:00 against the provider from before the clamp change. Known edges, left: a child effect that READS `currentTimeRef` on a source change sees 0, not the old position (save the old position in its cleanup, which runs before the provider's); with the provider inside a hidden `<Activity>`, a track change made while hidden is not reset on reveal (no cleanup runs then); a child's layout-effect `seekTo` clamps to the previous file's length (visible only on an `<Activity>` reveal after a track change made while hidden; on an ordinary track change the reset overwrites it anyway). The selection is kept in both cases. `waveformData` is compared by identity: an object rebuilt on every render counts as new audio each time (and already recreated the player each time). Tests: the "new audio…", "the same audio in a new player…", "a child's own effect…", "a restore into a longer file…", "a restore from onReady…", "a seek is still clamped…", "the selection is kept…" and "unmounting the provider…" cases in `mediaElementSharedLoop.test.tsx`. Pass the track from a `useMemo` or state: inline `fadeIn` / `fadeOut` objects replace the player on every render of the parent, like inline callbacks. Pass `onReady` / `onError` / `createPlayout` as stable functions: an inline one recreates the player on every render of the parent, which now visibly stops playback.

A callback that throws inside `runFrameCallbacks` stops the whole loop, as it always has in the WebAudio provider.

## MediaElement Playback Follows the WebAudio Rules (#688, part 1)

The maintainer chose, question by question (2026-11-11), that `MediaElementPlaylistProvider` behaves as `WaveformPlaylistProvider` does, so that one control can serve both. This step left the public hook names unchanged; part 2 ("One Set of Context Objects for Both Providers") replaced them with the shared ones.

- **`restAt(cursor)` is the one way playback ends.** It pauses the player and seeks it to `cursor` (never the engine's `stop()`, which rewinds the element to 0), stops the loop, sets `isPlaying` false and writes the cursor. Stop, the end of the audio (`setOnPlaybackComplete`), the end of an annotation and the end of a range all go through it. The player's own time must agree with the cursor because the element reports its position back (`timeupdate` writes `currentTimeRef`).
- **Three refs describe the play that is running or queued**, with the WebAudio provider's meanings: `playStartPositionRef` (where Stop and the ends return the cursor; the selection's start for selection playback, even when resumed part-way), `playbackEndTimeRef` (a bounded play's end, or null) and `isSelectionPlayRef`. `play()` sets all three; `seekTo` and `setSelection` replace them. The engine's own duration timer (`playout.play(when, offset, duration)`) is NOT used: it is a `setTimeout` that does not follow a pause or a rate change.
- **`endPlaybackIfDue(time)` runs from two places**: the animation loop on every frame, and the engine's `timeupdate` event (about four times a second, also in a hidden tab, where animation frames stop while the audio goes on). It must stay idempotent for one position. Maintainer's choice C: the fallback covers ranges AND annotation ends, so the active-annotation highlight also advances while hidden. No automation here can hide a tab; the unit tests fire `timeupdate` with no frame run.
- **`seekTo` during playback restarts** (`playout.play(undefined, t)`), because the engine schedules fades in `play()`. While stopped it seeks the element and makes the position the new play start, so a Stop after it does not jump back to an older play's start. (The WebAudio `seekTo` does not reset its play start while stopped; only Escape or a Stop pressed while stopped can show that. Left as it is.)
- **`setSelection` moves the cursor to the start**, restarts a running play (a range as selection playback, a collapsed one open-ended) and re-points a queued play. While stopped it seeks the element only when the start moved: a rightward drag keeps its start and must not seek the media element per pointer move. A leftward drag does seek per move.
- **The drag in `MediaElementPlaylist` is the multitrack view's** (one hook since 2026-11-12, `useSelectionDrag`): ordered `setSelection(min, max)` per move while stopped; during playback nothing is committed before the release (see "The Selection Drag Commits on Release During Playback"). At this step the press was the seek.
- **A play asked for with no player is queued** in `pendingPlayRef` (position only; its end is `playbackEndTimeRef`) and started by the init effect when the player arrives. `playoutInFlightRef` is false only after an init has failed; it STARTS true and the init's cleanup sets it true again, because a child's effect (mount, or keyed on the track) runs before the provider's init effect and its `play()` must queue (first version: the flag was set by the init effect, so a mount-effect play was dropped in production and queued under StrictMode; found in review). Stop, Pause, new audio and a failed init clear the queue; a same-audio replacement keeps it. The request is changed in place by `seekTo` / `setSelection`. A queued play moves `currentTimeRef` to its start at once (as the WebAudio provider does); when it is cancelled by Pause or a failed init the `currentTime` state is brought up to the ref, and Stop does the same through `restAt`. The start happens outside the click that asked for it: fine in Chromium after any interaction with the page; Safari unverified.
- **A play that cannot go on ends playback.** The engine's `error` event (also mid-playback) and its `playrejected` event (new in `media-element-playout` with this change: the element's `play()` promise rejected with anything but an `AbortError`, or the AudioContext could not be resumed) call `restAt(currentTimeRef.current)` when playing. Not covered: with the `audioContext` prop the engine waits for `resume()`, which a browser may leave pending with no user gesture, so nothing is emitted and `isPlaying` stays true (#783, unverified in a browser). An `AbortError` is what a `pause()` or a newer `play()` does to a pending play; reporting it would end the play that replaced it. The error message carries the media error's code and text and NOT the source URL (it may hold a token; consumers show `error.message`).
- **Where playback comes to rest is the new play start** (`restAt` writes `playStartPositionRef`; the same-audio branch of the cleanup does too): a Stop pressed while stopped does not move the cursor. A pause is not a rest, so Stop after Pause returns to the play start; a pause followed by a same-audio replacement IS one (the cleanup writes the play start), and the cleanup does not write it while a play is queued (that play set its own, the selection's start for a queued selection resume; found in the second review). Maintainer's choice; the WebAudio provider does not do this (its Stop button is disabled while stopped).
- **The element's `ended` is ignored when playback has already been ended** (`!isPlayingRef.current` in the `setOnPlaybackComplete` callback). A range that reaches the end of the audio is rested at its end by the loop or by `timeupdate` first; `ended` then arrived and rested it again at the play start (found in review).
- **`duration` and peaks are derived during render**; `isReady` is state: true on the engine's `loadedmetadata` event, false again in the init effect's cleanup. `onReady` is called from the same event. The engine's `error` event becomes an `Error` for `onError` (plus a warning). Listeners are attached with `playout.on()` BEFORE `addTrack` (the engine attaches them when it creates the element), and each checks `cancelled`: a replaced player's late events are ignored. A `createPlayout` object without `on()` throws inside the init's `try` and is reported through `onError`.
- **Before the context split (part 2), a leftward selection drag re-rendered the whole MediaElement view per move** (50 and 56 components on the two example pages, 5 before part 1): the cursor follows the selection's start and `currentTime` shared a value with `isPlaying`. Since part 2 `currentTime` has its own context and the shell does not read it; the count after is under MEASUREMENTS in the part 2 section.
- Tests: `mediaElementPlaybackSemantics.test.tsx` (fake playout with `on`/`emit`, a player that can be held back or made to fail). A mutation run of 67 one-line changes (the script pattern is in the root notes) leaves one survivor: `restAt` clearing `playbackEndTimeRef`. I called it equivalent once and the review showed a path where it mattered (the `ended` event after a rest); that path is now closed by the `isPlayingRef` guard, and no other reader was found, but treat the line as load-bearing. The run also showed four dead lines and a dead field, which were removed. Known and left: with a suspended `AudioContext` the engine defers the element's start AND the move to the start position, so the first frame of a range can read the element's old position and end the range at once (the annotation form predates #688), and a Pause during the wait shows that old position as the cursor (the `restAt` or Pause cancels the waiting start, so at least no sound follows). Both are on #783: moving the element in `play()` before the wait would fix them, and it is the same start-up path; `isReady` may not turn true before the first play where the browser ignores `preload` (iOS, unverified), so nothing in the library waits for it. e2e: "Stop returns the cursor…", the two "during playback…" tests (a drag, a click) and "a source that cannot be loaded…" in `e2e/media-element.spec.ts` (the page plays `.opus` files: route on that, not `.mp3`), and the cursor check in "with continuous play off…" in `e2e/media-element-annotations.spec.ts`. An e2e test that the total time shows before the audio has loaded was dropped: it passed against the old provider too, which set `duration` when the player object was created, without waiting for the network.

## One Set of Context Objects for Both Providers (#688, part 2)

`src/contexts/playlistContexts.ts` holds every context object, its value type and its hook. `WaveformPlaylistProvider` and `MediaElementPlaylistProvider` render the SAME context objects for what they share, so a component written against `useIsPlaying()` or `usePlaybackControls()` works under either. The four `useMediaElement*` hooks, `usePlaylistControls()` and `usePlaylistAnnotations()` are removed, not aliased (the #768 rule: a missing export fails at import, a slimmed hook hands out `undefined`).

- **`usePlaybackRefs()` is the one hook that was slimmed and not removed**: it kept its name and four fields (`currentTimeRef`, `visualTimeRef`, `registerFrameCallback`, `unregisterFrameCallback`), and eight went to `useEngineRefs()`. The value is a plain object: a leftover `const { playoutRef } = usePlaybackRefs()` in plain JS reads `undefined`. Part 2 shipped throwing getters for the eight names (`playbackRefsValue()`); the maintainer had them removed in part 3 (2026-11-12): the upgrade guide is where a replacement is named, and a guard also breaks code that reads a name without depending on it. Do not bring them back.

- **The file imports no provider and no engine.** Its only value import is `createContext` / `useContext` from `react`; everything else is `import type` (also the two types it takes from `WaveformPlaylistContext`). A MediaElement-only bundle must not pull in the WebAudio provider through the hooks. Keep it that way: a helper that needs a provider's code belongs in the provider file.
- **`BLOCKED` is what a provider puts in a context it does not serve.** `WaveformPlaylistProvider` blocks the two MediaElement-only contexts (`PlaybackRateContext`, `MediaElementTrackContext`); `MediaElementPlaylistProvider` blocks the nine WebAudio-only ones (`EditorControlsContext`, `EngineRefsContext`, `AnnotationEditingContext`, `LoopContext`, `SelectedTrackIdContext`, `UndoRedoContext`, `PlaylistTimelineContext`, `PlaylistMixerContext`, `TrackReorderPreviewContext`). `useSlot` throws on the marker and names the provider that is needed and the one that is nearest, so a hook never reaches through one provider to an outer one of the other kind. A new provider-specific context must be added to the OTHER provider's blocked list in the same change, or nesting leaks. Outside any provider the default `null` gives "`<hook>` must be used within …" (both names for a shared hook).
- **Three internal optional readers, exported from the file and NOT from the package.** `useLoopOptional()` returns `null` on the marker (and with no provider): `usePlayFromSelectionOrCursor` uses it, because it starts playback under both providers and there is no loop under MediaElement. `usePlaylistViewOptional()` and `usePlaylistZoomOptional()` return `null` with no provider above: `useAnnotationKeyboardControls` uses them, because it may be called outside a provider with explicit `samplesPerPixel` / `sampleRate`. Do not add an optional reader so that a component can "work under both": give it a shared hook, or it belongs to one provider.
- **Which MediaElement components read what.** The `MediaElementPlaylist` shell reads `useIsPlaying()` and NOT `useCurrentTime()` or `useSelection()`, so a seek or a selection drag does not render the waveform. The parts that do follow the cursor and the selection are the shared ones (part 3, "One Playhead, One Progress Overlay, One Selection Highlight"): `ClipProgress`, `AnimatedPlayhead`, `CustomPlayhead`, `PlayheadOverlay`, `SelectionOverlay`.
- **The transport buttons are `seekTo` only.** `RewindButton`, `FastForwardButton`, `SkipBackwardButton` and `SkipForwardButton` call `seekTo(0)`, `seekTo(Infinity)` and `seekTo(currentTimeRef.current ± skipAmount)`; clamping and "restart when playing" are the provider's. They used to call `setCurrentTime(t)` and then `play(t)` when playing, which only the WebAudio provider has. That is why WebAudio `seekTo` no longer checks `engineRef.current` before calling `play(clampedTime)`: the buttons called `play` with the engine mid-rebuild, and `play` with no engine and a build in flight writes the request into `pendingResumeRef` (see "Engine Rebuilds vs Playback"), so the play that is waiting for the new engine starts at the new position. With the check, a button press during a rebuild would have moved the cursor only. `seekTo` still calls `play` only when `isPlayingRef.current`. It calls `play(clampedTime)` with no duration, so the re-pointed play is open-ended (`pendingResumeRef` gets no `endTime`): a waiting selection play loses its end, as for any `seekTo` during playback. The `0` shortcut (`rewindToStart` in `usePlaybackShortcuts`) is `seekTo(0)` too.
- **WebAudio `seekTo` lets a finite time past the end through in two modes** (`pastEndAllowed`: `Number.isFinite(time)` and `indefinitePlaybackRef.current || recordingActiveRef.current`, the latter true while `setRecordingActive(true…)` is in effect). `seekTo(Infinity)` (Fast Forward) still means the end of the audio, the result is never below 0, and otherwise the clamp is to `durationRef.current` as before. Reason: in those two modes the transport may run past the end of the audio, and `SkipBackwardButton` used to call `setCurrentTime`, which does not clamp. Once the button became `seekTo(currentTimeRef.current - skipAmount)`, the old clamp made Skip Backward from 30 s over 10 s of material land at 10 s and not at 25 s (found in the first review). Net change for a consumer: `seekTo` from code in those modes accepts a position past the end, and so does `SkipForwardButton` (it stopped at the end on `main`); the maintainer chose that for `indefinitePlayback` ("there is no finite end"), and `FastForwardButton` is disabled there (`usePlaylistView().indefinitePlayback`, always false under the MediaElement provider). A recording session without `indefinitePlayback` is treated the same by `seekTo`, but cannot disable the button (no context carries it); whether recording should require `indefinitePlayback` is an open question the maintainer raised (#785).
- **`StopButton` is disabled unless playing, under both providers** (maintainer's rule). After Pause it is disabled and the cursor stays at the pause point; `stop()` from code after a pause still returns the cursor to where playback started. The hand-built Stop on the MediaElement example pages was always enabled.
- **`PlayButton` is one component.** It starts playback through `usePlayFromSelectionOrCursor`, so under MediaElement it plays a highlighted selection as a range (part 1's selection playback) and from the cursor otherwise. `usePlayFromSelectionOrCursor` calls `useSelection()`, and its two callers are `PlayButton` and `usePlaybackShortcuts` (so `KeyboardShortcuts`). On a MediaElement page only `PlayButton` reads the selection that way: `KeyboardShortcuts` cannot mount there. The other `useSelection()` readers there are `SelectionOverlay`, `PlayheadOverlay` and `SelectionTimeInputs`.
- **`usePlaybackShortcuts()` throws under `MediaElementPlaylistProvider`**, as it did before the hook split (then because `usePlaylistControls()` did). After the split it read only shared hooks and would have run there, so it calls `useWebAudioProviderOnly('usePlaybackShortcuts')` first (internal, in the context file: a `useSlot` read of `EditorControlsContext`, which the MediaElement provider blocks). Reason, maintainer's decision: the hook listens on the window, a page may hold several single-track players, and what keys do for that player is not decided (#723, #730). `useKeyboardShortcuts` reads no context and `useAnnotationKeyboardControls` reads only the two optional readers, so a consumer can call both under the MediaElement provider; the latter, given a `scrollContainerRef` and no `samplesPerPixel` / `sampleRate`, now gets the two from that provider and scrolls to the active annotation (`samplesPerPixelProp ?? playlistZoom?.samplesPerPixel`: a passed option wins, and the nearest provider is read).
- **MediaElement `setSelection` orders its two times and clamps both** to 0…`latestAudioRef.current.waveformData.duration` (`clamp(Math.min(…))`, `clamp(Math.max(…))` at the top of the callback). Until the first review it stored them as given, which was enough while its only caller was the drag (already ordered). `SelectionTimeInputs` now calls it with typed times, which can be reversed or past the end, and the highlight, the cursor and what Play plays must be one range. The engine orders the WebAudio pair.
- **MediaElement playback speed: the latest instruction wins (maintainer, 2026-11-12).** The instructions are the `playbackRate` prop when its VALUE changes and `setPlaybackRate` (the user). The pieces: the `playbackRate` state (what `PlaybackRateSelect` shows) follows a changed prop during render (`ratePropSeen`, compared with `Object.is` because a NaN prop compared with `!==` set state on every render: "Too many re-renders"); `playbackRateRef` is written by `setPlaybackRate` and by a layout effect, which writes only a prop value it has not applied yet (`ratePropAppliedRef`). That check is load-bearing: the effect also runs with an unchanged prop (a StrictMode remount, a revealed `<Activity>`) and after a child's layout effect of the same commit, and without the check each of those put the prop's speed back over a chosen one (a version without it was found in the third review; it had the layout effect right and the check missing). A layout effect, because it is committed renders only and runs before any child's passive effect of the same commit, so a child that sets a speed in answer to a prop change is the later instruction and wins. The init effect then tells a new player `playbackRateRef.current`: always for a custom `createPlayout` (it is called with no arguments and learns the speed only there, so the prop now reaches a custom playout; on `main` it never did), and for the bundled engine only when the speed differs from the prop it was created at (its setter clamps to 0.25–4 and its constructor does not, so repeating the prop turned a prop of 5 into 4). History, four versions in one PR: on `main` every new player ran at the prop's speed under a select that kept the user's; the first fix remembered only the user's choice, so a prop changed from 1 to 2 created the player at 2 and set it straight back to 1; the second told the player only when the ref differed from the prop, which left a custom player at its factory's speed; the third told every player and wrote the ref on every layout-effect run. Left as they are: a child's LAYOUT effect that sets a speed in the commit of a prop change shows in the select but the new player gets the prop's (same on `main`); a prop change and a `setPlaybackRate` in one batch leave the prop's speed; a `setPlaybackRate` call made into a hidden `<Activity>` after a prop change made while hidden is lost for the player on reveal (the state follows the prop in the hidden render, `ratePropAppliedRef` only when layout effects run again, so on reveal the layout effect writes the prop over the call's speed; it needs a call from outside the hidden tree); a custom `createPlayout` that returns the package's own `MediaElementPlayout` is told through the engine's setter, which clamps to 0.25–4, so a prop outside that range plays clamped under a state that shows the prop (the last two found in the fourth review round, by reading). Tests: the "review fixes" block of `sharedPlaybackInterface.test.tsx` (custom playout) and `mediaElementBundledRate.test.tsx` (the bundled path, with `resolveMediaElementPlayout` mocked).
- **Reading only shared hooks means not throwing under the other provider**: `useClipDragHandlers` (its one context read is `usePlaylistView()`) under MediaElement, `MediaElementAnnotationList` under `WaveformPlaylistProvider`. Not a supported use; a hook that must not run under the other provider needs an explicit guard like `useWebAudioProviderOnly`.

## The View Is a Root With Parts (#685, step 1)

`PlaylistVisualization` keeps its props and is the default composition: `<WaveformRoot>` with one part per thing that is drawn, each prop handed to the part it configures. It reads no context. Nothing new is exported yet (the parts become public when they also serve the MediaElement view).

| Part (internal name) | File | Drawn in | Options |
| --- | --- | --- | --- |
| `TimescalePart` | `waveformParts.tsx` | timescale strip | `renderTick` |
| `LoopRegionPart` (= `LoopRegionOverlay`) | `VisualizationOverlays.tsx` | timescale strip | none |
| `TrackControlsPart` | `TrackControlsColumn.tsx` | controls column | `renderTrackControls`, `onRemoveTrack`, `trackReordering` |
| `TracksPart` | `TrackRows.tsx` | tracks area | `gainScaled`; children `ClipHeadersPart`, `FadesPart`, `RecordingPreviewPart` |

- **The root sorts its children by part type** (`sortWaveformParts`): the two timescale parts go to the timescale strip, the controls part to the controls column, everything else stays in the scrolling tracks area in order. Fragments are looked through. A part wrapped in another component is not recognised and lands in the tracks area. Every top-level child keeps one position in the tracks area (`null` when it is drawn elsewhere or switched off), so `{flag && <Part />}` does not remount the tracks-area parts after it. That does not hold inside a fragment whose number of children varies, and the timescale strip and the controls column are compact lists: switching an earlier part off there remounts the later ones (the loop region after the timescale). `PlaylistVisualization` always renders all of them.
- **`ClipHeadersPart`, `FadesPart` and `RecordingPreviewPart` are markers that render nothing.** The tracks part and the root both find them with `scanTracksParts`. The maintainer chose markers over children rendered inside every clip after a prototype on `/examples/multi-clip`: with real per-clip children written inline, a trim rendered 384 components per move against 94, because new children on every parent render re-rendered every clip (three `useDraggable` hooks each). The header is structural as well: it adds to the row height the root must know before anything is drawn, and in ui-components' `Clip` it is what switches the clip's dragging and trim handles on (maintainer's choice: keep that).
- **A part is the component that draws, not a wrapper that forwards to one.** A first version put a forwarding component around `TrackRows`, `TrackControlsColumn` and the two overlays; whole-view renders (zoom, a trim that changes the length) then cost up to 6 components more than before. With the parts reading contexts themselves the extra is 1 to 3 (measured below).
- **Why a render of the root does not render the parts:** the part elements are passed on to `Playlist` exactly as the root received them, never cloned or re-keyed, so on a render of the root alone React sees the same elements and skips them. The `useMemo` around the sort only saves the sorting. `React.Children.toArray` would have cloned every element to give it a key; the lists are spread as the children of one fragment per place instead.
- **Two layout values, by what changes them** (`waveformLayoutContext.ts`, internal): the extent (`displayDuration`, `tracksFullWidth`) is the only layout value the timescale, the loop region and the annotation row read (the tracks part reads it too, for the row width); the rows value (`tracks`, the peaks, heights, tops, `animateTrackLayout`, render modes, spectrogram helpers, `selectTrack`, the settings-modal opener, the recording's channel count, `showClipHeaders`) is read by the tracks and the controls. One value would render the timescale on every trim move.
- **The root is the only reader of `usePlaylistTimeline()` in the view.** The tracks part and the controls part take `tracks` and `peaksDataArray` from the rows value. A first version had both call `usePlaylistTimeline()`; that value also changes when `isReady` flips and when `onTracksChange` is a new function, so both parts rendered for those too (found in review: with an inline `onTracksChange` and a provider re-render, `renderTrackControls` ran three times per track where it had run once; the once is the mixer state, which the provider publishes again because a new `onTracksChange` re-runs its loading effect). ## Annotation Edge Drag: Preview Source, One Report per Drag

Both providers create one `annotationPreview` (`ValueSourceHandle<AnnotationData[] | null>`, in the controls value, stable). `useAnnotationDragHandlers({ preview })` publishes each move to it and calls `onAnnotationsChange` once, on release; without `preview` it reports every move, as before. The components that draw annotations read `useAnnotationsWithPreview(annotations, annotationPreview)`: `AnnotationBoxesOverlay`, `MediaElementAnnotationBoxes`, `PlaylistAnnotationList`, `MediaElementAnnotationList`. Nothing else follows the preview: the engine, the animation loop's annotation lookup and `KeyboardShortcuts` see the committed annotations until release.

- Each move is applied to the RESULT OF THE PREVIOUS MOVE (the preview's snapshot, or the current `annotations` without one), not to the annotations at drag start. That is what lets an edge dragged into a separated neighbour pick it up and carry it along with Link endpoints on (#747, tried by hand by the maintainer); computing from the drag-start snapshot, as dawcore's `AnnotationDragHandler` does, loses that and failed `e2e/media-element-annotations.spec.ts`. The snapshot (`dragRef.current.snapshot`) is kept for Escape only: it is restored (no preview) or the preview is dropped (with one), so every annotation the drag moved goes back (maintainer's decision, 2026-11-11).
- The release commits and clears inside one `flushSync`. Cleared first, or committed in a later render than the clear, the boxes would show the old positions for a frame.
- The hook's handlers read `annotations` and `onAnnotationsChange` through refs, so they keep their identity for the whole drag.
- `AnnotationText` (annotations package) reads the list through a ref in its edit and control handlers. They are props of every memoized row; built from the array they re-rendered all rows whenever one annotation changed.
- Known edge: with a preview, the release commits the previewed array as a whole, so a change made to `annotations` by something else during the drag (a keyboard nudge, a text edit) is overwritten. Without a preview each move builds on the current `annotations` and such a change survives.
- Not covered by a unit test: the `flushSync` on release (two plain calls pass every test; a missing frame cannot be seen in jsdom).
- The WebAudio side has no built-in drag wiring: the consumer calls the hook (see the annotations examples), so the gain there is opt-in. The MediaElement boxes always use the preview.

Measured on `/examples/annotations` (15 annotations, dev build, 4x CPU throttle, `probes/close704.cjs … boundary`), per pointer move: 312 components / 18 ms React render before (all under the example's own root component, which holds the annotations); 47 / 4 ms after (the list shell and the boxes shell with the items that moved).

## Recording Preview Rendering Path

**Two paths for recording data:**

1. **Live preview** — `RecordingPreviewClip` (`components/TrackRows.tsx`) subscribes to `recordingState.progress` and renders its peaks directly, one `ChannelWithProgress` per channel. Bypasses the `WaveformPlaylistContext` peak generation pipeline entirely.
2. **Post-recording** — clips go through `derivePeaks` (Path A/B/C), which applies `mono` merge via `extractPeaksFromWaveformDataFull`.

Both paths must respect `mono` flag consistently. Live preview slices to first channel when `mono` is true. `recordingState.bits` flows through to the renderer (not hardcoded).

**Live preview must strip latency** — Playhead uses audible time (raw − `outputLatency` − `lookAhead`); preview peaks must drop the leading-silence portion to match. Compute `latencyOffsetSamples = (outputLatency + lookAhead) * sampleRate`, slice each channel via `subarray(latencyPixels * 2)` (each pixel is min/max), and reduce the preview clip's `durationSamples` by `latencyOffsetSamples`. Container `startSample` stays raw — only the audio data shifts. Mirrors `useIntegratedRecording`'s finalization compensation (PR #384).

**`durationSamples` must be zoom-independent:** Use `duration * sampleRate`, not peaks-derived calculations that depend on `samplesPerPixel` (which changes on zoom).

## Refs for Dynamic Audio Callbacks

**Problem:** useCallback with state dependencies creates stale closures when callbacks are stored and called later.

**Solution:** Store current state in a ref, read from ref inside callback:

```typescript
const tracksRef = useRef(tracks);
tracksRef.current = tracks; // Update on every render

const selectTrack = useCallback((index: number) => {
  const current = tracksRef.current; // Fresh state
}, []); // Stable function - no dependencies
```

**Applied in:** `WaveformPlaylistContext` track controls (`tracksRef`), `WaveformRoot`. The effects hooks used this until #679; their state now lives in an `EffectsRack` store read at call time (see "Audio Effects Architecture").

## Smooth Playback Animation Pattern

**Problem:** React state updates during playback cause flickering. Components need 60fps updates.

**Solution:** Single `requestAnimationFrame` loop in `WaveformPlaylistContext` drives all visual updates via the **Animation Frame Registry**. Components register per-frame callbacks via `registerFrameCallback(id, cb)` / `unregisterFrameCallback(id)` from `usePlaybackRefs()`. Direct DOM manipulation via refs — no `setState` in the loop.

**FrameData:** The animation loop computes `FrameData { time, visualTime, sampleRate, samplesPerPixel }` once per frame and passes it to all registered callbacks. Callbacks must read `sampleRate`/`samplesPerPixel` from `FrameData`, not from closed-over render values — avoids stale closures during zoom changes.

**Consumers:** `AnimatedPlayhead`, `AudioPosition` and `ChannelWithProgress`'s `ClipProgress` (id: `useId()` — unique per instance; the registry is a `Map`, so two components under one id replace each other). Auto-scroll uses `visualTime` directly in the loop body. The MediaElement provider has the same registry since #769, reached through `usePlaybackRefs()` since #688, part 2, with `visualTime` equal to `time`.

**Per-frame annotation lookups** in both providers' loops go through `createAnnotationLookup()` (`src/utils/annotationLookup.ts`): `atTime` / `byId` return exactly what the `find` calls they replaced returned, cached against the annotations array's identity (so annotations must be replaced, not mutated). `atTime` only uses the cached hit and binary search when the list is sorted and non-overlapping; otherwise it falls back to the linear scan, because with overlaps "first match" depends on index order.

**Do NOT add new rAF loops for visual playback updates.** Register a frame callback instead. Use `visualTime` for DOM positioning, `time` for state/logic.

**Loop handling:** Looping is handled natively by Tone.js Transport (`Transport.loop`/`loopStart`/`loopEnd`). The animation loop does NOT detect loop boundaries — `Transport.seconds` auto-wraps, so `getPlaybackTime()` returns the correct position. Selection/annotation playback disables Transport loop; `stop()` disables it before stopping.

**AudioContext Init Pattern:** `audioInitializedRef` guards `engine.init()` (AudioContext resume via `Tone.start()`). Only the first play call awaits init; subsequent plays skip it entirely — no microtask yield. Reset to `false` when engine is rebuilt in `loadAudio`. This keeps the stop→play path fully synchronous after first play, preventing audio layering race conditions.

**Engine is always persistent (never torn down on empty).** `loadAudio` creates the `PlaylistEngine`+adapter eagerly on mount and reuses it via `setTracks([])` when the timeline empties — it is NOT disposed at `tracks.length === 0`. This keeps a ready Transport so the first play/record never races an async engine rebuild or pays build latency (the cause of the intermittent "frozen recording playhead" — recording into an empty timeline auto-creates a track, and the overdub `play()` used to win the race against the rebuild and no-op). Lazy _module_ loading (dynamic import, #510) is unchanged — only the lifecycle is eager; an empty-on-mount provider holds a suspended AudioContext (resume still deferred to first play). The 0→1 track add takes the synchronous incremental path (`isIncrementalAdd` no longer requires `prevTracks.length > 0`; still gated on an existing engine).

## Engine Rebuilds vs Playback (#675)

A `tracks` change that needs a full rebuild disposes the engine, then creates the new adapter ASYNCHRONOUSLY (`await resolvePlayoutAdapter` — a dynamic import on the Tone path). Three rules keep playback correct across that window; breaking any of them brings back "Play is disabled, nothing plays, time frozen at 0":

1. **A disposed engine is never reachable.** Every dispose goes through `disposeEngineKeepingPlayback()`, which nulls `engineRef`. Before this, `play()` in the window ran against the dead engine (the Tone adapter only warns `adapter.play() called but no playout is available`), set `isPlaying=true`, and nothing started the new engine.
2. **"Was it playing?" comes from the engine, not `isPlayingRef`.** `isPlayingRef` is as fresh as the last render. React commits the new `tracks` and runs the rebuild effect in a later task; a `play()` whose `await engine.init()` resolves in between starts the OLD engine and calls `setIsPlaying(true)`, and the effect then reads a stale `false`. `disposeEngineKeepingPlayback()` checks `engine.getState().isPlaying` at dispose time and queues the resume itself.
3. **Queued plays start from the build completing, not from the `tracks` change.** `pendingResumeRef` (`{ position, endTime? }`) is consumed by the resume effect, which depends on `engineEpoch` — a counter bumped when a freshly built engine is assigned. The `tracks`-triggered run happens before the build finishes and finds `engineRef` null. `play()` queues into the same slot when `engineBuildInFlightRef` is set, and re-checks `engineRef.current === engine` after its own `init()` await; `stop()`/`pause()` clear the slot; a failed build clears it.

4. **A request stays in the slot until it actually starts.** The resume effect does NOT clear `pendingResumeRef` before awaiting `engine.init()`; after the await it proceeds only if the engine and the slot are both unchanged. So `stop()`/`pause()`/a newer `play()` during init cancel it by replacing or clearing the slot, and if the engine is replaced meanwhile, the new engine's own epoch run finds the request still waiting (clearing it first left a window where it was re-queued after the new engine's run and fired minutes later on an unrelated `tracks` change — found in review).
5. **`play()` checks `playRequestIdRef` after its `init()` await.** `play()`, `stop()` and `pause()` each bump it. A play that was parked in `init()` returns if the id moved (it would otherwise start after the user's Stop, or over a newer play), and when its engine was replaced it queues only if a replacement exists or a build is in flight — never after a failed build.
6. **`stop()` and `pause()` always reset the UI state, engine or not.** With `engineRef` null during a rebuild they still call `setIsPlaying(false)` and stop the animation loop. Playback that was running when the rebuild began keeps `isPlaying` true until its resume; returning early on a null engine after cancelling that resume left it stuck true (a regression in the first version of this fix, caught in review).

`isPlaying` stays false while a play is queued by `play()` — it only turns true when an engine has actually been started.

**Testing this (`playDuringEngineRebuild.test.tsx`):** the fake `createAdapter` returns a PROMISE of the adapter (awaited by `resolvePlayoutAdapter`, like the real dynamic import) so the test holds the rebuild window open; with a synchronous adapter the new engine is ready one microtask later and the race never opens. The commit-to-effect ordering (rule 2) cannot be produced inside `act()` — it flushes effects before microtasks — so that one test changes `tracks` outside `act()` (`IS_REACT_ACT_ENVIRONMENT = false`) and releases `init()` from a layout effect.

**How it was found:** the "flaky" playback-start e2e tests on `/examples/waveform-data` (tracks stream in, so the playlist rebuilds right after first `ready`). Two standalone stress scripts never reproduced it (0/240); only the Playwright runner's timing did (~1 in 10 play tests with `--repeat-each` on the whole spec). A temporary spec that logged the console and the `data-playlist-state` transitions around the click showed both paths. After the fix: 1,776/1,776.

## Playhead outputLatency Compensation

`getPlaybackTime()` returns **raw engine time** — no latency subtraction. **Storage refs (`currentTimeRef`, pause/seek targets) must stay raw** so `play(time)` resumes correctly — subtracting latency from storage compounds on every pause/resume cycle.

**Display uses `visualTimeRef`.** While playing, the animation loop sets it from `engine.getAudibleTime()` (raw − `outputLatency` − `engine.lookAhead`, held at play-start during the pre-roll window). When resting (seek/pause/stop/selection-end), `toVisualTime` is the identity — the cursor displays the raw commanded position exactly; compensation is a property of playing, not of position. Every site that assigns `currentTimeRef.current = X` also assigns `visualTimeRef.current = toVisualTime(X)` via `setCurrentTimeRefs`. Static-display consumers read `visualTimeRef`; frame callbacks receive `visualTime` via `FrameData`; auto-scroll uses `visualTime`. The dual-ref pattern is mandatory: one ref → either storage broken (compounding) or display broken (lag).

## Engine State Subscription Pattern

**Pattern:** Engine owns state → emits `statechange` → hook's `onEngineState()` mirrors into useState/refs.

**All engine-owned state uses the `onEngineState()` hook pattern:**

- `useSelectionState` — selectionStart, selectionEnd (published through `SelectionContext`, #733)
- `useLoopState` — isLoopEnabled, loopStart, loopEnd
- `useSelectedTrack` — selectedTrackId
- `useZoomControls` — samplesPerPixel, canZoomIn, canZoomOut
- `useMasterVolume` — masterVolume
- `useUndoState` — canUndo, canRedo

**Still React-only:** isPlaying (animation loop timing), tracks (loaded via useAudioTracks). `currentTime` is read from engine during playback via `getPlaybackTime()` (→ `engine.getCurrentTime()` → `Transport.seconds`).

**Engine-initiated stop mirror (#608 follow-up, final-review CRITICAL 1):** `isPlaying` is React-owned for provider-initiated play/pause/stop, but the provider also subscribes to the engine's `'stop'` event (alongside `statechange`) to catch engine-_initiated_ stops — e.g. `PlaylistEngine` self-stopping when a bounded `play(start, end)` completes on an adapter with `onPlaybackEnded` (the Tone path). Without this, that self-stop rewinds the engine's own current time to `playStartPosition` before the rAF loop's own `time >= playbackEndTimeRef`/`time >= duration` checks can ever observe it, wedging React `isPlaying=true` with a frozen playhead. The `'stop'` handler sets `isPlaying=false`, stops the animation loop, and mirrors `engine.getCurrentTime()` into the time refs — it never calls `seek()` itself (the engine already rewound). It's suppressed via `suppressEngineStopMirrorRef` around every provider call site that calls `engine.stop()` as an implementation detail of an immediate restart (`play()`, `setSelection`, `reschedulePlayback`, the engine-rebuild-with-resume path) — those already establish the correct target state themselves, and an unguarded mirror would clobber it mid-transition (refs aren't batched like `setState`). Stop paths that terminate playback (`stop()`, the rAF loop's own end-of-playback branches) don't need suppression: they write the identical value the mirror would, or run their own ref-write synchronously right after it.

**Subscription location:** Inside `loadAudio()` after `engineRef.current = engine`, the statechange handler calls each hook's `onEngineState(state)`.

**Seed on rebuild:** When `loadAudio()` creates a fresh engine, seed it from hook-exposed refs before `setTracks()` — otherwise the first statechange resets user state to defaults. **Checklist** (update when adding engine-owned state):

- `engine.setSelection(selectionStartRef.current ?? 0, selectionEndRef.current ?? 0)`
- `engine.setLoopRegion(loopStartRef.current ?? 0, loopEndRef.current ?? 0)`
- `if (isLoopEnabledRef.current) engine.setLoopEnabled(true)`
- `engine.setMasterVolume(masterVolumeRef.current ?? 1.0)`
- `if (selectedTrackIdRef.current) engine.selectTrack(selectedTrackIdRef.current)`
- `canUndo`/`canRedo` — no seed needed. `setTracks()` calls `clearHistory()`, so undo state always resets on rebuild.

**Guard handler with ref comparisons:** Each hook's `onEngineState()` compares `state.field !== ref.current` before calling `setState` to skip unnecessary React updates. Ref assignments are synchronous; `setState` calls are batched by React.

The `soundFontCache` prop is deliberately EXCLUDED from the `loadAudio` effect deps — late cache changes are forwarded to the live adapter by a dedicated effect (`syncSoundFontCacheToAdapter(adapterRef.current, soundFontCache)`), which rebuilds only MIDI tracks. ## Trim/Move Asymmetry in useClipDragHandlers

**Move:** `onDragEnd` delegates to `engine.moveClip()` in one shot. The collision modifier constrains the visual position per-frame using the engine's pure `constrainClipDrag` function.

**Trim:** `onDragMove` updates React state per-frame via `onTracksChange` for smooth visual feedback (cumulative deltas from original clip snapshot). `isDraggingRef` prevents `loadAudio` from rebuilding the engine during the drag, so the engine keeps the original (pre-drag) clip positions. On drag end, `engine.trimClip()` commits the final delta.

**Why not `engine.trimClip()` per frame:** Engine methods apply incremental deltas to current state. The drag handler computes cumulative deltas from the original snapshot. Calling the engine per frame would compound deltas incorrectly.

**`isDraggingRef` lifecycle:** Set `true` in `onDragStart` (boundary trim only), set `false` in `onDragEnd` before `engine.trimClip()`. Guards two places in the provider: (1) `loadAudio` effect body skips full rebuild, (2) `skipEngineDisposeRef` prevents the previous effect cleanup from disposing the engine mid-drag.

**Cancel-revert for boundary trims:** `onDragEnd` checks `event.canceled` and restores React state from `originalClipStateRef` snapshot. Without this, Escape during trim leaves UI at partially-trimmed state while engine has original positions. Same pattern in `useAnnotationDragHandlers` with `originalAnnotationStateRef`.

**`skipEngineDisposeRef` must include `isDraggingRef`:** During drag, `onDragMove` triggers `loadAudio` re-runs (because `tracks` is in deps). The previous effect's cleanup checks `skipEngineDisposeRef` — if it only checks `isEngineTracks` (which is `false` during drag), it disposes the engine on the first drag move.

## Stable Drag Handlers and Modifiers (#694)

A boundary trim calls `onTracksChange` on every pointer move, so anything keyed on `tracks` is rebuilt per move. Three things are therefore read through refs instead:

- `useClipDragHandlers` reads `tracks` and `onTracksChange` from refs; `onDragStart`/`onDragMove`/`onDragEnd` change identity only with `samplesPerPixel`/`sampleRate`.
- `ClipInteractionProvider` passes `ClipCollisionModifier.configure({ tracks: getTracks, … })` with a stable getter (the option accepts `ClipTrack[] | (() => ClipTrack[])`), so the `modifiers` array handed to `DragDropProvider` is not rebuilt mid-drag.
- Clip order: `sortedClipsOf(clips)` (`src/utils/sortedClips.ts`) caches the sorted copy per clips array in a `WeakMap`; during a move the array is not replaced, so `ClipCollisionModifier.apply` sorts once. A trim replaces the array every move, so `onDragStart` records the trimmed clip's `sortedClips`/`sortedIndex` once in `trimOrderRef`; only the neighbours are read from it (`constrainBoundaryTrim`). Each move checks, by identity, that every other clip of the track is still the one the order was computed from, and recomputes if not (an undo during the trim, a recording landing on the track).

`useKeyboardShortcuts` likewise keeps the latest `shortcuts` in a ref and subscribes to `keydown` once per `enabled` value; callers build the array inline. Guarded by `stableDragHandlers.test.tsx`, which mocks `@dnd-kit/react`'s `DragDropProvider` to capture the props it is given.

## Clip Interaction Options Have One Source (#690)

Whether clips can be dragged and trimmed (`enabled`) and whether their trim handles are widened for touch (`touchOptimized`) come from ONE place: `ClipInteractionContext` (`contexts/ClipInteractionContext.tsx`), read by `ClipView` for what a clip does, and by `ClipInteractionProvider` only to inherit `touchOptimized` (below). `ClipInteractionOptions` (exported) is the only component that provides it; `ClipInteractionProvider` renders `<ClipInteractionOptions enabled touchOptimized={…}>` around its `DragDropProvider`. `<Waveform>` and `<PlaylistVisualization>` take neither as a prop, and neither is threaded through `TrackRows` / `TrackRow`.

- A prop left out of `ClipInteractionOptions` is inherited from the one above (`??`, not `||`), so it nests: `<ClipInteractionOptions touchOptimized={false}>` inside a touch-optimized provider keeps 8px handles and stays interactive, and `enabled={false}` switches interaction off for part of the tree.
- `ClipInteractionProvider` resolves its own `touchOptimized` the same way (`prop ?? inherited`) and uses that one value for `useDragSensors` and for the `ClipInteractionOptions` it renders, so sensors and handle width cannot disagree and a provider inside `<ClipInteractionOptions touchOptimized>` inherits it.
- The value is memoized on its two booleans. `ClipInteractionProvider` renders on every pointer move of a trim (it follows `tracks`); an unmemoized value would re-render every clip per move.
- History, so it is not repeated: a first version (#773, reverted by #774) kept the two `<Waveform>` props and combined them with the context using `||`. Two sources meant no prop could switch off what the provider turned on, and `<PlaylistVisualization>` changed behaviour under the provider without anyone having decided it. The maintainer's rule for these components (2026-11-11): no doubled sources; a small context with a value that rarely changes, read where it is used, instead of props passed down through components that do not use them.
- A view option that every clip needs and that never changes per frame belongs in a context like this one. `samplesPerPixel` and `sampleRate` are still props of `ClipView`: they were kept as props while the data context that held them changed on every trim move. Since #768 they are in the view and zoom values, which do not, so `ClipView` could read them itself (not done; #685 reshapes these components).

Tests: `clipInteractionOptions.test.tsx` (it mocks `useDragSensors` to record the options the provider passes). `e2e/mobile-multi-clip.spec.ts` checks the 24px handles on a page that sets only the provider flag. `/examples/custom-drag-setup` (`CustomDragSetupExample.tsx`) is the custom path for real: its own `DragDropProvider` plus `ClipInteractionOptions`, with a checkbox per option; `e2e/custom-drag-setup.spec.ts` drags and trims there by exact pixel distances, switches interaction off and on, and checks the handle widths. In that spec a clip is dragged by pressing 8px below the top of its `[data-clip-container]` (the header strip), which works whether or not the header is a draggable; clip positions are whole pixels, so compare within 1px of the computed value.

## @dnd-kit/react v0.5.0 Event API Quirks

- **`event.operation.position.delta`** is `undefined` in snapshots — `@derived` getters are non-enumerable and stripped by `snapshot()`. Compute manually: `position.current.x - position.initial.x`.
- **`event.operation.position.current`** is stale in `onDragMove` — `move()` dispatches before updating `position.current` (happens in `queueMicrotask`). Use `event.to?.x` for the correct pointer position (`to?: Coordinates` is typed on the dragmove event).
- **`event.operation.transform.x`** in `onDragEnd` reflects the final post-modifier transform. Use for clip moves; for boundary trims, cache the last delta from `onDragMove` in a ref.
- **Event types are event OBJECTS, not handler types** (0.4+ redesign): `DragStartEvent`/`DragMoveEvent`/`DragEndEvent` from `@dnd-kit/abstract` are used directly as the handler parameter type. The 0.3-era `Parameters<DragStartEvent>[0]` collapses to `never` (build error, not a runtime bug).
- **Feedback config is per-entity, never provider-level** (0.4+ moved `feedback` out of the hook options into `plugins: [Feedback.configure({...})]`). `Clip.tsx` declares `dropAnimation: null` on the clip-move draggable and `feedback: 'none'` on trim handles itself; `SortableTrackControls` uses the FUNCTION form `plugins: (defaults) => [...defaults, Feedback.configure({ feedback: 'move' })]` so the sortable's default `OptimisticSortingPlugin`/`SortableKeyboardPlugin` survive (a bare array replaces them and drag-commit silently stops working — guarded by `sortableTrackControlsFeedbackPlugins.test.tsx`). The former `noDropAnimationPlugins` provider helper was REMOVED: in 0.5 every entity that carries its own Feedback config re-registers the plugin with `undefined` options (`Draggable` effect → `registry.plugins.register(plugin)` → `existingInstance.options = undefined`), which wipes provider-level Feedback options the moment a clip mounts — provider-level `dropAnimation: null` is unreliable by construction. Per-entity `dropAnimation` takes precedence over the plugin instance (`Feedback.ts` resolution order), so the entity-level declaration is the only robust one. `sortable.ts` likewise reads only `draggable.pluginConfig(Feedback)?.feedback` for its `'move'` handling — a provider-level `feedback` callback never reaches it.
- **Per-entity config matches `Feedback` by constructor identity** (`pluginConfig` does `desc.plugin === plugin`). Two copies of `@dnd-kit/dom` in a bundle make `'none'`/`'move'` silently no-op — keep `@dnd-kit/*` as peers (never `dependencies`) in every published package.

## Error Handling in Playback Callbacks

- **`engine.play()` try-catch in play callback** — `engine.play()` is synchronous but can throw (adapter failures). Wrap in try-catch; on error, `stopAnimationLoop()` and return early to avoid `setIsPlaying(true)` with no audio.
- **Fire-and-forget async `.catch()` handlers** — `reschedulePlayback()` and `resumePlayback()` are async functions called without `await` in useEffect callbacks. Without `.catch()`, throws become unhandled promise rejections. Each `.catch()` resets UI state (`setIsPlaying(false)`, `stopAnimationLoop()`).

## AudioContext Is the Single Source of Truth for Sample Rate

**Rule:** Never derive `sampleRate` from clips or AudioBuffers — use the AudioContext hardware rate. All decoded audio and recordings run at this rate.

- `WaveformPlaylistContext`: `sampleRateRef` seeded from `sampleRate` prop ?? `48000` (provisional, no playout call) during the `useState` initializer. After the adapter is created in `loadAudio`, the ref is reconciled from `adapter.audioContext.sampleRate` (the real hardware rate). A Tone consumer that passes no `sampleRate` prop sees 48000 for the brief pre-first-load window.
- `useAudioTracks`: `contextSampleRateRef` set from `audioContext.sampleRate` in `loadTracks`.
- `useExportWav`: calls `getGlobalAudioContext().sampleRate` directly.
- **Never** fall back to 44100 or derive from `tracks[0].clips[0]?.sampleRate` — that fails in recording-only workflows.

## sampleRate From Context (Not Props)

Internal hooks (`useClipDragHandlers`, `useClipSplitting`) read `sampleRate` from `usePlaylistView()` — do NOT add it as a parameter. `useAnnotationKeyboardControls` takes it as an option and otherwise reads `usePlaylistViewOptional()`, which returns the value under either provider and `null` outside one. `useAnnotationDragHandlers` accepts optional `sampleRate` (defaults to `48000` — tone-free engine default; providers pass the real rate from context) because it's used in both WaveformPlaylist and MediaElement contexts. `SnapToGridModifier` and `calculateBoundaryTrim` are not hooks — they still receive `sampleRate` as a parameter from callers that have context access.

## Aligned Peak Resampling (waveformDataLoader.ts)

**Decision:** When slicing WaveformData before resampling to a different scale, source slice indices must align to the resampling ratio.

**Why:** WaveformData.resample() groups N consecutive source bins per output bin (N = targetScale/sourceScale). If the slice starts at a non-aligned index, output bins cover different source samples than a full-file resample would, causing zoom-dependent peak amplitude.

**Pattern (in both `extractPeaksFromWaveformData` and `extractPeaksFromWaveformDataFull`):**

```typescript
const ratio = samplesPerPixel / sourceScale;
const targetStart = Math.floor(offsetSamples / samplesPerPixel);
const targetEnd = Math.ceil((offsetSamples + durationSamples) / samplesPerPixel);
const sourceStart = Math.floor(targetStart * ratio);
const sourceEnd = Math.min(waveformData.length, Math.ceil(targetEnd * ratio));
// slice(sourceStart, sourceEnd) → resample(targetScale)
// (WaveformData.slice endIndex is exclusive, like Array.slice)
```

**Key invariant:** Floor/ceil slicing ensures all source bins contributing to target bins are included. For integer ratios (power-of-two scales like 256→1024), this gives exact bin-boundary alignment. For non-integer ratios (e.g., 256→1000), first/last bins may be slightly more inclusive than a full-file resample, but never underrepresent peaks.

**Why floor/ceil, not round:** `Math.round` can exclude a partial source bin at either boundary, underrepresenting peaks. `Math.floor` (start) and `Math.ceil` (end) are consistently inclusive — they may include one extra source bin, but the resampler's min/max aggregation makes this the safe direction for waveform visualization. Non-integer ratios are common (default `samplesPerPixel=1000` with `baseScale=256` gives ratio 3.90625).

**Mono merge:** Uses weighted averaging (same as `makeMono` in webaudio-peaks). This is consistent across both packages — do not change to min/max without updating both.

## AudioBuffer Deduplication in Peak Generation

**Decision:** `useWaveformDataCache` deduplicates worker jobs by `AudioBuffer` identity, not clip ID.

**Why:** When a recording is split into many clips sharing the same `AudioBuffer`, per-clip generation causes duplicate `Float32Array.slice()` allocations and OOM on large timelines.

**Implementation:** Two `WeakMap<AudioBuffer, ...>` refs:

- `generatedByBufferRef` — results (`WaveformData`), read during render via `getWaveformData(buffer)`
- `inflightByBufferRef` — in-flight worker promises

**Pattern:** Generate once per buffer; every clip sharing it finds the result by buffer when `version` bumps. `WeakMap` allows GC when `AudioBuffer` is released.

## MIDI Clip Rendering Pipeline

**Problem:** MIDI clips have no `audioBuffer` or `waveformData`, so Path C in peak generation gave them `length: 0`, rendering as invisible zero-width clips.

**Fix:** In Path C, detect `clip.midiNotes` and compute `pixelLength = Math.ceil(clip.durationSamples / samplesPerPixel)`.

**Data threading:** `ClipPeaks` includes `midiNotes`, `sampleRate`, `offsetSamples` which flow through `PlaylistVisualization` → `ChannelWithProgress` → `SmartChannel` → `PianoRollChannel`.

**A piano roll comes from the track kind, not from a render mode (#756, #763).** `RenderMode` is `'waveform' | 'spectrogram' | 'both'` and applies to audio tracks: `trackRenderMode(track, override)` (`src/utils/trackRenderMode.ts`) gives the override, else the track's `renderMode`, else `'waveform'`, and always `'waveform'` for a MIDI track so that nothing starts a spectrogram for it. What makes a piano roll: `TrackRow` gets `kind` (row background, `data-track-kind`), and `ChannelWithProgress` and `SmartChannel` treat a clip whose `midiNotes` is not null as a MIDI clip (piano roll, no progress overlay). `DefaultTrackControls` gets `kind` too and shows no track menu for a MIDI track: the menu holds only render-mode choices and spectrogram settings. The engine guarantees the two agree (a MIDI track holds only clips with notes). The press handler (`handleMouseDown`) finds the row under the pointer with `trackIdAtOffset` over `trackLayout`, the layout the rows are positioned with, and does no height arithmetic of its own: its old loop counted a `'both'` track twice as tall as it is drawn, so a press on any row below one selected the row above (#762). The selected row carries `data-selected="true"` (`clickSelectsRowUnderPointer.test.tsx`, `e2e/track-selection.spec.ts`). Do not bring `'piano-roll'` back as a mode value.

**Styling a track row from outside:** an `outline` or `background` on `[data-track-row]` does not show: the row's children (`position: relative` with their own background, clips at `z-index: 10`) paint over it. The row must not get a `z-index`, `transform` or `filter` (a stacking context there breaks clip interactions). Draw on `[data-track-row]::after` with `position: absolute; inset: 0; pointer-events: none` and a `z-index` above 100 (the playhead). The Track Management guide carries this example.

**What selects a track:** a press on the click overlay (row under the pointer), a press on a clip unless it starts on a draggable header or trim handle, and a click anywhere in the default controls except the remove, menu and reorder buttons (they stop propagation). A render-mode radio in the track menu DOES select: the dropdown is a portal and React bubbles its click to the controls.

**A track the engine rejects does not crash the page.** The engine throws on a track whose clips do not match its kind. Both places where the provider hands tracks to the engine (the incremental path and the full build) are inside `try`/`catch` in the async load, so React never sees the throw and an error boundary does not catch it: the incremental path checks its whole batch with `assertTrackKind` before applying any of it (a bad track late in a batch must not leave the earlier ones added), warns `Incremental add failed…` and falls through to the full build, which calls `onError(error)`, warns, and leaves `isReady` false until `tracks` is valid again (`trackKindProvider.test.tsx` covers the initial mount and an append to a running playlist). With `deferEngineRebuild` true the effect returns before the full build, so the report comes when the deferral ends. Anything new that passes tracks to the engine outside those two blocks must handle the throw itself.

**The `reschedulePlayback` effect restarts the AUDIO only when `continuousPlay` turns on (#701).** It compares against `prevContinuousPlayRef`; every other run (playback starting, the loop closure changing) only restarts the animation loop. Keyed on the current value instead, every Play with continuous play on stopped and restarted the engine, and so did any duration change. The transition branch drops the end (engine side AND `playbackEndTimeRef`, otherwise the loop stops there anyway) only when that end is the active annotation's own end; any other bounded play (a selection, even one playing over an annotation) keeps its end and is rescheduled with it. "An annotation is active" alone is not a usable test: on a page whose annotations cover the timeline one is always active. **While the selection itself is what is playing, continuous play has no effect at all** (maintainer's rule, 2026-11-11): `play()` sets `isSelectionPlayRef` when its start and end are the highlighted selection's; the loop then takes the follow-only branch, so playback is not cut at annotation boundaries, and the toggle reschedules nothing. Before, a selection crossing an annotation boundary stopped at that boundary with continuous play off. The rule is keyed on WHAT IS PLAYING, not on "a selection is highlighted": a first version used the latter, and an annotation clicked with a selection highlighted elsewhere then behaved inconsistently (continuous play on from the start continued; ticked midway did nothing). An annotation play always follows the toggle, and a click never clears the selection. In that follow-only branch the loop leaves the highlight alone on the frame that reaches `playbackEndTimeRef`, so it does not jump to the next annotation as playback stops. The skip must stay INSIDE the follow-only branch: applied to the whole annotation block (as #727 first did) it also skipped the continuous-play-off branch, which is what stops an annotation at its end and returns the cursor to its start, and the cursor was left at the end instead. `setSelection` during playback replaces the bounded play that was running: a new RANGE restarts as selection playback, start to end (looping on: open-ended); a collapsed selection (a cursor move) continues open-ended. A queued `pendingResumeRef` is changed IN PLACE, because a resume parked in `init()` recognises its request by identity (#675 rule 4), and the resume effect reads `position`/`endTime` only after that await. `usePlayFromSelectionOrCursor` resumes from the cursor when it is strictly inside the selection, and `play()` recognises that as selection playback too (start inside the selection, end at its end). For selection playback `playStartPositionRef` is always the SELECTION start, and `stop()`, the engine-stop mirror AND the loop's own end-of-bounded-play branch all put the cursor there (the first two also seek the engine). The mirror and the loop race on the Tone path, so they must agree. With a queued resume, `setSelection` only re-points the request and returns (restarting as well started the engine twice); while stopped it resets `isSelectionPlayRef` and `playStartPositionRef`, so a Stop pressed while stopped does not send the cursor to an old play's start. Known edge: a clicked annotation that starts inside the highlighted selection and ends exactly at its end is treated as selection playback (the continuous-play toggle is ignored for that play). **The loop and `seekTo` read the timeline end from `durationRef` (#767).** The ref is written during render (like `isPlayingRef` and `tracksRef`), so a running loop sees the new end on its next frame and is not restarted, and a child that calls `seekTo` from a layout effect of the same commit is clamped to the new end (a first version wrote it in a layout effect; children's layout effects run before the provider's, found in review). The MediaElement provider's `seekTo` also reads a ref, but of the track's own length, not of `duration` (see "Provider Internals Exist Once"; `mediaElementControlsStability.test.tsx`).

## Shortcuts Yield to the Focused Control (#710)

`handleKeyboardEvent` (core) skips a shortcut when `keyBelongsToFocusedControl(event)`: every `<input>` type, `textarea`, `select` and contenteditable keep every key; `Escape` belongs to an open modal `<dialog>` or `aria-modal` container, on the composed path OR anywhere in the document (clicking the dialog's padding leaves focus on `<body>`); `Space`/`Enter` belong to a focused native `<button>` (not when `disabled`) or `<summary>`, and `Enter` alone to an `<a href>` (a link does not use Space). A hidden `aria-modal` container is ignored. Note every `<input>` type blocks ALL shortcuts, including undo and split, while focused.

- **How the control got focus makes no difference, by the maintainer's decision (2026-11-11).** A pointer exception (clicked button/slider/dropdown leaves Space as play/pause) was built, merged (#718, #721) and then removed (#724 and the PR after it): a clicked control still has focus, and a focused native control must behave as it does on any other page. Do not reintroduce focus-source tracking (`observeFocusSource` was deleted) or use `:focus-visible` for behaviour; it is for drawing the ring only, and Chromium makes the focused element match it as soon as any key is pressed anyway.
- Consequence to remember when writing examples and tests: after clicking Mute, Space toggles Mute; Space is play/pause only when focus is not on a control. The React Play/Pause/Stop buttons are disabled when they do not apply, so focus drops to `<body>` after a click and Space keeps working; dawcore's transport buttons stay enabled and keep focus.
- Before #710, `preventDefault` on the keydown blocked the button's own activation: a keyboard user could not press a focused Mute with Space, and Escape could not close the spectrogram settings modal.
- ARIA-role-only widgets (`role="button"` divs: dnd-kit clip headers and sortable handles, which only have a `PointerSensor`) are deliberately NOT covered; yielding to them would make Space dead on a Tab-focused clip header.
- Covered by core's `keyboard.test.ts` and `e2e/keyboard-focus.spec.ts`.

## Selection Drag Is Followed on the Window

`WaveformRoot` and `MediaElementPlaylist` handle only `mousedown` on the click overlay, through `useSelectionDrag` (next section). Moves and the release come from `useWindowDrag(isSelecting, onMove, onEnd)` (`src/hooks/useWindowDrag.ts`), which listens on `window` while the drag is active, so the selection follows a pointer that has left the waveform and the drag ends wherever the button is released.

- Positions come from `clampedOffsetX(dragElementRef.current, clientX)`: the overlay the press landed on, clamped to its ends. A fast drag past the left edge therefore selects from 0.
- `onEnd(null)` means the drag ended with no release position: a window `blur` (the `mouseup` went to another application), or a move with the primary button no longer held (a lost `mouseup`). End the drag, keep the selection, no seek (during playback: drop the preview).
- Only `e.button === 0` starts a drag: a right-click opens the context menu and its release may never arrive. The window listeners are capture-phase, the callbacks ref is written in a layout effect, and the `user-select` switch is counted across instances (the media-element example has two players).
- Before this, a release outside the overlay left `isSelecting` true: the next move over the tracks extended the selection with no button held, and `ClickOverlay`'s `$isSelecting` z-index (110) stayed above the clips (105), so headers and trim handles could not be grabbed until the next click.
- The hook sets `user-select: none` on the root element for the drag. Do NOT replace that with `preventDefault()` on the mousedown: the press must still take focus off a focused control (Space after clicking the waveform is play/pause, see "Shortcuts Yield to the Focused Control").
- e2e gotcha: a diagonal `page.mouse.move(..., { steps })` out of the tracks changes the selection on the way; leave vertically when the test is about the range.

Covered by `hooks/__tests__/useWindowDrag.test.tsx` and the "outside the tracks" / "past the left edge" tests in `e2e/multi-clip.spec.ts` and `e2e/media-element.spec.ts`.

## The Selection Drag Commits on Release During Playback

`hooks/useSelectionDrag.ts` is the one implementation of the drag, used by `WaveformRoot` and `MediaElementPlaylist`. Its doc comment has the full rules; in short (maintainer's rules, 2026-11-12):

- **Stopped:** the selection follows the pointer (press collapses it, each move sets the ordered range, the release leaves it; a click calls the view's `onClickWhileStopped`: `setCurrentTime` in the multitrack view, a collapsed `setSelection` in the MediaElement one).
- **Playing, automatic scroll off:** nothing is committed before the release. Moves publish the range to a `ValueSource` (`SelectionPreviewContext`, internal), which `SelectionOverlay` shows in place of the selection; the release calls `setSelection` once (the range, which the provider plays start to end, or open-ended under the multitrack provider with looping on; or, for a range under 0.1 s, collapsed at the PRESS time). A range under 0.1 s is not previewed either.
- **Playing, automatic scroll on:** no range can be drawn: the view scrolls under a still pointer, so the time under it at the release is not the time at the press. Moves are ignored and the release seeks once to the time captured at the press, however far the pointer went. Never recompute a click's time from `getBoundingClientRect()` at the release during playback.

Why: `setSelection` restarts a running play under both providers, so writing it on the press and per move would restart playback under the pointer. Until this change the press did that (and the multitrack release did it a second time), moves were ignored while playing, and no range could be selected during playback.

- **The preview is a source, not state, and the automatic-scroll setting is read through a ref.** `<AutomaticScrollFlag flagRef>` (same file) is a child that renders nothing and writes the ref in a layout effect; the views render it. Calling `usePlaylistSettings()` in the view would render the view's root on a toggle (in `MediaElementPlaylist`, the whole waveform) for a value it never draws. `visualizationMemoBoundaries.test.tsx` fails for the multitrack root if it does, and `mediaElementShellQuiet.test.tsx` for the MediaElement view. A view that uses the hook must render the flag and the `SelectionPreviewContext.Provider`.
- **Readers of the selection see the OLD selection during a playing drag** (`SelectionTimeInputs`, `SetLoopRegionButton`; `PlayButton` reads it too but is disabled while playing): only the highlight previews, and only in the view being dragged (the source is per hook call, so a second view under the same provider shows the old selection until the release).
- **When playback stops or ends under the drag** the next move clears the preview and writes the selection live; the release then follows the stopped rules. With no move in between, the release is a click, and it collapses the selection itself (`wroteSelectionRef`: the press did not, because playback was running; without this an older highlighted range stayed selected in the multitrack view and Play would have played it).
- **Automatic scroll switched on under a drag that had already drawn a range:** the next move withdraws the preview, and the release seeks to the press.
- **`setSelection`'s restart writes `playbackStartTimeRef` and `audioStartPositionRef`** (multitrack provider), as `play()` does. The release used to end with `play()`, which wrote them; once it called `setSelection` alone, `useEngineRefs()` consumers (the flexible-API example's own time readout) kept counting from the replaced play. Found in review. Any new path that restarts the engine must write both.
- **`onEnd(null)`** (window blur, lost `mouseup`): the preview is dropped and nothing is committed; while stopped the selection stays as the last move left it.
- The multitrack press still selects the row under the pointer during playback. It does not call `setCurrentTime` itself any more: while stopped the hook's `setSelection(t, t)` already writes the cursor (refs and state), which is all `setCurrentTime` does (a mutation run showed the extra call changed nothing).

Tests: `selectionDragDuringPlayback.test.tsx` (the hook under hand-built contexts, 50 px per second; the highlight showing the preview), the drag cases in `mediaElementPlaybackSemantics.test.tsx` and `mediaElementSharedLoop.test.tsx`, and "Pressing and dragging on the tracks during playback" in `e2e/multi-clip.spec.ts` plus the two "during playback" tests in `e2e/media-element.spec.ts`. `probes/pressrelease793.cjs <port> <route> [auto]` prints where playback is at the press, while held, after a drag and after the release.

## Progress Overlay Width Invariant

**Decision:** In `ChannelWithProgress`, `ProgressOverlay.$width` uses `clipPixelWidth()` from core, but `Background.$width` uses `smartChannelProps.length` (peak data length).

**Why:** Background must match the canvas area — extending it to `clipPixelWidth` bleeds the waveform fill color into the gap between audio end and clip end (where the playlist background should show). ProgressOverlay must match the clip container — using `peaksData.length` causes `scaleX(ratio)` to scale a narrower element, making progress visually lag behind the playhead.

## Controls Offset Removed

**Decision:** All `controlsOffset` / `controlWidth` arithmetic removed from mouse handlers, playhead positioning, selection, auto-scroll, and zoom calculations.

**Why:** Controls are now outside the scroll container (in `ControlsColumn`), so pixel positions in the scroll area map directly to timeline positions without offset adjustment.

**Affected:** `WaveformRoot`, `MediaElementPlaylist`, `AnimatedPlayhead`, `WaveformPlaylistContext` (auto-scroll + zoom), `MediaElementPlaylistContext` (auto-scroll), `useAnnotationKeyboardControls`.

## Derived State Sync: setState During Render, Not useEffect

**Problem:** Syncing `useMemo` output to `useState` via `useEffect` causes a 1-render lag. If another prop (e.g., `deferEngineRebuild`) changes in a separate React batch, downstream consumers see stale state and re-run effects (double engine rebuild).

**Fix:** Use synchronous setState-during-render (React's "getDerivedStateFromProps" pattern):

```typescript
const derived = useMemo(() => compute(input), [input]);
const [state, setState] = useState(derived);
const prevRef = useRef(derived);
if (derived !== prevRef.current) {
  prevRef.current = derived;
  setState(derived);
}
```

**When:** Any time derived state feeds into `WaveformPlaylistProvider` props alongside other props that may change in separate batches.

## Important Patterns (Browser-Specific)

- **Context Value Memoization** - All context value objects in providers must be wrapped with `useMemo`. Extract inline callbacks into `useCallback` first to avoid dependency churn. A `useMemo` holds only while EVERY dependency keeps its identity, and one unstable entry among ~40 fails silently (#691: a non-memoized `formatTime` from a helper hook rebuilt `controlsValue` on every provider render). Three rules: (1) object props that consumers write inline (`controls`, `theme`) go through `useShallowStable` before being used as a dependency, and defaults are module constants, never inline literals in the destructuring; (2) callbacks in a context value must not depend on state they only read or update — use functional `setState((prev) => …)` and the existing refs (`isPlayingRef`), which also avoids dropped updates when two setters run in one batch; (3) any new field in a context value needs a case in `__tests__/contextValueStability.test.tsx`, which asserts the identities directly. Nothing derived from state belongs in the controls value, only actions, refs and sources (#767 removed two things that moved it, `duration` and a `formatTime` rebuilt per time format; the tests pin it per trigger, not as a whole).
- **Fetch Cleanup with AbortController** - `useAudioTracks` uses AbortController to cancel in-flight fetches on cleanup. Follow this pattern for any fetch in useEffect. For per-item abort (e.g., removing one loading track), use `Map<id, AbortController>` instead of `Set<AbortController>`.
- **Guard Before State Update in Callbacks** - In callbacks that update both React state and audio engine, validate inputs (e.g., trackId lookup) BEFORE calling `setState`. If the guard is after `setState`, invalid inputs cause UI/audio desync (UI updates but audio doesn't).
- **RefObject Nullability** - `React.RefObject<T>` has `current: T | null` in React 18 types, even when initialized with a value. Call sites accessing hook-returned refs need `?? 0` (numbers) or `?? false` (booleans) fallbacks to satisfy TypeScript, even though the values are never actually null at runtime.
- **Provider-Level Concerns Stay in Provider** - Callbacks with cross-cutting side-effects (e.g., `setSelection` updates currentTime and restarts playback, `setLoopRegionFromSelection` reads from selection hook and writes to loop hook) belong in the provider, not in individual state hooks. Hooks handle engine delegation + state mirroring only.

## SnapToGridModifier (Beats & Bars)

**Location:** `src/modifiers/SnapToGridModifier.ts`

**Two modes via discriminated union:**

- `mode: 'beats'` — Quantizes in PPQN tick space (bar or beat grid). Uses `samplesToTicks` → `snapToGrid` → `ticksToSamples` round-trip.
- `mode: 'timescale'` — Quantizes by `gridSamples` (consumer typically derives this from `getScaleInfo(samplesPerPixel).smallStep * sampleRate / 1000`).

**Boundary trims:** Modifier skips trims (returns `transform` unchanged). Trim snapping is handled in `useClipDragHandlers` via optional `snapSamplePosition` callback.

**Consumer pattern:** Example conditionally includes modifier in array (exclude entirely when snap is off) rather than relying solely on the modifier's internal `snapTo === 'off'` guard.

## Snap-to-Grid: Absolute Position, Not Delta

**Decision:** Snap the clip's absolute timeline position to the grid, not the drag delta.

**Why:** Delta-snapping preserves off-grid offsets permanently — if a clip starts off-grid (from collision, initial placement, or trimming), snapping the delta to grid-sized increments keeps it at the same offset from every grid line.

**Move snapping (SnapToGridModifier):** Reads `startSample` from `source.data`, computes `proposedPosition = startSample + delta`, snaps that to grid, derives delta as `(snappedPosition - startSample) / samplesPerPixel`.

**Trim snapping (useClipDragHandlers):** Optional `snapSamplePosition` callback. After `calculateBoundaryTrim`, snaps the boundary's absolute position (left → snap `startSample`, right → snap end position). Stored in ref to avoid dependency churn. `lastBoundaryDeltaRef` uses the effective (snapped) delta so `engine.trimClip()` gets the correct value.

**Draggable data:** `Clip.tsx` includes `startSample` and `durationSamples` in all draggable `data` objects (clip move + both boundary handles) so modifiers can compute absolute positions.

## Hook Isolation for Render Props

**Problem:** Calling a render prop function (e.g., `renderPlayhead({...})`) directly in a conditional branch merges its hooks into the parent's hook count. If the prop toggles, React throws "Rendered more hooks than during the previous render."

**Fix:** Wrap in a dedicated component that always calls the render prop, isolating its hooks in its own component boundary. Applied in `VisualizationOverlays.tsx` (`CustomPlayhead`, inside `PlayheadOverlay`), which both views render.

**No stub refs:** until #688 part 3 the MediaElement view passed `ZERO_REF` placeholders for the engine refs in `PlayheadProps`. Those props are gone; `PlayheadProps` holds only what both providers have.

## 60 Hz Values Are Sources, Not State (#695)

Meter levels and recording progress change about 60 times a second. They are published through core's `ValueSource` (`subscribe` + `getSnapshot`) and never put in React state by the library:

- `useOutputMeter()` returns `{ meter, resetPeak, error }`. `meter` keeps its identity for the life of the hook, and the hook does not re-render when levels change. `<SegmentedVUMeter meter={meter} />` draws from it; `useMeterLevels(meter)` (ui-components) is the opt-in, throttled state.
- `<Waveform recordingState>` takes `progress` (from `useRecording` / `useIntegratedRecording`), not `durationSamples` and `peaks`. `RecordingPreviewClip` is the ONLY component that follows it frame by frame (`useSyncExternalStore`). The shell reads two numbers through `useRecordingLayout` (`hooks/useRecordingLayout.ts`): the take's channel count and `recordingDisplayEnd()`, the timeline end the take needs, which moves in 10-second steps (10 to 20 s ahead of the take). Selectors that return numbers are what keep the shell from rendering per frame; do not read `progress.getSnapshot()` in the shell's render for anything else.
- Rule for new per-frame data: add a source (or a frame callback while playing), let the one component that draws it subscribe, and give everything else a coarse selector. Never thread the value through the host component as a prop.

Measured on the recording example (4 tracks, dev build, fiber-walk probe): idle with a mic stream 63 commits/s and about 17,000 component renders/s before, 0 after; recording 182 commits/s and about 43,000 renders/s before, 60 and about 1,140 after (the preview clip). `recordingPreviewSubscription.test.tsx` counts renders with wrappers around the real components; `e2e/recording.spec.ts` drives the page with a synthetic microphone.

## Output Metering (useOutputMeter)

**Critical: Context mismatch gotcha.** Always use `getGlobalContext()` from `@waveform-playlist/playout` — never `getContext()`/`getDestination()` from Tone.js. `getGlobalContext()` creates a new Context via `setContext()`, replacing the default. Nodes created with `getContext()` before that happens end up on a dead audio graph.

**Destination.chain(workletNode)** inserts the meter worklet as a pass-through in the master output. Audio flows through unchanged while the worklet measures every sample. Cleanup: `destination.chain()` restores the default path.

**Sample-accurate metering:** Uses `meter-processor` AudioWorklet from `@waveform-playlist/worklets`. The worklet accumulates peak and RMS across all 128-sample quantums and posts results at ~60Hz — no transient is missed between animation frames.

## End-of-Timeline Semantics (indefinitePlayback, fillViewport, setRecordingActive)

**Matched with dawcore's `<daw-editor>` (#589/#590/#593, PR #592):**

- **Default:** the animation loop auto-stops playback when raw engine time reaches `duration` and returns the cursor to the play-start position (player style).
- **`indefinitePlayback` prop:** opt out — the transport rolls until an explicit stop/pause (DAW style; implies the fillViewport layout). Stored in a ref for the loop; exposed via `usePlaylistView()`.
- **`fillViewport` prop (layout only):** `WaveformRoot` floors `displayDuration` to fill the scroll container. `indefinitePlayback || fillViewport` gates the floor. Recording UIs want `fillViewport`, not `indefinitePlayback`. The container width is state: measured in a layout effect (first paint already fills) and kept current by a `ResizeObserver` on the scroll container, only while the floor is active. Never read `clientWidth` in the render body (`fillViewportContainerWidth.test.tsx`).
- **Recording session suppression:** while `setRecordingActive(true, …)` is active, the auto-stop is skipped so punch-in takes run past existing material. Overdub flows MUST call it eagerly (before `play()`) — the recordingState render round-trip loses the race against the first animation frame (empty timeline: `time 0 >= duration 0` stops instantly).

**`setRecordingActive(active, armedTrackId?)` (`useEditorControls()`):** besides the suppression, an `armedTrackId` transiently mutes that track for the session — punch-in replaces whatever the take overlaps, so the doomed material must not play under the overdub. Previous mute captured/restored via engine-level `setTrackMute` (survives adapter rebuilds); UI `trackStates` mute untouched. Auto-wired from the view's `recordingState` prop (the effect is in `WaveformRoot`, driven by the recording marker) by an effect with cleanup (releases on recording end AND unmount; re-arms on remount-while-recording). Explicit ends (selection playback via `playbackEndTimeRef`, annotation boundaries) stop regardless of all of the above.

## Output Meter Clearing (isPlaying Prop)

**Problem:** When playback stops, browsers stop calling the worklet's `process()` (tail-time optimization — no active upstream sources). The last non-zero levels freeze in React state.

**Fix:** `useOutputMeter({ isPlaying })` — a separate `useEffect` publishes silent levels (current, peak, RMS) and clears the smoothed state when `isPlaying` transitions to `false`. Prefer state-driven cleanup over staleness timers. A worklet message that is still in flight when the reset runs starts the smoothed peak decaying again, so on the recording example the output meter falls over about three seconds after Stop rather than at once (seen while checking #695 and not compared against a build from before it; the reset and the message handler are the same logic as before).

## Incremental Track Addition (loadAudio optimization)

**Detection:** `incrementalChange` (and `isIncrementalAdd`, true when it is not null) is computed during render by comparing `prevTracksRef` with current tracks. Uses reference equality on individual track objects — if every previous track is unchanged or was empty and got its clips, and any new ones were appended, the incremental path is used.

**When incremental:** `incrementalTrackChange(prevTracks, tracks)` (`src/utils/incrementalTrackChange.ts`) returns `{ added, filled }`: tracks appended (file drops, new empty tracks), and tracks that had NO clips and now have some (a `useDynamicTracks` placeholder whose audio arrived; a first take recorded into an empty track). Tracks that were already there must keep their index, with new tracks after them (the engine appends an added track and `trackStates` is positional), otherwise it is a rebuild. Filled tracks are applied BEFORE added ones: an add is mirrored to the parent, and a parent that stores what it is given would otherwise get the placeholder back. Added tracks go through `engine.addTrack()`, filled ones through `engine.updateTrack(id, track)` with mirroring to `onTracksChange` suppressed (`suppressTracksMirrorRef`: the parent already has them) and `engine.clearHistory()` afterwards, as a rebuild did (undo must not go back to an empty placeholder), followed by `onUndoEngineState(engine.getState())` because `clearHistory` emits no statechange. The filled track's name replaces the placeholder's in `trackStates`. No engine dispose/rebuild. Before this, each decoded file was a full rebuild.

**When full rebuild:** a track that already has clips is replaced (recording into a track with content, a consumer edit), a track removed, an empty track renamed.

**Never give consumers a reason to copy track objects (#752).** Both fast paths are identity checks: `tracks === engineTracksRef.current` (the array the engine just reported) and `current === previous` per track. Until #752 a track's effects function was a field (`ClipTrack.effects`), and the documented way to set it was `tracks.map((t) => ({ ...t, effects }))`. Measured with a counting adapter and a parent that stores `onTracksChange`: with that map, every clip move, trim and split did its incremental `updateTrack` AND THEN a dispose + new adapter + `setTracks`, and every added or filled track was a full rebuild; with the tracks passed through, none. What `onTracksChange` hands back is always new track objects (`getState()` copies each one), with every field carried along. So anything per-track that is not plain data goes through a provider prop keyed by track id (`trackEffects`), never onto the track. `trackEffectsProp.test.tsx` holds the counts, including the control case with copied tracks.

**`skipEngineDisposeRef` integration:** `isIncrementalAdd` joins `isEngineTracks` and `isDraggingRef` in preventing the effect cleanup from disposing the engine.

**`prevTracksRef`:** Updated in all `loadAudio` exit paths (engine tracks guard, incremental add, clear state, full rebuild) to keep detection accurate.

## Rewind / Seek Without Playback

**Rule:** Use `seekTo(time)` to move the cursor without starting audio. Never use `play(time, 0)` — `playDuration=0` is truthy (`!== undefined`), so the Transport starts but the animation loop immediately stops at `endTime=0`. This causes ghost audio playback with no visual indication. The built-in `RewindButton` calls `seekTo(0)` (#688, part 2; until then `setCurrentTime(0)` plus `play(0)` if already playing).

## Debugging State Changes with console.trace

**Technique:** Wrap `useState` setter with a traced version to pinpoint which code path modifies state. Useful for controlled state like `tracks` where multiple sources (`onTracksChange`, recording hooks, file drops) can call `setTracks`.

```typescript
const [state, setStateRaw] = useState(initial);
const setState = useCallback((v) => {
  console.log('[Component] setState: ' + summarize(v));
  console.trace('[Component] setState trace');
  setStateRaw(v);
}, []);
```

## MediaElement Progress Overlay

`MediaElementPlaylist` renders the shared `ChannelWithProgress` (with `isSelected`) since #688 part 3; see "One Playhead, One Progress Overlay, One Selection Highlight". The overlay is animated with `transform: scaleX(ratio)` (never `width`, which lays out every frame), and geometry and colour go through `.attrs()` inline styles.

## MediaElement currentTime vs currentTimeRef

`currentTime` (React state from `useCurrentTime()`) only updates on pause/stop/seek/playback-end — NOT during playback. For smooth real-time display, use `<AudioPosition />`, or `currentTimeRef` in a frame callback registered through `usePlaybackRefs()` with direct DOM manipulation (e.g., `ref.current.textContent = ...`). Never use `currentTime` for time displays that should update during playback.

## React Hook Patterns (cross-cutting)

- **Derive Render Guards from Props, Not Effect State** — Don't use effect-set state (e.g., `isReady`, `trackStates`) in render guards. Effect state lags props by one+ renders, causing content to flash/disappear. Compute values synchronously from props instead.
- **Copy Refs in useEffect Body** — When accessing a ref in `useEffect` cleanup, copy `.current` to a local variable inside the effect body. ESLint's `react-hooks/exhaustive-deps` rule flags refs that may change between render and cleanup. **Exception:** for `[]` deps effects (mount/unmount only), refs are null at mount — copying captures null forever; read refs directly inside the cleanup function instead.
- **Refs from Custom Hooks in Dep Arrays** — When a `useRef` is returned from a custom hook, ESLint's `exhaustive-deps` can't trace its stability. Include it in the dep array (harmless, never triggers) rather than `eslint-disable-next-line` which would mask real missing dependencies.
- **Render-Phase Guards ≠ Effect Dependencies** — Derived booleans computed during render (e.g., `isEngineTracks = tracks === engineTracksRef.current`) that are read inside effect bodies as guards should NOT be in the effect's dep array. They flip between renders, causing spurious re-runs. Read them inside the effect body; depend only on the source data (`tracks`). When the same guard also needs to be visible to the _previous_ effect's cleanup, store it in a ref during render.
- **Gate Provider Behind Async Readiness** — When multiple async resources must load before rendering (e.g., MIDI tracks + SoundFont), gate the `WaveformPlaylistProvider` mount behind all resources being ready. Prevents double engine rebuilds. Check both the loading flag AND `tracks.length > 0` since hooks can briefly report `loading: false` with empty data.
- **Provider Child Effects and playoutRef Timing** — React runs child effects before parent effects. A child component's `useEffect` accessing `playoutRef.current` will find `null` on first run. Under the MediaElement provider add `isReady` (from `useMediaElementTrack()`) as a dependency: it turns true when the player exists and its media has loaded. (`duration` was that signal until #688; it no longer changes.)

## Tone.js Usage Outside the Playout Package

- **Dynamic Import Tone.js** — `import * as Tone from 'tone'` eagerly creates a default context with AudioWorklet nodes, which fails before user gesture. Use `import type` for types and `await import('tone')` inside effects after AudioContext is running. Call `Tone.setContext(new Tone.Context(audioContext))` to share the native AudioContext.
- **`Tone.js Effect.input` Is Not a Native AudioNode** — `Effect` subclasses (BitCrusher, etc.) set `this.input = new Tone.Gain(...)` (a Tone wrapper). Native `AudioNode.connect(effect.input)` fails with "Overload resolution failed". Use `Tone.Gain` as a bridge: `outputNode.connect(bridge.input)` works because `Tone.Gain.input` IS a native `GainNode`. Then `bridge.chain(effect, destination)` for the Tone chain.

## Stop Before Clear

Always call `stop()` before clearing tracks. Clearing React state without stopping Tone.js Transport leaves orphaned audio playing. Use `ClearAllButton` (re-exported from `@waveform-playlist/browser`) which handles this via `usePlaybackControls().stop()`.

## Shared Clip Pixel Width

Use `clipPixelWidth()` from `@waveform-playlist/core` for any pixel width derived from `startSample`/`durationSamples`/`samplesPerPixel`. Both `Clip.tsx` (container) and `ChannelWithProgress.tsx` (progress overlay) must use this shared function — never `peaksData.length`, which may be shorter than the clip when audio is shorter than configured duration.

## `handleStop` During Recording: Use `pause()` Not `stop()`

`engine.stop()` rewinds Transport to the last play-start position. During a paused/resumed recording, every resume calls `play(currentTime)` — making the most recent resume the new play-start. So calling `stop()` after `stopRecording()` jumps the playhead back to the last resume position. Use `pause()` instead during recording so the playhead stays where the user clicked stop. Plain `stop()` (when not recording) retains the standard rewind behavior.

## Track Reordering (#612)

`useEditorControls().reorderTrack(trackId, toIndex)` forwards straight to `engine.reorderTrack()` — purely organizational (see engine CLAUDE.md), never rebuilds the adapter. The engine mirror rides the existing `onTracksChange`/`tracksVersion` statechange path in `WaveformPlaylistContext`; no separate reorder-specific plumbing.

**`trackStates` re-alignment is the one non-obvious piece.** `trackStates` is a positionally-indexed array (name/mute/solo/volume/pan per track index, no track id of its own) that `reorderTrack` never touches directly — the engine reorder only moves `tracks`. The `tracksVersion` statechange handler re-derives an id→state map from the pre-reorder pairing (`tracksRef`/`trackStatesRef`, reflecting the last committed render) and re-projects it onto the new track order, so each track's mixer identity travels with it instead of staying pinned to its old index. Guarded to same-length arrays (add/removeTrack already go through a full `trackStates` reinit) and to an actual order change, so non-reorder structural mutations (moveClip/trimClip/splitClip) are a no-op here.

**UI:** `<Waveform trackReordering>` (also on `PlaylistVisualization`, default `false`) renders a `ReorderRail` (grip + move up/down chevrons, from `@waveform-playlist/ui-components`) on the default track control panel. Move buttons call `reorderTrack` directly and work with no other setup. Drag needs `ClipInteractionProvider` (the ambient `DragDropProvider`) — `SortableTrackControls` registers the row as a vertical sortable item (`data: { kind: 'track-reorder', trackId }`); `ClipInteractionProvider`'s `onDragEnd` branches on that `kind` to call `reorderTrack(data.trackId, sortable.index)` instead of the clip-move path. `SortableTrackControls` is also exported standalone for custom-controls consumers who don't use the default panel.

**`@dnd-kit/react` sortable-plugin DOM corruption (live-browser bug, fixed):** dragging the reorder grip activates two `Sortable` default plugins that do raw, React-bypassing DOM surgery — the `Feedback` plugin splices a placeholder node in on drag start and `placeholder.replaceWith(element)`s it back on drop (any pointer movement, `feedback !== 'none'`), and `OptimisticSortingPlugin`'s `reorder()` calls `insertAdjacentElement` live during `dragover` collision. Confirmed via `MutationObserver` instrumenting the React-owned row: 4-6 childList mutations per drag, final `parentElement`/`nextSibling` different from before. React's fiber tree never observes these moves, so it silently fails to patch the DOM on the NEXT reorder (drag or button) for the rest of the session — `tracks`/`trackStates` are correct (verified via render-time tracing) and the canvas track area (not `useSortable`-wrapped) reorders fine; only the panel/name column gets stuck. Two-part fix: (1) `SortableTrackControls` sets `feedback: 'move'` on `useSortable` (per-entity, via `plugins: (defaults) => [...defaults, Feedback.configure({ feedback: 'move' })]` since @dnd-kit 0.5) — **not** `feedback: 'none'`, which looks like the boundary-trim precedent (`Clip.tsx`/`AnnotationBox.tsx`) but is wrong for a _sortable_: `'none'` bails out of `Feedback`'s render function before it ever sets `dragOperation.shape`, and `CollisionObserver` requires that shape — with `'none'`, collision (and `sortable.index`) never updates and drag-commit silently stops working entirely. `'move'` skips the placeholder/replaceWith splice (`placeholder = feedback !== 'move' ? ... : null`) while keeping the unconditional shape assignment, so collision keeps working. (2) `OptimisticSortingPlugin`'s own `reorder()` splice still fires on any drag that crosses a collision boundary and isn't configurable away without losing live index tracking — `bumpTrackReorderEpoch()` (`useEditorControls`) is called unconditionally in `ClipInteractionProvider`'s `onDragEnd` for every track-reorder drag (committed or canceled) and folded into the `ControlSlot` key in `TrackControlsColumn` (`${track.id}-${trackReorderEpoch}`), forcing a remount that discards any corrupted fiber state before the next reorder. Verified with a live-browser MutationObserver check (zero residual mutations with `feedback: 'move'` alone is NOT achieved — the epoch remount is required) and `e2e/track-reorder.spec.ts`'s drag test, which checks ground-truth `data-track-id` DOM order AND the name span together (a names-only or ids-only check would have missed this class of bug — the existing button-only test never drags, so it never exercised the corrupted code path).

**Custom `renderTrackControls` consumers who mount `SortableTrackControls` themselves** must fold `trackReorderEpoch` (from `useTrackReorderPreview()`) into their own panel keys the way `TrackControlsPart` does — without it, the post-drag remount that heals `OptimisticSortingPlugin`'s DOM splice never happens for their subtree.

**`feedback: 'move'` popover-dismissal (dragged row vanishes mid-drag, fixed):** dnd-kit's `Feedback` plugin layers the dragged element via the Popover API — `popover="manual"` + `showPopover()` puts it in the browser top layer (beats every z-index/stacking context; its stylesheet's `position: fixed; z-index: calc(infinity)` is only the fallback). But `OptimisticSortingPlugin`'s `insertAdjacentElement` splice (remove + reinsert) force-dismisses a shown popover **with no toggle events** (spec: removal-dismissal fires none), and a dismissed `[popover]` element is UA-hidden (`[popover]:not(:popover-open) { display: none }`) — so the row disappeared entirely the moment the drag crossed a collision boundary, looking like it was "hidden by the track controls being dragged over". dnd-kit's own recovery (`createDocumentMutationObserver` re-calling `showPopover`) is created only `if (placeholder)` — which `feedback: 'move'` (required, see above) never creates, so 'move' sortables silently opt out of recovery. And the dismissal repeats on **every** boundary crossing (verified live: healed once manually, closed again on the next splice), so a one-shot fix is insufficient. Fix: `createDragPopoverHealer` (`src/utils/dragPopoverHealer.ts`) — a body-scoped childList MutationObserver mirroring the upstream recovery, run by `SortableTrackControls` only while `isDragSource` is true; it re-shows the popover whenever the element is connected, has the `popover` attribute, and is not `:popover-open` (microtask timing = same-frame heal, no flicker). Covered by jsdom unit tests (stubbed `showPopover`/`matches`) and a mid-drag assertion in `e2e/track-reorder.spec.ts` (element must be `:popover-open` with non-zero height after crossing the boundary — confirmed RED with the healer disabled).

**Playwright synthetic-drag calibration:** `@dnd-kit/react`'s collision detector samples position per animation frame — 1-2 coarse `page.mouse.move(..., {steps})` calls fired back-to-back can outrun that sampling and never register a collision (the drag silently no-ops: `sortable.index` stays at `initialIndex`). Use many discrete `page.mouse.move()` calls (~15) with a short `waitForTimeout` (~60ms) after each, ending at the target grip's exact center — a larger overshoot over-shifts collision into the next row (the dragged item's own shape, not just the cursor, drives collision, so extra cursor travel means extra shape displacement).

**Drag-preview layout (`trackDragPreview`, `useTrackReorderPreview()`):** `useEditorControls().setTrackDragPreview` and `useTrackReorderPreview().trackDragPreview: TrackDragPreview | null` (`{ trackId, toIndex }`, `src/utils/trackOrderPreview.ts`) publish a view-only preview of the in-progress reorder — the engine's committed `tracks` order is untouched until drop. `ClipInteractionProvider`'s `handleDragOver` sets it from the sortable's live `sortable.index` on every `dragover` (functional-set with an equality guard so repeated dragovers at the same index don't re-render); `handleDragEnd` clears it unconditionally (both commit and cancel) in the same handler that calls `reorderTrack`/`bumpTrackReorderEpoch`, so React batches the preview-clear with the commit and the columns jump straight from previewed to committed layout with no intermediate frame. `PlaylistVisualization` derives `displayOrderIds` via `applyTrackOrderPreview(tracks, trackDragPreview)` and feeds both the waveform column and the controls column from the SAME `computeTrackLayout(displayOrderIds, heightById)` map (`{ topById, totalHeight }`) — rows are absolutely positioned (`.attrs()` `top`, deliberately NOT `translateY`: a transform creates a stacking context on every row, flattening clips' `z-index: 105` beneath the ClickOverlay's `z-index: 1` and blocking all clip interactions — found by full-suite e2e, fixed by positioning with `top`) at their layout top, and DOM order never changes mid-drag. This makes `OptimisticSortingPlugin`'s live DOM splices (see the DOM-corruption note above) visually inert — they still happen and the epoch-remount + `dragPopoverHealer` fixes are still required, but the columns no longer visually rely on DOM order. Transitions (`top 150ms ease`) are gated by `useTrailingActive(trackDragPreview !== null, 200)` (`src/hooks/useTrailingActive.ts`) — a 200ms trailing-active window so a canceled drag's revert-to-original-position also animates, not just the drag itself — and are skipped entirely under `prefers-reduced-motion`. Waveform row wrappers carry `data-track-row` + `data-track-id`; the row matching `trackDragPreview.trackId` also carries `data-track-drag-source`. The drag-source's controls slot renders fully opaque (`theme.selectedTrackControlsBackground`, matching the selected-track tint) with a shadow, since it floats in the browser's top layer via dnd-kit's Popover-based `Feedback` plugin and would otherwise show the row underneath through it. Custom `renderTrackControls` consumers can read `trackDragPreview` from `useTrackReorderPreview()` to mirror the preview in their own panel.
