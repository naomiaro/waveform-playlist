# Core Package (`@waveform-playlist/core`)

Framework-agnostic types, pure functions, and utilities shared across all packages. No runtime dependencies.

## Build & Test

- **Build:** `pnpm build` (tsup, auto-externalizes deps)
- **Test:** `cd packages/core && npx vitest run`
- **Typecheck:** `pnpm typecheck`

## Key Patterns

**Sample-based architecture with tick authority:** Timeline positions use `startTick` (authoritative, optional) and `startSample` (derived cache). Duration and offset remain sample-only (`durationSamples`, `offsetSamples`). Engine enriches clips missing `startTick` on ingestion. Use `clipTimeHelpers` for seconds conversion. `clipPixelWidth` uses floor-based endpoint subtraction to guarantee no pixel gaps. `createClipFromTicks()` creates clips with authoritative tick positions.

**Multi-meter grid:** `computeMusicalTicks` accepts `meterEntries: MeterEntry[]` (not `timeSignature`). `MusicalTickData` has `pixelsPerQuarterNote` (not `pixelsPerBeat`/`pixelsPerBar`). `detectMeterChanges()` extracts meter from beat number sequences. `ticksToBarBeatLabel` removed — labels computed inline.

**`gainToDb` vs `gainToNormalized`:** `gainToDb` is the raw gain→dB conversion used by audio nodes (Tone.js `Volume` takes dB). `gainToNormalized` maps gain to 0–1 for UI meters (gain → dB → normalized with configurable floor). Do not duplicate `gainToDb` — it's shared by playout, browser, and dawcore packages.

**`gainToDb` clamps at 0.0001 (−80 dB):** Prevents `Math.log10(0) = -Infinity`. `gainToNormalized` does NOT use `gainToDb` internally — it computes `20 * Math.log10(gain)` directly because `dBToNormalized` already handles `-Infinity` via its floor check, and the clamp would change normalized output for very small gains.

**`trackChannelCount(track)`:** Returns max `audioBuffer.numberOfChannels` across a track's clips (1 with no decoded audio). Takes the structural `TrackChannelSource` (`ClipTrack` satisfies it; so do dawcore's export tracks). Selects the pan LAW for `createPanStage` and the offline render's output channel count.

**Pan stage (`panStage.ts`, #669) — the ONE pan implementation.** `createPanStage(context, pan, sourceChannelCount)` builds explicit-stereo input gain → splitter → 2×2 gain matrix → merger from `PanStageContext` (`Pick<BaseAudioContext, 'createGain' | 'createChannelSplitter' | 'createChannelMerger'>`); `panMatrix()` holds the two Web Audio `StereoPannerNode` laws (mono: equal-power, never mixes channels; stereo: fold-over, unity at centre), chosen by the SOURCE channel count. Consumers: `@dawcore/transport` `TrackNode`, dawcore `exportAudioImpl`, playout's three track classes and browser `useExportWav` (the last two via Tone's `rawContext`). Never a `StereoPannerNode` (law follows the layout it receives — the pre-fader effects chain's output) and never a Tone `Panner` (channel mode locked under standardized-audio-context). Don't copy the stage into another package; core is its home. This is the only module in core that creates audio nodes — it stays dependency-free because the context is passed in.

**Effect registry (`effects/registry.ts`, #679):** moved here from dawcore so one `registerEffect()` serves `<daw-editor>` and the React hooks. It creates no audio nodes itself; a definition's `create(ctx, params)` and optional async `prepare(ctx)` are handed the context. The state (definitions and the per-context prepared records) is on `globalThis` under `Symbol.for('@waveform-playlist/core/effect-registry/v1')`, not in the module (versioned: every copy that shares the state must agree on its shape, so a change to `RegistryState` needs a new key): `browser` pins core exactly, so an app whose own core version differs installs two copies, and with a module-level map an effect registered through one would be unknown to hooks using the other. Core registers nothing; dawcore's `native-*` built-ins are registered by `@dawcore/components` on import (marked `builtIn: true`, only when the name is free; a host lists its own catalogue plus app registrations, so the React picker skips `builtIn` definitions), each only if that name is not already registered (no overwrite, no warning: an app's earlier registration under that name wins). `prepareEffect` runs a hook once per context per definition object (a re-registered type prepares again, a failed run is forgotten); hosts call `ensureEffectPrepared` before `createEffectInstance` wherever they can await, and `createEffectInstance` rewraps a `create` throw with a prepare hint only when the type has a hook that has not settled on that context (the hint is host-neutral: `await prepareEffect(type, audioContext)`, with the `<daw-editor>` form in parentheses; the original error is kept in `cause`). An instance whose initial `applyParams` throws is disposed before the error is rethrown, because the caller never receives it. **`NativeEffectInstance.output` contract:** the host owns every connection out of `output` and disconnects ALL of them when it rewires the chain (the React rack does this for every instance on every rewire), so a definition must not connect `output` to anything inside the effect; a feedback path or a tap is taken from a node before it. The names are `Native…` because `@waveform-playlist/browser/tone` has its own `EffectDefinition`/`EffectInstance` for the Tone catalogue.

**Fade curves:** `fades.ts` generates `Float32Array` curves for `setValueCurveAtTime`. No Tone.js dependency — works with native `AudioParam`. The browser package's `useExportWav` also uses `applyFadeEnvelope` which delegates to these curve types.

**Keyboard shortcuts:** `handleKeyboardEvent` is a pure function — no React dependency. The `undefined` vs `false` distinction in modifier keys matters: `undefined` = match any state, `false` = must NOT be pressed.

**Musical ticks:** `beatsAndBars.ts` uses Tone.js-compatible PPQN (192). `musicalTicks.ts` uses 960 PPQN for finer resolution in snap-to-grid. Both accept PPQN as a parameter. **Grid lines restart at each bar line** (#643): `snapTickToGrid` snaps within the bar containing the tick (the line after the bar's last whole subdivision is the next bar line; ties snap up; a line is a fixed point) and `computeMusicalTicks` draws its bar/beat/eighth/sixteenth levels the same way — the same restart-at-bar rule as `@dawcore/transport`'s `quantizeTick` (nearest, ties up, lines are fixed points), so a drag snap, the drawn grid and a transport quantize agree in odd meters (7/8 quarter grid: 0, 960, 1920, 2880, 3360 — never 3840). Remaining differences from `quantizeTick`: core returns unrounded ticks, rounds triplet steps via `snapToTicks`, accepts negative ticks, and caps the next line at the following meter entry instead of requiring entries on bar boundaries; a degenerate entry (numerator 0) falls back to a plain entry-anchored snap rather than NaN. Only the `coarse` level steps meter-independently from the segment start (constant visual density). Unchanged wherever the bar is a multiple of the step — all of 4/4, but NOT 3/4 or 6/8 half-note/triplet grids (3/4 `'1/2'`: 0, 1920, 2880, not 3840). The parity test in `musicalTicks.test.ts` sweeps 7/8, 5/4, 7/16 and a 4/4→7/8 map at every zoom level.

**A track has one kind (#756).** `ClipTrack.kind: 'audio' | 'midi'` is required and every clip on the track is of that kind; `createTrack` defaults it to `'audio'`. The rule is enforced in one place, `assertTrackKind`, called by `PlaylistEngine.setTracks/addTrack/updateTrack`. Everything else that needs to know (the Tone adapter, the React view, recording, dawcore) reads `trackKind(track)`; none of them infers the kind from the clips. Do not add a second definition of "MIDI clip": use `clipKind`.

## Clip Constructors

- **Prefer `createClip()` Over `createClipFromSeconds()` When Samples Known** — `createClipFromSeconds` round-trips through float seconds: `samples/rate → seconds → Math.round(seconds*rate)`. Safe when the same rate is used for both legs, but drifts silently when rates differ (e.g., `effectiveSampleRate` vs `audioBuffer.sampleRate`). Use `createClip()` with integer samples when available. For tick-based creation (variable-tempo), use `createClipFromTicks()` which sets `startTick` as authoritative and derives `startSample`.
- **`createClipFromSeconds` Supports Peaks-First Rendering** — `audioBuffer` is optional. Provide `waveformData` (from `waveform-data.js`) + `sampleRate` + `sourceDuration` instead. This enables rendering waveforms before audio decode completes. The `WaveformDataObject` interface defines the required shape.

## WaveformData Constraints

- **`WaveformData.resample({ scale })` only resamples to coarser (larger) scales** than the source. Attempting to resample finer throws. When caching `WaveformData`, validate `cached.scale <= requestedScale` before returning cache hits.

## `SpectrogramConfig` Does Not Include `colorMap`

`SpectrogramConfig` covers FFT/render parameters only (`fftSize`, `hopSize`, `windowFunction`, `frequencyScale`, `minFrequency`, `maxFrequency`, `gainDb`, `rangeDb`, `zeroPaddingFactor`, `alpha`). The color map is a separate `ColorMapValue` field on consumers — `SpectrogramProvider` props, `SpectrogramOrchestrator` options, `editor.spectrogramColorMap`. Do not pass `colorMap` inside `SpectrogramConfig` — it will fail typecheck.
