# Dependency updates

Upgrades go to the latest stable only; bumping a 0.x peer range is a major (root `CLAUDE.md`, "Semantic Versioning").

## pnpm and Dependabot

- **What Dependabot opens (`.github/dependabot.yml`):** one grouped PR with the npm security fixes it makes, and one weekly grouped PR for the GitHub Actions in `.github/workflows`. npm version updates are off (`open-pull-requests-limit: 0`). Security PRs always target the default branch (`dev`). **It makes fixes for direct dependencies only:** every Dependabot PR since the move to pnpm (#267 to #648) bumped a direct dependency but #622 (a transitive esbuild alert: it changed only `pnpm-lock.yaml`, did not move esbuild and was closed as superseded by #631), and none was opened for the 12 packages that were only transitive among the alerts #879 closed (body-parser, qs, undici and nine more), not even for the nine whose fix was inside the parent's range (eight) or came through an existing override (serialize-javascript). Transitive alerts in `pnpm-lock.yaml`, and any whose parent at its latest release still asks for the vulnerable major (an override, as tinypool and webpack-dev-middleware on #879), need a sweep by hand as below; Dependabot closes its own PRs once their alerts are gone.
- **A sweep by hand checks itself against the alerts:** test every open alert's `vulnerable_version_range` against every version of that package in the new `pnpm-lock.yaml` with `semver.satisfies` (0 left = done), and run the same test over the fixed alerts. When an override forces a major on a tool, run the code path that loads it: the website's normal build never starts tinypool (`future.v4: true` turns on `faster.ssgWorkerThreads`, but the pool falls back to the current thread below 100 pages per thread, and the site has about 60); `DOCUSAURUS_SSG_WORKER_THREAD_COUNT=4 docusaurus build` does (the code comment's `DOCUSAURUS_SSG_WORKER_THREADS` is wrong; `DOCUSAURUS_PERF_LOGGER=true` prints `SSG Worker N` lines when the pool runs). webpack-dev-middleware runs only under `storybook dev`, not `storybook build`.
- **Transitive Dependabot alerts**: try `pnpm update -r <pkg>...` first (refreshes the lockfile within parents' existing ranges) before adding a `pnpm.overrides` entry — most alerts are just stale lockfile patches the parent range already allows. Reserve overrides for a version an intermediary pins _below_ the fix (forced; may break upstream's tested range, e.g. js-yaml 3.x via gray-matter).
- **`pnpm update -r <names>` silently degrades to direct-deps-only** (pnpm 8) if you pass `--depth Infinity` OR if any named package is a direct dep somewhere in the workspace (e.g. `uuid`, `esbuild` in browser) — the transitive names in the same call are then skipped with no error. Keep direct deps out of the list and confirm by grepping `pnpm-lock.yaml` for the new versions.
- **Neither `pnpm update` nor `pnpm install` moves a package's AUTO-INSTALLED peer entry while the old version still satisfies the range** (pnpm 8, 2026-11-24, dnd-kit 0.5.0 → 0.5.3): `browser` and `annotations` declare `@dnd-kit/*` only as peers, and their importer entries stayed at 0.5.0 after `pnpm update -r` with and without a version, while ui-components' devDependency moved, which left two copies of `@dnd-kit/dom` in the workspace (dnd-kit's `Feedback` is matched by constructor identity). `pnpm update -r <pkg>@^x` also rewrote the devDependency specifiers and re-resolved `@types/react` for the website (a second copy, 19.3.0 and 19.3.1); hand-editing the specifiers and running `pnpm install` against the old lockfile did not. What worked: the specifiers by hand, `pnpm install`, then the importer `version:` lines of the peer-only packages edited (count asserted), the now-orphaned old package blocks deleted (pnpm does not prune them), `pnpm install --frozen-lockfile`, and a plain `pnpm install` that leaves the file byte-identical. That `pnpm install` still re-resolved unrelated entries, as on #891 below: 72 `tslib` references outside the dnd-kit blocks moved 2.8.1 → 2.9.1 (docusaurus, storybook's docgen plugin, `@peculiar/*`, `automation-events`, `react-remove-scroll`, `no-case`, `recast`): 18 in `dev: true` blocks, 20 in `dev: false` blocks and 34 in blocks without a `dev` field; and two `webpack-dev-server`/`webpack-dev-middleware` keys changed suffix. A grep for changed package KEYS (`^[+-]  /`) misses the moves inside blocks; count changed dependency lines too (`git diff dev... -- pnpm-lock.yaml | grep -c '^+.*tslib: 2.9.1'`) and list them in the PR. Check what each package links, not the lockfile: `readlink packages/<pkg>/node_modules/@scope/<name>` (`require('<pkg>/package.json')` fails for a package whose `exports` omits it).
- **Before removing a `pnpm.overrides` entry, check the FIXED alert history, not just open alerts** — `gh api --paginate 'repos/naomiaro/waveform-playlist/dependabot/alerts?state=fixed&per_page=100'` and test each `vulnerable_version_range` against the new lockfile; a dropped override silently reopens old alerts (serialize-javascript and uuid did, 2026-10-06). Scope a new selector to the parents' declared spec (`esbuild@^0.27.0`, not `esbuild@<0.28.1`) so unaffected consumers aren't dragged along (vite 6's `esbuild ^0.25` was one, until #879 removed vite 6). `pnpm audit` reads the npm advisory DB, which runs ahead of this repo's Dependabot list — use it to find in-range fixes worth taking early.
- **A peer of a regular dependency is forwarded: "the source imports neither" is not a reason to remove a peer.** recording imports neither `tone` nor `styled-components` but depends on playout and ui-components, which peer on them; #829 listed both as stale and #896 kept them (maintainer's choice), and added the missing `react-dom` to annotations and recording (ui-components peers on it). Before removing or adding a peer, list the package's regular dependencies (third-party ones too) and their peers. A peer every working install already satisfies through a dependency is a patch to add.
- **A deep import that exists only through a package's `exports` map sets a tooling floor for consumers.** Phosphor 2.1.10's `@phosphor-icons/react/dist/csr/<Name>` resolves only where `exports` is read (webpack 5, Vite, Jest ≥ 28, Node ≥ 14.13 for subpath patterns); a resolver that ignores `exports` (browserify `resolve`, or enhanced-resolve with `exportsFields: []`) cannot find it, which is how webpack 4 and Jest 27 resolve (#896; not run on those tools). Read the `require` condition too: Phosphor maps every deep path to its whole CJS bundle, so only ESM tools load less. Say the floor in the changeset.
- **Check a built entry's imports with a resolver, not by loading it in plain Node.** `import('packages/ui-components/dist/index.mjs')` stops at `styled.button is not a function` (styled-components' CJS interop) after every import has resolved, and Phosphor's icons do not render from plain Node CJS (its package is `"type": "module"`), on `dev` too.
- **`dependencies`→`peerDependencies` move churns the lockfile** — it changes pnpm hoisting and can re-resolve unrelated transitive deps (e.g. `@types/react` 19→18 from a workspace `^18` vs react-19 mismatch). A pristine-base `pnpm install` no-op confirms the move (not pre-existing drift) is the cause; `--frozen-lockfile` still passes if internally consistent.
- **Adding ANY dependency re-resolves unrelated transitive versions on this lockfile** (2026-11-23, #891): `pnpm add -Dw semver@^7.8.3`, and a hand-edited `package.json` line plus `pnpm install`, both also moved babel's `semver` 6.3.1 → 6.3.2 and `tslib` 2.8.1 → 2.9.1 (37 lockfile lines for one new entry). Read `git diff pnpm-lock.yaml` before committing a new dependency; for a few lines of build-script logic, writing them was the smaller change (`scripts/build/install-specs.mjs`, `satisfiesFloors`).
