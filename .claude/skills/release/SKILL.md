# Releasing

No release is started unless the maintainer asks for one. Every PR that changes `packages/*/src` adds a changeset; that rule is in root `CLAUDE.md`.

## Versioning and publishing

**Stable Releases:** Publish without tag to update `@latest`. `dev` is in pre mode, so a stable release starts with `pre exit` ("From dev to main"); a prerelease is "Prereleases: `@next` from dev".

```bash
pnpm release:version   # changeset version — computes all bumps incl. the dependent cascade
pnpm release:publish   # pnpm build && changeset publish --no-git-tag
```

**Version Bumping — Changesets owns the math (since 2026-07-05):** every PR that changes `packages/*/src` adds a changeset (`pnpm changeset`; pick `patch` for `@dawcore/*` — zerover, never minor/major). Each package follows its own semver independently. At release time `pnpm changeset version` computes all bumps INCLUDING the exact-pin dependent cascade (validated against the 2026-07-05 manual closure: identical 13-package result; `onlyUpdatePeerDependentsWhenOutOfRange` keeps floating peer floors like dawcore's `>=0.0.13` untouched; private packages excluded via `privatePackages`). Review the version diff, then `pnpm release:publish` (= `pnpm build && changeset publish --no-git-tag`: builds everything first — no prepublish hooks exist — then publishes topologically, skipping versions already on the registry; safe to re-run after a partial failure). Don't name a script `version` — `pnpm version` resolves to pnpm's built-in, not the script. The old `pnpm version:bump` (`scripts/bump-version.js`) is REMOVED — it synced ALL packages to one version, incompatible with independent versioning. `changelog: false` — the hand-written GitHub release remains the record. Then the chore(release) commit + GitHub release as below. **`changeset version` CONSUMES the `.changeset/*.md` files** — reverting `packages/*/package.json` after a dry-run does NOT restore them; re-create the changeset (or revert `.changeset/` too) before re-running. Validation pattern for config changes: write a throwaway changeset bumping one package, run `pnpm release:version`, diff the computed closure against expectation, then revert everything including `.changeset/`.

**Independent Versioning:** `@dawcore/components` and `@dawcore/transport` have their own version schemes (0.x.x), separate from the main `@waveform-playlist/*` packages.

**First-time scoped packages:** New scoped packages (`@waveform-playlist/*`, `@dawcore/*`) need `--access public` on first npm publish:

```bash
pnpm publish --filter @waveform-playlist/NEW-PACKAGE --no-git-checks --access public
```

**Verifying fresh publishes:** `npm view` caches 404s — a just-published new package can look missing for minutes. Verify with `curl -s https://registry.npmjs.org/@scope%2fname` instead.

**Pre-publish workspace-dep sweep:** for every `workspace:*`/`workspace:^` dep of the packages being published, verify local version == registry latest (during a prerelease: that the local version exists on the registry, as `next` for a package the pre run bumped and as `latest` for one it did not, such as wam and worklets in the first run) (`curl -s https://registry.npmjs.org/...`) — a feature PR that bumps a package version without publishing it (e.g. media-element-playout 12.3.0 in #473) makes dependents' exact pins unresolvable at install time.

**Hand-written peer floors are not raised by changesets: check them at every release.** `onlyUpdatePeerDependentsWhenOutOfRange` leaves a floating floor (`">=7.0.0"`) alone, so it goes stale without anyone noticing: on 2026-11-14 the engine's peer range on core was `>=7.0.0` while it imported `createSourceLoader`, `createValueSource`, `isLoadingClip` and `assertTrackKind`, which exist only in the unreleased core 13 (four pending majors). When reviewing the output of `pnpm release:version`, grep each `peerDependencies` floor in `packages/*/package.json` and compare it with what the package imports at runtime from that peer; the engine's floor on core was raised to `>=13.0.0-0` on 2026-11-23, before the first prerelease (a floor above the workspace's version was then tried: the version runs give the same result), and `@dawcore/components`' floor on core (`>=12.7.0`) has not been checked. A floor above the workspace's current version prints `must depend on the current version` at every version run until the bump ("Prereleases" below says what that line means); two prerelease runs and the exit gave the expected versions with it.

**Republish cascade is MANDATORY — never publish a package without its dependents (the outbound direction of the sweep above; AUTOMATED by `changeset version` since 2026-07-05 — this note is the why, and the fallback procedure if changesets is bypassed):** regular `workspace:*` deps publish as **EXACT pins** in the tarball; `workspace:^` peers publish as carets (verified from packuments). Publishing pkg X without republishing every published package that lists X in `dependencies` leaves those dependents pinning the OLD X — consumers silently install duplicate/stale copies. This happened: the core@12.5.0/ui-components@13.1.1 release skipped the cascade, so browser@15.2.0 shipped `core 12.4.0` + `ui-components 13.1.0` pins until the next sweep (2026-07-05) cured it. Procedure: compute the transitive exact-pin dependent closure of every bumped package (grep `"<pkg-name>"` across `packages/*/package.json` `dependencies`), patch-bump + republish ALL of it in topological order, then curl the new packuments and check the `dependencies` pins are the fresh versions. Caret peers force a republish only when the bump escapes the range (any major; ANY bump for zerover `^0.0.x` peers like `@dawcore/*`).

**`workspace:*` in devDependencies does NOT trigger the republish cascade** — devDeps are build-time only (never published pins), so changesets correctly excludes such packages (e.g. transport/worklets in the 2026-07-12 annotation-suite release). When auditing a computed closure, check WHICH section a workspace ref lives in before suspecting a missed bump.

**Security-key-only 2FA (since 2026-10-28): `changeset publish` cannot publish from this session.** The account has no authenticator app, only a hardware key, so there is no OTP to type and npm has no TTY here — every package fails `EOTP` ("Open this URL in your browser to authenticate") before anything uploads, and `changeset publish` itself pre-prompts for a typed code. Procedure that works: `pnpm release:version` → review the closure → `pnpm build` → hand the user a dependency-ordered chain of `pnpm --filter <pkg> publish --no-git-checks && …` (toposort `dependencies` across `packages/*/package.json`) to paste into a REAL terminal, not the `!` prompt (npm's `auth-type=web` opens the browser for one key tap per package) → verify from here: `~/.npm/_logs` `http fetch PUT 202` + `verbose exit 0` per package is the immediate proof, packuments lag 3–8 minutes (poll with `Cache-Control: no-cache`) → chore(release) commit → GitHub release. `! npm login` fixes an expired token (`npm whoami` E401) but does not bypass 2FA for publishing. The `--otp` flow below applies only if an authenticator app is added as a second 2FA method.

**npm auth failures during `changeset publish` are disguised:** an EXPIRED token surfaces as `E404 Not Found - PUT …` ("could not be found or you do not have permission") on every package, not as a 401 — check `npm whoami` first (it returns the real E401). With 2FA-for-writes enabled on the account, `changeset publish` spawns `npm publish` with no TTY, so npm can't open its OTP prompt and fails with `E403 … Two-factor authentication or granular access token with bypass 2fa enabled is required` — even when the user runs it themselves. Fix: `pnpm exec changeset publish --no-git-tag --otp=<6-digit code>` (one code covers all packages in the run), or a granular token with 2FA bypass in `~/.npmrc`. Publish PUTs return `202` and packuments lag the CDN by 1–3 minutes — poll `curl` with `Cache-Control: no-cache` before concluding a publish failed (the npm debug log's `http fetch PUT 202` + `verbose exit 0` lines are the immediate proof).

**Build before publishing:** No package defines prepublish hooks — always run `pnpm --filter <pkg> build` before `pnpm publish`, or the tarball ships a stale `dist/`.

## Prereleases: `@next` from dev

`dev` is in changesets pre mode since 2026-11-23 (`.changeset/pre.json`, tag `next`): `pnpm release:version` there gives `x.y.z-next.N`, and the changeset files stay until pre mode is left. The first prerelease (`-next.0`, 16 packages) was published by hand that day.

- **A prerelease is published by `.github/workflows/publish-next.yml` after every push to `dev`** (maintainer, 2026-11-23, after Tone.js's release workflow), in four jobs:
  - `version` (read only) runs `changeset version`, checks the result (`scripts/release/check-version-run.mjs`: no hand-written range on a package of this repository rewritten, every new version `x.y.z-next.N`, `@dawcore/*` still `0.0.x`, every package with a prerelease version known to npm), builds, runs the unit tests, and hands over one line: the list of `name: version`;
  - `commit` (may push) writes the bump itself with `scripts/release/apply-version-bump.mjs`, from its own checkout: it takes a version from that list only when it is the next prerelease of that package (the counter one up, on a patch, minor or major step from the version in `pre.json`'s `initialVersions`; `@dawcore/*` the patch step only), replaces the one `"version"` value in the file as it is on `dev`, adds the changeset files that are there to `pre.json`, and pushes `chore(release): next (N packages)`. Run on the real list it produced the diff the version step produces, byte for byte;
  - `pack` (read only) checks out that commit, builds, and packs every prerelease version the registry does not have (`scripts/release/publish-next.mjs --pack`);
  - `publish` (may publish) uploads those tarballs with the tag `next` (`publish-next.mjs --from`). What a tarball is, it asks npm's own reader (the `pacote` inside the npm that uploads, called as `npm publish` calls it), and refuses one that is not the expected package at the expected version, or whose manifest has a `tag` (npm puts a manifest's `tag` above `--tag`: it moved `latest` in a test against a fake registry) or a `publishConfig`. Afterwards it compares the registry with what it read before, for all 18 packages: any dist-tag but `next` that changed, or any version that appeared and was not meant to, fails the run in capital letters.

  The rule behind the four: the two jobs that run other people's code (dependencies' install scripts, the build tools, the tests) can only read; the two that hold a right install and build nothing, run `scripts/release/` (which imports nothing but node's own modules, and npm's reader), and decide from their own checkout whatever they can. Keep it so: no `pnpm install` and no artifact in `commit`, no `pnpm install` in `publish`, no import of a package in `scripts/release/`, and never a second way of reading a tarball beside npm's (three review rounds each found a tarball that `tar` and npm read differently). What the code running in `version` and `pack` can still decide: which of the allowed next versions a package gets, and what is inside a published package, since it builds it, as it does in a build on your own machine. The publish job takes the tarballs in through `actions/download-artifact`, pinned to v8.0.2: the v4 line unpacks with a library that lets a crafted artifact write outside its folder (GHSA-6jrj-vc65-c983).

  A merge with no new changeset changes no version and publishes nothing. `main`, the release number in the root `package.json`, the git tag and the GitHub release are not touched: they belong to stable releases (the site's config throws on a root version that is not three numbers).
- **When it fails:** a failed check is fixed by a PR (usually a range that needs its alternative, below). A run that committed the bump and then failed to publish is repeated with "Run workflow" on `dev` (on another branch the `version` job is skipped): the version step finds nothing, and what the registry has is skipped. One package that fails does not hold back the others; until the next run a dependent can then be on `next` while a package it pins is not, and installing that dependent fails for that long. If `dev` moved while a run was building, its push is refused, it publishes nothing, and the run the newer merge started does both.
- **npm trusts that workflow, not a token.** Every package has a "Trusted Publisher" entry on npmjs.com (Settings of the package): user `naomiaro`, repository `waveform-playlist`, workflow `publish-next.yml`, environment `npm-next`, allowed action `npm publish`. The GitHub environment `npm-next` accepts deployments from the branch `dev` only, which is what stops a copy of the workflow on another branch. npm has no way to limit an entry to a dist-tag or to prereleases (its documentation, read 2026-11-23): that only `-next.N` versions with the tag `next` leave this workflow is decided in `publish-next.mjs`. So a change to that script or to the workflow file is a change to what can reach npm without the hardware key, `latest` included: read such a diff as that, and a change to `pnpm-lock.yaml` as a change to the code that builds what is published. An entry cannot be edited (delete and create), is not checked when saved (a typo shows at the first publish), and expires when its first publish does not succeed within 2 days.
- **A NEW package** has no entry and no first version, and the workflow cannot publish it: the check fails the run when a package with a prerelease version has a name unknown to npm, before anything is committed. Publish its first version by hand, create its entry, then merge it.
- **By hand, when the workflow cannot be used:** `pnpm release:version` → `node scripts/release/check-version-run.mjs` → `pnpm build` → `node scripts/release/publish-next.mjs` in a real terminal (it packs and publishes with the terminal's npm login: one key tap covers about five minutes) → a `chore(release)` commit on `dev`. `--dry-run` packs and lets npm check each upload without sending it; `--list` only says what the registry lacks. npm 11 refuses a prerelease version without a tag; the script always passes `--tag next`.
- **The next one:** each later run raises `N` for the packages with new changesets and for their dependents (`core@13.0.0-next.1` took `browser`, `ui-components` and the others to `next.1`; the engine, which only peers on core, stayed at `next.0`).
- **A stable release starts with `pnpm exec changeset pre exit`.** With `pre.json` in `exit` mode or gone the workflow publishes nothing. Merge nothing with a changeset while the release PR is open: the workflow would bump `dev`, and the release PR's manifests and `pre.json` would conflict with it. The versions `pnpm release:version` then gives are the ones a run without pre mode gives (compared for all 18 packages). Enter pre mode again afterwards (`pnpm exec changeset pre enter next`) in a PR of its own.
- **A hand-written peer range must admit the prereleases the peer will get, and every `peerDependencies` block is diffed after each `pnpm release:version`.** `>=12.7.0` does not match `13.0.0-next.0`: a range matches a prerelease only when one of its comparators has a prerelease on the same `major.minor.patch`, and changesets asks `semver.satisfies` without `includePrerelease`. Two separate things then happen (`@changesets/assemble-release-plan` `shouldBumpMajor`, `@changesets/apply-release-plan` `shouldUpdateDependencyBasedOnConfig`):
  - the range is rewritten to `>=<the new version>` (`>=13.0.0-next.0`), for any bump of the peer, a patch included. `pre exit` does not undo it: a stable `@dawcore/components` would have kept `@dawcore/wam >=0.0.5-next.0` and dropped wam 0.0.1 to 0.0.4;
  - when the peer's own bump is a minor or a major, the dependent is bumped as a MAJOR: `@dawcore/components` came out as `1.0.0-next.0` for the engine's major (core's major only rewrote that floor: the edge to core was outside the dependents graph in that run, see the next point but one).

  What prevents both is a range that admits the coming version's prereleases: `>=13.5.0 || >=14.0.0-0`. All nine hand-written ranges on packages of this repository do. Seven by an alternative: dawcore's on faust, midi and wam (the next patch; `@dawcore/*` is zerover and only ever gets a patch, which is why wam, with no changeset yet, has one alternative), on core and the engine (their pending major) and on worklets (no changeset yet and any bump possible, so all three: `>=12.0.0 || >=13.0.1-0 || >=13.1.0-0 || >=14.0.0-0`), and playout's on the engine. Two are a floor on the coming version itself: dawcore's on transport (`>=0.0.16-0`) and the engine's on core (`>=13.0.0-0`, a real floor: it needs core 13).

  A range of this kind covers one `major.minor.patch`, so it is right only for the bump the peer has now. A peer whose pending bump grows (a patch that becomes a minor) needs a new one, and after a stable release ALL nine are stale: a new cycle with one minor changeset for core gave `engine@15.0.0-next.0`, `@dawcore/components@1.0.0-next.0` and `browser@18.0.0-next.0` (run in a copy). So:
  - **after every version run, before committing:** `node scripts/release/check-version-run.mjs` (the workflow runs it; it compares the manifests with `HEAD` and exits 1 on a rewritten range), or by eye from the repository root: `git diff -- ':/packages/*/package.json' | grep -B2 -A2 '>='`. A rewritten range, or a dependent whose bump is larger than its changesets ask for, means a range did not admit the new version. Restore, fix the range, run again. Empty output is the pass (the `:/` makes the pathspec work from any directory; a plain `packages/*` prints nothing from inside a package).
  - **a stable release removes them, and entering pre mode again adds new ones.** After `pre exit` and the version run, each range goes back to a plain floor on stable versions (`>=13.5.0 || >=14.0.0-0` → `>=13.5.0`, or the raised floor when the package now needs the new version; `>=13.0.0-0` → `>=13.0.0`), so a stable package does not ship ranges that name prereleases. Before `changeset pre enter next` the next time, with the peers' next bumps unknown, each of the nine gets the three alternatives worklets has (next patch, next minor, next major of the peer's released version), then a version run on a scratch branch and the diff above.
- **`Package "X" must depend on the current version of "Y"`** (printed several times per run) means X's range on Y does not match Y's version in the workspace, and changesets leaves that edge out of its dependents graph for the run: a bump of Y does not reach X. Before the first prerelease it prints on `dev` for three edges whose floors are above the released versions (dawcore's on transport and on core, the engine's on core) and for none after the bump; harmless here, because dawcore and the engine have changesets of their own.
- **Who needs the alternative when installing:** npm does (it checks a peer with plain `semver.satisfies`); pnpm 8.15 accepts a prerelease for a plain floor, except where the floor is the prerelease's own version (`>=0.0.16` against `0.0.16-next.0`).
- **Workspace ranges need nothing:** `workspace:*` is published as the exact prerelease (`core@13.0.0-next.0`), `workspace:^` as a caret on it (`browser@^17.0.0-next.0`), read from packed tarballs.
- **A build writes the versions of the manifests into browser and dawcore** (their install hints name peer ranges and carets on peers' versions, #884: `scripts/build/install-specs.mjs`), so what is published must be built AFTER the version step, from the bumped manifests (for a stable release also after the peer ranges are back to plain floors, "From dev to main" step 1). The workflow and the orders by hand already do; a `dist/` built before `pnpm release:version` names the old versions.
- A fix released from `main` is a normal release: `main` has no `pre.json`.

## From dev to main

`dev` is where a release is prepared; `main` is the commit that npm `latest` was published from (root `CLAUDE.md`, "Two branches").

1. On `dev`: `pnpm exec changeset pre exit` (`dev` is in pre mode: "Prereleases" above; without it the versions are `-next.N`), then `pnpm release:version`, the hand-written peer ranges back to plain floors ("Prereleases": "a stable release removes them"), the release number in the root `package.json`, the stable announcement bar, the root README's stable facts (below), the `chore(release)` commit, through a PR like any other change.
   - **The root README.** Its top sections describe the release that is stable today and the difference between it and next; with this release that difference is gone. Read every sentence of "Stable and next", "Install", "Quick Start" and "Documentation" (stable is not always named: the `annotations@latest` example is about it) and rewrite it for the new stable. In the version of 2026-11-23 those are:
     - the React paragraph: stable `browser` takes 18.2 or 19, but its optional packages peer on React 18 only (#888);
     - "A `latest` package beside `@next` ones can fail…" with its `annotations@latest` peers on `browser ^16` example;
     - the sentence under the Quick Start: "This is the next API. The stable equivalent is in the stable Getting Started", with its `useAudioTracks` note (#887);
     - "To move a project from stable to next, see the upgrade guide" and the "From stable to next" upgrade-guide line in Documentation, which name the move this release makes; with them, the title of `website/docs/react/upgrading.md` ("Upgrading to the next major");
     - "Without the Tone.js engine … npm still installs `tone` today" (#886), if the release ships its fix.
   - **Check each fact again against the new stable's peers** rather than editing words: `curl -s https://registry.npmjs.org/<scope>%2f<name>` after the publish (`npm view` caches 404s, "Verifying fresh publishes" above). Close an issue the README cites once the release fixes it, and #887 (about the live stable page) only after step 3 has moved `main` and the site has deployed. #887 and #888 both stop applying if the release ships the next major.
   - **This commit is also what `main` becomes,** so `main`'s README is this file, and "This README describes next, the code on `dev`" is false on `main` from the first commit to `dev` after the release (the `pre enter next` PR, "Prereleases" above). Leave it as it is: GitHub shows `dev`'s README, and `main`'s copy is read only by someone browsing that branch.
2. Publish from that commit (the hardware-key procedure above). Then point `next` at the release (maintainer's choice, 2026-11-23). Otherwise `@next`, which the README and every command of the next docs install, gives the last prerelease (`17.0.0-next.5`), older than `latest` (`17.0.0`), until the next merge with a changeset.
   - **Make the chain.** Give the maintainer one command per public package, for a real terminal like the publish chain. The version is the one in that package's manifest at the release commit, so `next` equals `latest` for all 18, including those the release did not bump:

     ```bash
     node -e 'for (const d of require("fs").readdirSync("packages")) { try { const p = require(`./packages/${d}/package.json`); if (!p.private) console.log(`npm dist-tag add ${p.name}@${p.version} next`); } catch {} }' | paste -sd'&' - | sed 's/&/ \&\& /g'
     ```

   - **Check it from here.** Each packument's `dist-tags` must show `next` equal to `latest`, read with `curl -s -H 'Cache-Control: no-cache' https://registry.npmjs.org/<scope>%2f<name>`. Whether npm asks for the hardware key on `dist-tag add` had not been tried (2026-11-23).
   - **The next prerelease moves `next` on as usual.** `publish-next.yml` publishes `x.y.z-next.0` of the following version with the tag `next`. Its registry check is about what that run publishes: a dist-tag other than `next` that changed, or a version that appeared and was not meant to. A `next` moved by hand between runs is neither.

3. Move `main` to the release commit, named by its SHA (`dev` may have moved on since: `origin/dev:main` would publish unreleased work as the stable site and put the tag on it):

   ```bash
   git fetch origin
   RELEASE=<sha of the chore(release) commit on dev>
   git merge-base --is-ancestor origin/main "$RELEASE" && git push origin "$RELEASE:refs/heads/main"
   ```

   The push is a fast-forward and is refused when it would not be; never force it. When the ancestor check fails, a fix was committed on `main` and not merged back: merge `main` into `dev` first with a real merge commit (`gh pr merge --merge`, or a merge pushed to `dev` as `959f4e92` was), never a squash, which leaves the check failing. A fix released from `main` has bumped versions there, so expect that merge to conflict in `package.json` files (not tried).
4. Tag and release that commit: `gh release create v<release number> --target "$RELEASE" …`.

After the fast-forward `main`'s files are exactly `dev`'s. What `main` carried of its own is gone with it, as intended: on 2026-11-23 that was five redirect pages under `website/static/docs` and `website/static/examples`, for pages only the next docs had.

The link between the branches is the merge commit `959f4e92` on `dev` (`git merge -s ours`, 2026-11-23): it recorded the new `main`'s first commits as merged while keeping `dev`'s files. A push to `main` or `dev` deploys both versions of the site.

## The release number

**A release has one number: `version` in the root `package.json`** (maintainer, 2026-11-23; the idea is openDAW's SDK version, without its meta-package). The packages keep their independent versions; the release number names the set that was published together. It starts at 16.0.1, the release tagged `transport-engine-improvements`.

- **Bump it by hand in the `chore(release)` commit** (changesets leaves a private root alone): a major when any package in the release has a major, else a minor when any has a minor, else a patch. A release of `@dawcore/*` only is a patch.
- **The git tag is `v<release number>`** (`v17.0.0`). What the release is about goes in the GitHub release's title (`v17.0.0 — the arrangement`), and its notes list every published package with its version. Tags before `v16.0.1` are descriptive names and stay.
- **The docs read it.** The version dropdown of the site shows `v<release number>` for the stable build (`website/CLAUDE.md`, "Versions of the Site"). The docs of the release before are not kept: the stable site is replaced.
- **The stable build's announcement bar** (`releaseAnnouncement` in `website/docusaurus.config.ts`) names the release and links its notes: update it in the release commit.

## The commit, the tag and the GitHub release

- **A full release is THREE artifacts** — easy to do partially: (1) npm publish (`pnpm --filter <pkg> publish --no-git-checks`), (2) the `chore(release): pkg@x.y.z` commit on `dev`, which `main` is then moved to ("From dev to main"), (3) the GitHub release on the tag `v<release number>` (`gh release create`). "Bump and publish" naturally stops after (1)+(2) — the GitHub release is a separate step, easy to forget. Preview the tarball first with `pnpm --filter <pkg> publish --no-git-checks --dry-run` (shows files/version/tag/access before the irreversible publish); verify the publish landed with `curl -s https://registry.npmjs.org/@scope%2fname` (npm view caches 404s).
- **Release tags are `v<release number>`, not `pkg@version`** ("The release number" above; until 2026-11-23 they were feature names such as `optional-playout-engines`). `gh release create v<release number> --title "v<release number> — <what it is about>" --target <release commit's sha> --notes-file <path>` creates the tag + release; the release commit is `chore(release): pkg@x.y.z, …`, made on `dev`; `main` is moved to it first ("From dev to main"). Bumping workspace package versions does NOT change `pnpm-lock.yaml`.
- **GitHub Release Notes:** use `gh release create --notes-file <path>` (or `gh release edit --notes-file <path>`), NOT `--notes "$(cat <<'EOF')"`. Shell escapes in HEREDOCs mangle inline backticks and quotes inside code spans, leaving visible `\"` and `` \` `` in the rendered release body.
- **`npm version <v> --no-git-tag-version` may normalize unicode escapes** in package.json (e.g. `\u2014` becomes a literal `—`) — an extra diff line beyond `version`; harmless, commit it.
- **`@dawcore/components` has no published dependents** — only `website` (`workspace:*`, unpublished) depends on it, so bumping it is a SINGLE-package release, not a workspace-pin republish cascade. Verify republish scope with `grep -rl '"@dawcore/components"' packages/*/package.json` before assuming the cascade.
